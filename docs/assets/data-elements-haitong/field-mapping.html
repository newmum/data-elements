配置面访问哪些数据？

数据面访问哪些数据？

来源 Processor 读取业务表；字段节点按窗口查询获授权的物理字典表；目标 Processor 负责目标表写入。纯转换和 STATIC_MAP 不需要 SQL。

  5. NiFi 调度时编译并验证摘要；每次执行读取一个 FlowFile，在其中分窗口批查并转换，再输出成功记录和受控错误信封。

03 · 同一个画布节点，可能有三种运行形态

新版 · 一个主 Processor + 窗口级批查

来源 → HaitongTransformRecord → 目标
               ├─ success → 正常下游
               ├─ invalid → 保留队列
               ├─ failure → 原始输入保留队列
               └─ retry   → 自回路，有界退避

mappings 内部为 schemaVersion=2.0 或声明 executionEngine=JAVA_RECORD 时，编译器识别为 Java 规则。旧 1.0 规则被预览服务转为 Java 计划，并不证明其已发布拓扑也自动升级。

旧版 · 性能排查优先识别的兼容路径

普通映射：QueryRecord
单值码表：base QueryRecord → SplitRecord(1)
        → EvaluateJsonPath → UpdateAttribute → ExecuteSQLRecord → final QueryRecord
多值翻译：base QueryRecord → ExecuteGroovyScript → final QueryRecord

旧链存在按记录查字典的路径，其请求数随行数增长。旧代码仍在仓库是兼容现状，不应被解读为满足现行批量规范的推荐实现。升级必须检查队列、版本和来源水位，不能直接清空重建任务。

Hive 目标 · 原始采集分支绕过字段治理

保存的画布：来源 → 字段映射 → Hive sink
发布的该分支：来源 ─────────→ Hive sink

HiveSinkPublicationPolicy.forPublication 在发布图上绕过字段映射/字段增强，保留保存的 DSL；如果同一字段节点还被 JDBC 等其他分支使用，它仍会部署供其他分支消费。因而“Hive 入湖慢”不能先归因于字段映射：这个分支可能根本不执行它。仅升级字段节点也会对被移除节点明确拒绝。

04 · 规则协议：不是把文本拼成任意脚本

每条规则是“输入 → 有序步骤 → 输出契约”，可加条件分支。统一内核不依赖 Spring/NiFi/JDBC；函数使用白名单实现，表达式有独立解析器。目标字段引用形成依赖图，必须拓扑可解。

部分关键字段实际含义
计划schemaVersion、executionEngine、policies、rules、dictionaryBindings、schemaContract2.0 草稿，经后端绑定后才成为可发布计划；dictionaryBindings 保存授权后定义。
输入kind=FIELD / LITERAL / EXPRESSION / SYSTEM；name/value/expression/generator字段、常量、安全表达式、确定性系统值；TARGET 可引用其他规则输出。
输出target.name / logicalType / nullable / length / precision / scale输出字段名与逻辑类型；精度、空值和长度约束不是装饰，违规则进入错误策略。
步骤stepId、operator、args、onError、defaultValueDIRECT、CAST、FUNCTION、LOOKUP、LOOKUP_MULTI、STATIC_MAP、DATE_PARSE 等。
条件when、then、else先决定分支，再执行被选分支；字典需求由实际执行的分支触发。
错误步骤/规则 onError；policies.recordErrorMode步骤回退与整条记录/整个 FlowFile 策略分层；不能混同“字典未命中”和数据库不可用。

执行查值表

STATIC_MAP / 内联多值 LOOKUP；通常生成 *_cn 描述列。

  1. 标准候选：da_metadata_t 提供数据元/标准定义，da_metadata_code_t 提供标准代码集及条目。登记界面的匹配和分类建议属于配置期，不能当作运行时每条记录的匹配算法。
  2. 最终确认：来源表 db_table_t.field_governance_config 的 fields[].dictionaryRelation 保存 enabled、sourceType、mode、forceStandardEnabled、forceStandardValueMappings / enumItems、多值开关和分隔符。
  3. 生成任务：Magic 将源编码及已确认标签整理成值表。可接受 sourceCode/sourceValue/value/code 等历史键，标签优先 standardLabel，再兼容 label/sourceLabel/name。空编码/空标签被过滤，同编码取首个有效项。
  4. 落库：旧任务字段记录 func_code='ENUM_MAP'、func_enable=1、dict_enable=0；func_value 保存 {ruleKind:'MANDATORY_STANDARD', values:{...}, multiValue, multiValueSeparator}。
  5. 编译：单值 enumMap 迁为 STATIC_MAP；多值标准翻译使用内联 values 的 LOOKUP_MULTI，不绑定物理字典连接。

真实字典与强制对标不能靠 code_table_id 一列判断：历史上该列可能是物理表 ID、标准字典 ID 或表名。先看 relation 类型和显式关闭状态；明确关闭后不能被旧兼容列重新启用。Binder 在旧记录同时保留字典和 ENUM_MAP 标志时，以有效字典翻译为先。

目标列由登记/物化的 fieldTransformBindings 明确 sourceField → targetField 关系；_cn 是常见建议和历史缺失配置兼容，不能看到后缀就反推所有当前规则。首跳生成治理结果及 ODS 系统字段，级联任务直接保留前一跳结果，不重复翻译、生成主键或覆盖原有治理类型。

登记界面怎样建议标准与对齐取值？

数据元通过 value_domain_id 关联标准代码集；界面同时加载数据元与标准代码候选。类别建议使用归一化词/二元组相似度：精确匹配100分、包含关系90分、其余按Dice相似度；只有分数≥78且领先第二名≥6分才自动建议。值对齐先保留已保存的人工映射，否则仅接受唯一编码或唯一名称的精确匹配；歧义不猜。不同代码集lookup去重后按50个一批请求详情。这些都发生在配置阶段。

另一个配置完整性问题：登记组件请求标准数据元 pageSize=2000 且仅取第一页，但服务端实际将页大小限制为100。数据元超过100时，候选可能不全。这应改为服务端搜索/分页选择或有界分页契约；它影响可选标准的完整性，不是NiFi逐行处理慢的直接解释。上游标准API是租户级读取，不要误称它也执行字典数据源的同一套角色过滤。

06 · 码表：定义绑定、键收集、参数化 SQL、结果回填

1. 用户选的是登记资源，不是任意连接

定义包含 datasourceId / tableId / schema / table / keyColumns[] / keyTypes[] / valueColumn / filter / duplicatePolicy。后端用服务器可信配置解析连接，校验表及键/值/过滤列都属于该登记，重算定义身份并去重。不能由浏览器传 JDBC 密码或任意 SQL 绕过登记。

2. 一个窗口先聚合需求，再查库

内核先执行可执行规则；遇到未加载的字典键，用不填充栈的 Wait 暂停该规则，继续收集其他行/字段的需求。按 字典定义 ID 合并为去重键集合，然后依次调用 provider。结果加载后再执行待完成规则；若下一次 lookup 依赖前次结果，进入下一阶段。这里仍有规则重跑与对象分配开销，但不是逐行 SQL。

3. 物理 SQL 只读取键列和一个值列

-- 示意 SQL；标识符经过登记授权与方言引用，值使用绑定参数
SELECT code, label
FROM authorized_schema.dictionary_table
WHERE code IN (?, ?, ...)
  AND (category = ? AND status = ?)

-- 复合键使用有界 OR-of-AND：
WHERE ((kind = ? AND code = ?) OR (kind = ? AND code = ?)) AND (...固定条件...)

单次键容量 C=min(500, floor((P-F)/K))：P 为参数预算（SQL Server 2000、SQLite 900、其他分支 1000），F 为固定过滤参数数，K 为复合键列数。键数超过 C 就拆批，单条 SQL 超时 10 秒。去重键正常随输入增长而增多，允许按这些有界批次增长；不要求任意大数据量永远只有 1 SQL。

4. 多值码表

LOOKUP_MULTI 将数组或按字面分隔符拆出的 token 去首尾空白、去空 token，窗口查询键去重，但输出保留原有顺序和重复项。需明确 missPolicy / allMissingPolicy / partialMissingPolicy / nullLabelPolicy / emptyLabelPolicy / outputMode。例如 A,,X,A,B 在“部分未命中保留 token”时得到 甲,X,甲,乙；查询键仅 A、X、B 三个。

5. 什么情况下仍会查很多次？

  • 默认 LIVE_BATCH 不跨窗口复用字典结果。
  • 同表、同键、同过滤但 valueColumn 不同，当前仍是不同定义；同一窗口可能对同表发出多次 SQL。
  • 不同数据源、不同过滤、不同 freshnessMode、前后依赖阶段，均不能草率合并。
  • FlowFile 太碎会产生很多小窗口。1 万行分成 1 万个 FlowFile，与一个 FlowFile 内分窗口，成本不同。

07 · 三种码表新鲜度：收益与正确性同时决定

模式实际读取行为适用条件与代价
LIVE_BATCH（默认）每个窗口、每个依赖阶段的缺失键按批查询真实码表；窗口内复用结果。要求读到近期内容；不同窗口读取时刻不同，不提供整个任务的数据库快照隔离。
TTL_BATCH_CACHE命中直接返回；未命中键仍合并批查，包含未命中值的负缓存。TTL 1–600 秒，最多约 5000 项，值超过 4096 字节不缓存。适合高复用、允许明确时效窗口的码表。更新后短时间可能仍见旧值/旧未命中；跨定义、跨服务/租户隔离不能取消。
VERSIONED_SNAPSHOT制作时完整读取并保存资源，运行加载固定版本内容及索引，运行查值不发实时 SQL。适合小型稳定码表和可重放任务。完整快照上限 5000 行、约1MiB，不允许悄悄截断；修改后要显式制作/发布新快照。
强制对标 STATIC_MAP / 内联 values值表已在规则中，执行时内存查找。这是确认后的固定映射语义，不是通过开缓存把任意实时码表转成静态值表。

缓存键包含作用域、定义摘要及类型化键；快照同时校验 definitionHash 与 snapshotHash。NiFi 服务启用/禁用会清空缓存。只更改前端下拉值不会自动改变已发布运行服务。

10 · 性能约束、提交边界与错误语义

约束当前值/行为对性能的影响
记录窗口最多512行，输入累计8MiB；单行1MiB窗口大小是内核常量；当前 Processor 未提供可直接调大的 window-size 属性。宽行会提前切窗。
结果预算单字段步骤结果256KiB；窗口输出累计8MiB；字典结果32MiB“8MiB窗口”不是堆总占用上限，还需计入Map、字符串、字典索引、输出和 NiFi Reader/Writer。
规则/字典最多1000条规则、1000个字典定义、8个不同字典数据源100个字段不等于100个数据源；不同返回列仍可能产生多个定义。
查找阶段最多16阶段；一个阶段总请求键不超过20000；单多值字段最多1000 token有依赖的 lookup 会增加阶段；单阶段字典依次读取，不是无界并发。
并发每个 Processor 实例内部 Semaphore(2)并发任务设成8，也不会在本处理器内同时执行8个输入；设成1时内部2的能力也用不到。
事务/可见性整个输入 FlowFile 一次 Session 成功结束；内部窗口不独立提交巨大 FlowFile 虽分窗限内存，但首批输出可见性、重试重算范围、连接排队仍受整个输入影响。
重试DICTIONARY_UNAVAILABLE 才进入有界重试，默认最多5次；指数退避，上限300秒每次重试保留原输入并删除候选输出；重试风暴会显著降低有效吞吐。
数据错误FAIL_FLOWFILE / ROUTE_INVALID默认 FAIL_FLOWFILE 可因坏数据保留整输入；ROUTE_INVALID 分离坏行但改变处理语义，不能只为跑分快而切换。

invalid 信封包含计划摘要、输入行序号、错误及原记录，位于受控内容队列；普通日志/属性不应保存原始敏感记录。字典不可用与字典编码不存在分别处理，不能把连接故障伪装成 NULL。

12 · SQL 数量交互估算器

模型只估算一个依赖阶段、固定窗口、各定义键数相同的批量 SQL；不模拟CPU、网络或数据库计划，不是实测预测器。实际有按字节切窗、重复键、TTL命中、阶段差异时，以真实属性计数为准。输入“每窗口去重键”包含多值 token 或键分布，不必等于行数。

简化公式：窗口数 × 定义数 × ceil(每窗口唯一键数/C)。末窗按同样键规模作保守近似；实际末窗通常较少。旧链参照“每行每定义一次查询”，只用于理解放大倍数，不代表任意旧组合拓扑的精确SQL。
