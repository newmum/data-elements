## 1. 建设目标与边界

### 1.1 目标

1. 一个字段映射节点在 NiFi 中对应一个主要处理器，20 个或 100 个字段不生成逐字段处理器。
2. 普通转换、条件、函数、单值码表、多值码表、标准映射、统一格式共用一套类型语义；预览与正式执行使用相同版本的 Java 内核。
3. 消除单值字典逐记录数据库往返。读取按窗口、依赖阶段、字典定义和参数容量组织；关闭缓存仍满足批量规范。
4. 让业务人员在字段行内完成简单规则，在详情抽屉组合复杂规则；明确展示转换前后、失败原因和规则来源。
5. 完整承接当前数据接入登记、ODS 物化、首跳治理及后续级联保留规则，升级时不丢失已有功能。
6. 以任务为单位选择迁移，支持计划对比、版本校验、队列保护和可验证回退。

### 1.2 范围划分

| 纳入本次详细设计 | 由现有其他模块继续承担 |
| --- | --- |
| 字段匹配、值计算、类型转换、规则链、字段验证 | 来源查询、增量水位、文件目录与工作表选择 |
| 数据库字典和登记标准映射的统一执行 | 数据源主档、连接凭据、驱动配置 |
| 单值/多值、身份证显式转换、日期解析和函数 | 目标数据库写入、UPSERT、目标主键与数据库事务 |
| 接入配置和画布 DSL 的转换与版本保护 | 目标物理表的创建、变更和删除审批/操作 |
| 规则预览、计划编译、NiFi NAR 和发布适配 | 任意用户脚本执行、任意 SQL 重写、跨记录聚合和多表 JOIN |

规则引擎第一期处理一级字段。JSON 提取可以是返回单值的显式函数，但不等于自动支持嵌套数组展开、笛卡尔积、行合并或流式窗口聚合。新增目标字段只改变规则输出 Schema；目标物理表需要通过现有物化/结构流程确认，不能由“新增字段”按钮偷偷执行 ALTER TABLE。

## 2. 现有系统核对与差距

### 2.1 当前业务链路

当前有效接入链路以 `access-apply`、物化模板和接入任务生成接口为主：读取已登记来源及治理配置，形成目标字段和 DDL，创建或复用目标表，保存任务字段映射并生成画布 DSL，最后由海通发布编译器生成 NiFi 流程。

需要区分历史低代码组件与真实运行主链：`access-modal.vue` 中仍有模拟创建流程，旧 `field-mapping.vue` 的码表和函数选项包含硬编码演示项。不能据此宣称当前系统已经具备截图中的完整逐字段转换功能。源码证据和接口见第 20 章。

### 2.3 必须消除的语义分歧

| 位置 | 核查到的差异 | 升级要求 |
| --- | --- | --- |
| enumMap 无 fallback | Java 预览返回原值，SQL 分支返回 NULL | 新规则必须持久化未命中策略；存量按实际旧路径生成兼容策略 |
| 单值登记枚举 | 任务生成路径可生成 `fallback=null`，Binder 路径可生成“未映射” | 两种历史结果均不能静默合并；迁移报告展示来源和前后结果 |
| concat 含 NULL | 预览过滤 NULL 后拼接；SQL 把 NULL 作为空串保留分隔符位置 | 增加 `nullElementPolicy`，存量按旧执行结果迁移 |
| 未实现转换函数 | 部分预览落入原值返回分支 | 新内核返回明确能力错误，禁止成功假象 |
| when/target/全局策略 | 编辑协议可表达，正式执行能力不足 | 配置、校验、预览、执行逐项一致后才开放发布 |
| 当前预览数据 | 前端构造一行 `${字段}_样例` | 标为“演示样例”；实际采样必须通过授权、有界的来源采样服务 |
| 字典预览查询 | 单值预览存在逐记录/字段查询；多值预览按每条映射批取，尚未跨同字典字段合并 | 预览与NiFi都使用窗口级LookupDemand收集，不能只替换正式处理器 |
| 当前部署 | 旧流程清理后重新编译，不等于已实现状态迁移与回退 | 第 17 章新增发布状态机及状态保存验收 |
| 类型错误缺省策略 | 任务生成器使用 SKIP_ROW，Binder 缺省可使用 CAST | 逐任务保留并提示旧语义，不能在恢复规则时暗改丢行/转型行为 |
| 登记字典条件/customSql | 登记可表达的条件和自定义 SQL 未全部被任务生成承接；LIKE/IS NULL/IS NOT NULL 可能被跳过 | 新规则统一条件 AST，未知条件拒绝；复杂 SQL 进入明确迁移分类 |

### 2.4 当前 NiFi 执行拓扑

| 路径 | 当前主要执行形态 | 主要处理器数量及问题 |
| --- | --- | --- |
| 普通映射、常量、部分函数、单值枚举 | QueryRecord | 通常 1 个；存在 SQL 与 Java 预览语义差距 |
| 单值数据库字典 | base QueryRecord → SplitRecord(1) → 每连接组 EvaluateJsonPath / UpdateAttribute / ExecuteSQLRecord → final QueryRecord | `3 + 3D`，D 为连接组数；1 组 6 个，2 组 9 个；每条记录按组查库 |
| 纯多值翻译 | base QueryRecord → ExecuteGroovyScript → final QueryRecord | 3 个；已有批查，但缺少总字节/token 等上限 |
| 单值和多值混合 | 上述两条路径组合 | `4 + 3D`；保留单值逐记录开销 |
| 同库来源下推 | 满足条件时把治理转成来源 SQL | 仅限可证明适配的全量、同连接等任务，受来源方言约束 |

上述计数仅指字段映射节点的主要 Processor，不包含来源、目标、Controller Service 和辅助错误设施。QueryRecord 在 FlowFile 上执行 Calcite SQL，来源下推则在真实数据库执行 SQL，两者必须分别分析。[Apache QueryRecord 说明](https://nifi.apache.org/components/org.apache.nifi.processors.standard.QueryRecord/)

## 4. 总体架构与模块职责

### 4.1 统一处理链

```text
澄天登记治理配置 ──> 接入规则适配器 ──┐
                                     ├─> MappingDraft ─> 统一编译器 ─> ExecutionPlan
海通现有画布编辑器 ──────────────────┘                      │
                                                ┌─────────┴─────────┐
                                                │                   │
                                        后端正式预览适配器      NiFi Record 适配器
                                                │                   │
                                                └──── 纯 Java 内核 ─┘
                                                          │
                                              已批量预取的字典结果

现有来源 Processor ─> HaitongTransformRecord ─success─> 现有目标 Processor
                                      ├─invalid─> 受控错误记录队列
                                      ├─failure─> 整批故障保留
                                      └─retry───> 有界重试流程
```

### 4.2 模块拆分

| 模块 | 输入/输出 | 主要职责 |
| --- | --- | --- |
| M01 元数据与治理适配 | 登记字段/关系 → 来源、目标 Schema 和规则草稿 | 批量解析字段、治理来源、首跳/级联差异和显式清空 |
| M02 字段映射编辑 | 草稿 → 新草稿版本 | 行配置、规则抽屉、推荐、模板、批量修改和差异确认 |
| M03 规则编译与校验 | 草稿 + Schema + 能力 → 不可变计划 | 类型检查、依赖 DAG、函数/字典绑定、预算与兼容性 |
| M04 规则内核 | 类型化输入 + 固定上下文 + lookup 结果 → 输出/错误 | 无外部 I/O 的转换、条件、验证和结果投影 |
| M05 字典提供者 | 批量类型化键 → 命中/未命中/故障 | LIVE_BATCH、静态快照、批次分割、授权绑定与缓存 |
| M06 预览服务 | 同一计划 + 限量样本 → 逐行逐规则结果 | 调用与 NiFi 相同内核；标明样例和字典版本 |
| M07 NiFi 扩展 | FlowFile → success/invalid/failure/retry | Record Reader/Writer、窗口编排、Session 生命周期 |
| M08 发布与能力适配 | 计划 + 目标节点能力 → 部署版本 | Bundle 精确绑定、全节点版本检查、状态迁移、回退 |
| M09 运行观测 | 计数与受控错误 → 监控/回溯 | 规则级错误、SQL/窗口指标、版本和重试轨迹 |

内核不依赖 Spring、NiFi、JDBC、HTTP、租户上下文，不允许函数内部获取连接或调用接口。预览适配器和 NiFi 适配器负责外部资源读取及执行编排；二者可复用有界窗口协调库，不能各写一套字典/错误语义。

Java 自定义处理器作为长期方案；UpdateRecord 可保留给简单原生任务，QueryRecord 保留给通用 SQL 节点。LookupRecord 或脚本组件本身并不能证明已满足本系统的批量字典协议。选择 Java 的理由是执行一致性和可控生命周期，性能收益须压测验证。[UpdateRecord](https://nifi.apache.org/components/org.apache.nifi.processors.standard.UpdateRecord/)、[DatabaseRecordLookupService](https://nifi.apache.org/components/org.apache.nifi.lookup.db.DatabaseRecordLookupService/)

## 5. 数据接入与画布的业务衔接

### 5.1 规则来源和所有权

| 规则来源 | 展示标签 | 修改与回写约定 |
| --- | --- | --- |
| 登记的字典/标准/统一格式 | 登记继承 | 任务内修改形成显式覆盖，不悄悄修改登记主档 |
| 接入自动生成 | 系统生成 | 系统字段和首跳规则需保护；覆盖时说明影响 |
| 用户手工配置 | 人工配置 | 保存到当前任务/画布，保持稳定 ruleId |
| 导入模板 | 模板导入 | 导入后独立草稿，记录 templateId/version 来源 |
| 历史迁移 | 兼容迁移 | 保留 legacyRuleRef、旧策略和迁移诊断 |

字段身份优先使用当前租户已登记的字段 ID，名称只是引用快照。新增表达式字段用局部稳定 ID，发布前必须绑定可验证的目标字段。重命名时按 ID 对齐并提示；ID 缺失的旧规则只允许唯一名称匹配，出现歧义时阻止发布。

### 5.2 接入配置流程

来源数据源与来源表均须 `asset_status > 0`，并满足有效记录、当前租户和角色数据范围，不把条件擅自收窄为全部必须等于2。字典、目标和来源关联仍分别按现行业务规则校验。

1. 打开接入申请/物化配置，按当前租户与角色范围批量取得来源字段、目标候选、治理设置、字典定义及版本；打开行为不写 DSL。
2. 生成来源逻辑 Schema、目标物理类型建议及规则草稿，展示“直接、字典翻译、强制对标、统一格式、系统字段”的来源。
3. 用户可调整目标字段、规则和异常策略。新增 `_cn` 或表达式字段同步进入目标字段预览与 DDL 预览。
4. 提交前批量校验全部选中目标、字典、字段及关联关系，比较配置版本。任一目标越权或失效整次拒绝，不留下半套任务。
5. 沿用现有建表/复用流程；确认实际目标 Schema 后保存接入任务、字段映射和画布草稿。DDL 是外部副作用，不能声称与所有任务记录共享一个跨库事务；失败需保留建表结果和可重试状态，不盲目删除已建表。
6. “保存配置”与“部署运行”仍是不同用户动作。保存成功返回草稿版本，部署成功才显示运行计划版本。

### 5.3 首跳与级联

按资源中心 ODS 分域 `sort_no` 决定新建链路顺序，同序号按分域 ID 稳定排序，不按点击顺序、库名或数组偶然顺序推断。每个任务只有本跳真实来源和一个目标库。

- 首跳：应用登记确认的治理规则，生成 ODS_UUID、ODS_RKSJ、ODS_GXSJ，保留原编码并按规则新增描述字段。
- 后续跳：来源是上一跳物化表，直接传递系统字段、描述字段和已治理类型；默认不重新生成 UUID、重新翻译或再次转换身份证。
- 用户主动增加后续治理时作为新的显式规则，并显示“将对已治理值再次处理”的影响，不能通过恢复历史配置偷偷增加。
- 组合画布只聚合展示。切换当前任务保留草稿；保存、部署、启动、停止只作用于选中任务。

主增量字段 `incrementalColumn` 只在新建模板时初始化一次。打开、保存、启动及字段映射升级均保持已保存选择，不从登记重新覆盖；缺失或失效时提示手工补齐或明确改为全量。这是配置保护，与运行水位保存分别验收。

### 5.4 原生类型与统一格式

LXDH、SFZH 继续作为字符语义，不丢前导零、不擅自截断或补位。DATE/DATETIME 进入输出逻辑类型和目标 DDL；目标类型按真实方言转换，例如 SQL Server DATETIME2、PostgreSQL TIMESTAMP、Oracle/达梦既有 DATE 约定。不能把目标库的类型名称直接拿来作为跨引擎函数名。

显式关闭字典、清空统一格式、取消强制对标均要保留“用户已清空”标记，不能因旧 `code_table_id` 有值而重新启用。`code_table_id` 可能指向标准字典或旧表名，必须结合治理来源判别，不能一律查询同 ID 的物理表。

| 输入模式 | 单字段/多字段/常量/表达式/系统值 | 字段可按名称和中文注释搜索；常量可显式选择 NULL |

### 6.3 自动匹配与严格模式

自动匹配按“稳定字段关联 ID → 完全同名 → 经明确配置的大小写/别名归一 → 注释与类型推荐”分级。只对未配置目标生成建议；人工规则默认锁定，重跑推荐不覆盖。一个候选对应多个目标时保留一对多；同一目标多个候选时显示冲突，由用户选择，不取第一条。

“严格映射”作为预设组合，可展开查看：

- `requireAllRequiredTargets=true`：目标必填字段必须有输出或明确的数据库默认值处理。
- `allowUnknownSourceFields=false`：规则引用必须属于来源 Schema。
- `onSourceSchemaDrift=FAIL`：运行输入结构变化时拒绝整批，不能自动套用新字段。
- `allowUnmappedPassthrough=false`：仅输出确认字段。
- `onTypeMismatch=ERROR`：产生字段错误，交给节点 `recordErrorMode`。严格预设默认 FAIL_FLOWFILE；用户可以明确改为 ROUTE_INVALID，但字段/Schema 校验仍保持严格。

宽松预设也不能放宽租户和角色授权、重复目标、循环依赖、未知函数及凭据保护。字段缺失补 NULL 是独立选项；目标不允许 NULL 时仍须进入错误策略。

### 6.4 批量操作、模板和预览

批量设置支持空值策略、日期模式、目标类型、函数链和启用状态。后端一次接收有界规则 ID 集合，先完成授权和版本检查，返回逐规则影响；前端确认具体差异后一次应用到草稿，支持撤销，禁止逐行请求。

模板保存协议版本、参数、函数版本需求与占位引用，不保存连接密码或样本业务数据。跨任务导入先重绑字段/字典/目标，生成冲突清单；不能因模板带有资源 ID 直接获得访问权限。

预览提供手工样例、可识别的演示样例和授权来源采样三种方式。建议默认 20 行，最大 100 行、2 MiB；超限明确拒绝或要求缩小样例。样本采集一次请求完成，所有规则共用同一批输入；不为每个字段分别取样。预览展示计划摘要和相同上下文，接口失败只提示本次预览不可用，不能退回浏览器另一套算法伪装正式结果。

## 7. 逐字段规则目录与执行语义

### 7.1 规则目录

| 规则编码 | 中文名称 | 必填参数 | 输出与使用场景 |
| --- | --- | --- | --- |
| DIRECT | 原值映射 | 来源字段、目标字段 | 保留逻辑值和类型，字段重命名不改变值 |
| LITERAL | 常量赋值 | type、value | 字符、数值、布尔、NULL；不把“null”字符串当 NULL |
| CAST | 按目标类型转换 | logicalType；decimal 另需 precision/scale | 显式转型、精度/溢出和布尔值集合 |
| CONCAT | 多字段合并 | 输入列表、separator、nullElementPolicy | 有序组合，支持静态前后缀 |
| STRING_OP | 字符串处理 | 具体函数与类型化参数 | trim、替换、截取、补齐、大小写等 |
| NUMBER_OP | 数值处理 | 函数、精度与舍入 | 精确数值计算、四则、舍入 |
| DATE_PARSE / DATE_FORMAT | 日期解析/格式化 | 输入/输出模式、逻辑类型、时区策略 | DATE、DATETIME、瞬时时间/时间戳、字符串 |
| LOOKUP | 单值码表翻译 | definitionRef、键引用、输出列、missPolicy | 数据库字典批取；支持复合键 |
| LOOKUP_MULTI | 拆分码表翻译 | 同上 + split/join/token 策略 | 多码保序输出或数组输出 |
| STATIC_MAP | 枚举/强制对标 | 版本化 typed entries、输出类型 | 运行零业务查库；标准码与标准名分别输出 |
| ID_CARD_15_TO_18 | 身份证 15 位转 18 位 | 世纪规则、校验选项、错误策略 | 显式升级旧号码，输出 STRING(18) 语义 |
| ID_CARD_VALIDATE | 身份证结构校验 | 长度、日期、校验位选项 | 返回布尔/错误或保护原字段，独立选择 |
| CONDITIONAL | 条件赋值 | predicate、then、else | 短路选择分支规则链 |
| EXPRESSION | 安全表达式 | 受限 AST/可解析表达式 | 引用来源、参数、已计算目标，禁止任意脚本 |
| VALIDATE | 输出校验 | 必填、长度、范围、枚举或正则 | 失败进入指定记录策略 |
| SYSTEM_VALUE | 系统值 | 受控生成器和时间上下文 | ODS 系统字段及经允许的批次信息 |

规则支持“直接→去空白→字典→格式化→校验”等显式步骤链。普通用户优先看到预设，计划始终保存算子和参数；不使用易失真的数字菜单序号或一长串自由函数文本保存业务含义。

### 7.2 输入状态、策略优先级和默认值

必须区分 `SCHEMA_FIELD_MISSING`（运行结构缺字段）、`RECORD_FIELD_MISSING`（结构允许但某记录缺值）、`NULL`、`EMPTY_STRING`、`BLANK_STRING`、正常值、字典未命中和执行故障。字符串空白仅由显式 trim/blankToNull 预设处理；不把数值 0 和 false 当成空值。

Schema 字段缺失先按漂移策略处理，不能被普通 onMissingSource 覆盖。只有编译时声明 `sourceOptional=true`、已确定逻辑类型且允许该字段在运行 Schema 中缺省，才把它交给记录缺值策略。“字段不存在补 null”预设必须明确这种许可；严格预设默认不启用。

策略优先级：步骤明确策略 → 字段规则策略 → 节点策略 → 当前版本默认值。Schema 非空、目标类型、权限与资源失效不能被宽松策略跳过。

| 状态/事件 | 新建规则默认 | 可选动作与约束 |
| --- | --- | --- |
| 记录来源字段缺值 | ERROR | NULL、DEFAULT_VALUE；“字段不存在补 null”预设显式选择 NULL；Schema 缺省另需上述许可 |
| 来源值 NULL | PRESERVE_NULL | DEFAULT_VALUE；空串不自动归入 NULL |
| 输入空串 | PRESERVE | NULL、DEFAULT_VALUE、ERROR；日期登记兼容预设可显式 blankToNull |
| 字典键不存在 | NULL | EMPTY_STRING、KEEP_INPUT、DEFAULT_VALUE、ERROR |
| 函数/转型数据错误 | ERROR | NULL、KEEP_SOURCE、DEFAULT_VALUE；回退仍需满足目标类型 |
| 记录数据错误 | FAIL_FLOWFILE | ROUTE_INVALID；存量 SKIP_ROW 迁移为明确隔离语义并提示变化 |
| 重复字典键 | ERROR | 明确唯一选择策略；历史字典序最大兼容模式见 11.3 |
| 字典连接/Reader/Writer故障 | 基础设施故障 | 不适用“未命中回退”，进入 15 章故障协议 |

来源缺失/NULL 的默认值替换发生在规则链前，替换值继续执行步骤。步骤数据错误的字段级回退结束该字段链，进入最终目标类型与约束校验，不递归执行失败步骤。LOOKUP 未命中是正常查找结果，根据 missPolicy 产生当前步骤值后可继续后续步骤。

协议统一使用字段/步骤 `onError=ERROR` 表示产生错误并交给节点处理，节点 `recordErrorMode` 仅为 `ROUTE_INVALID` 或 `FAIL_FLOWFILE`。不再引入含义重叠的 FAIL_RECORD；第一期不允许字段直接覆盖整条记录的路由模式。

`KEEP_SOURCE` 指本规则最初的来源值，`KEEP_INPUT` 指当前步骤输入值；对于先 trim 再查字典的规则二者可能不同，不能混用。多输入规则使用 KEEP_SOURCE 时必须明确回退字段，禁止把数组随意塞入字符目标。

新规则默认值是本方案决策，不能直接覆盖存量。当前 `SKIP_ROW`、`CAST`、NULL、“未映射”等历史配置均需在迁移报告中显式落实；`CAST` 作为旧类型错误选项迁移为显式 CAST 步骤和单独错误动作，不继续把转换动作混在错误策略里。

### 7.3 原值、常量、类型转换与合并

| 项目 | 详细约定 | 例子 |
| --- | --- | --- |
| 原值 | 返回原逻辑值；名称变更不触发隐式转型 | `"001" → "001"` |
| 常量 | 常量携带类型；NULL 要显式选择 | STRING `"1"` 与 INT `1` 不相同 |
| 整数 | 校验小数、范围和符号；默认拒绝小数截断 | `"12.5" → INT` 默认报错 |
| 小数 | BigDecimal；precision/scale、roundingMode 必填或版本默认 | `"12.345" → DECIMAL(6,2), HALF_UP = 12.35` |
| 浮点 | 明确有限数值要求，默认拒绝 NaN/Infinity | 金额默认用 DECIMAL，不能转 double 后再补精度 |
| 布尔 | 明确 trueValues/falseValues，大小写策略 | `"Y"` 只有配置后才转 true |
| 字符 | 以字符类型保留编码；长度溢出默认错误 | 截断必须显式 STRING_OP，不按目标长度暗截 |
| CONCAT | 保留输入顺序；NULL 可 EMPTY、SKIP、ERROR | `[A,NULL,B]` + `,`：EMPTY=`A,,B`，SKIP=`A,B` |
| 输出投影 | 规则输出优先替换同一身份的直通字段；冲突需在编译时消除 | 不生成 `SELECT *, a AS a` |

第一期字符串截取按 Unicode code point 计数，索引从 0 开始、结束位置不含；数据库写入列长度另按目标能力校验。字节长度、UTF-16 码元长度和用户可见字符簇不混称“字符数”。JSON 数字超过 JavaScript 安全整数范围时在编辑/接口层使用类型化十进制字符串传递。

### 7.4 单值码表

配置至少包含：字典引用、查询键列表、取值列、静态/记录相关条件、类型、未命中策略、重复键策略、新鲜度和定义版本。支持一份字典返回多列供多个目标使用；请求按字典定义合并，不能每列查询一次。

| 键状态/查找结果 | 行为 |
| --- | --- |
| NULL 键 | 默认不发查询，按 NULL 输入策略 |
| 查到且 label 为正常值 | 输出该值 |
| 查到且 label 为 NULL | 记为“已命中空值”，按 nullLabelPolicy=PRESERVE/AS_MISSING/ERROR |
| 查到且 label 为空串 | 与 NULL 区分，可原样输出或显式校验 |
| 没有对应键 | 执行 missPolicy |
| 连接超时/权限失效 | 基础设施/资源错误，不能按未命中处理 |
| 同键返回多条 | 执行重复键策略，不随机取第一条 |

示例：字典 `{A:在用}`，输入 `B`。三个截图预设分别输出 `""`、`"B"`、`null`。目标为数值或不允许空值时，回退还需通过目标校验，界面应在编译阶段尽量提前提示冲突。

### 7.5 拆分码表与多值标准

处理顺序：读取字符串/数组 → 受控拆分 → 可选 trim → 空 token 策略 → 收集去重查询键 → 批取 → 按原 token 顺序回填 → 拼接/数组输出。查询键可以去重，输出默认保留重复，不排序。

| 参数 | 新建默认/含义 |
| --- | --- |
| inputMode | STRING；也可显式 ARRAY，数组不再次按分隔符拆分 |
| splitMode / inputSeparator | LITERAL / 必填；REGEX 需受限正则能力 |
| trimTokens / emptyTokenPolicy | true / DROP，兼容当前多值行为 |
| preserveOrder / preserveDuplicates | true / true |
| outputMode / outputSeparator | STRING / 默认与输入分隔符一致 |
| partialMissingPolicy | KEEP_TOKEN，兼容当前部分命中保留原码 |
| allMissingPolicy | NULL / KEEP_SOURCE / ERROR；截图扩展 EMPTY_STRING、DEFAULT_VALUE |
| maxTokens | 建议每记录每字段 1,000，另有窗口总量预算 |
| nullLabelPolicy / emptyLabelPolicy | 分别处理已找到键但label为NULL/空串；新建默认PRESERVE，历史兼容默认AS_MISSING |

高级配置允许 partialMissingPolicy 为 EMPTY_SLOT、DROP_TOKEN、NULL_RECORD_VALUE、ERROR。EMPTY_SLOT 保留分隔位置，DROP_TOKEN 删除该项，二者不能都叫“转空”。截图“拆分码表不存在转空”在新预设中明确采用 EMPTY_SLOT；历史旧系统实际含义未知，迁移时不能靠截图自动决定。

统计区分 `keyFoundCount` 与 `effectiveMatchCount`。allMissingPolicy依据应用label策略后的有效命中数判断；新建PRESERVE把空label视为有效命中，旧多值兼容固定 `nullLabelPolicy=AS_MISSING`、`emptyLabelPolicy=AS_MISSING`，保留当前“没有有效译名就按未命中处理”的结果。不能仅保持token策略却改变空译名语义。

示例：输入 `A,,X,A,B`，字典 A→甲、B→乙。兼容预设输出 `甲,X,甲,乙`。EMPTY_SLOT 输出 `甲,,甲,乙`；DROP_TOKEN 输出 `甲,甲,乙`。输入 `X,Y` 且全部未命中时，按 allMissingPolicy 输出 NULL、原字符串、空串、默认值或错误；全部 token 为空时使用 emptyInputPolicy，不伪记为全部字典未命中。

第一期不把 CSV 引号转义规则隐含套入多值字段。若值本身包含分隔符，优先使用 ARRAY；需要 CSV token 解析时另选明确的解析器和转义配置。设置输出去重或排序会改变业务语义，必须显式勾选并进入计划摘要。

### 7.6 强制对标、枚举和输出绑定

沿用登记已确认的 `sourceCode → standardCode/standardLabel` 关系，不运行时调用推荐或模糊匹配。现有主要链路只输出标准名称；新设计增加三种明确输出：标准代码、标准名称、代码和名称双输出。

双输出是两条目标规则共享一次 STATIC_MAP 需求，不能在一条规则里隐式增加未登记列。默认保留来源代码，在绑定的目标描述字段输出名称；`_cn` 只是默认命名建议，真实输出依据 `fieldTransformBindings` 的目标 ID。同名冲突、删除输出列、标准快照缺失均须定位具体绑定并拒绝发布。

静态映射使用类型化条目数组，保留字符 `01`、字符 `1`、数字 1 的差异。多值标准复用 7.5 节，无需查询物理字典库。没有值域映射的手机号/身份证数据元标注不能自动生成中文译名列。

### 7.7 身份证转换与校验

SFZH 现有标签只表示统一格式要求，不自动启用 15→18。用户必须显式选择 `ID_CARD_15_TO_18`；建议保留原字段并把转换结果写入新字段，覆盖原字段时显示影响。

| 参数 | 设计约定 |
| --- | --- |
| 输入类型 | STRING；禁止科学计数法数值输入和数值化后丢零 |
| trim / normalizeX | 显式选项；X 默认统一大写 |
| acceptedLength | 15；already18Policy 可选 VALIDATE_AND_KEEP 或 ERROR |
| centuryPolicy | 必填；历史 1900 年代数据可显式用 PREFIX_19，不能根据当前年份猜世纪 |
| birthDatePolicy | 严格真实日历日期；拒绝不存在的日期 |
| checksumPolicy | 18 位输入校验；15 位转换按标准计算新校验位 |
| regionValidation | 默认不以当前行政区划否定历史地址码；启用时绑定有版本的区划字典 |
| onError | ERROR、NULL、KEEP_SOURCE 或 DEFAULT_VALUE；ERROR交节点recordErrorMode，其余回退必须与目标长度/非空兼容 |

转换步骤：确认 15 位数字格式及明确世纪 → 在出生日期两位年份前加入世纪形成 17 位本体 → 严格校验出生日期 → 计算校验位 → 返回 18 位字符串。标准的 17 位从左到右权重为 `7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2`，加权和模 11 的 `0..10` 对应 `1,0,X,9,8,7,6,5,4,3,2`。世纪补全是本系统显式迁移策略，不能把它说成对所有历史号码无条件适用的规则。[GB 11643-1999 原文](https://zjw.beijing.gov.cn/Portals/0/zhuanti/fazhan/%E8%BA%AB%E4%BB%BD%E8%AF%81GB11643-1999.pdf)

结构/校验位通过不等于真实人员或有效证件核验。预览和日志默认脱敏，测试使用公开标准示例或合成测试向量，不使用真实人员数据。出生日期、性别、地址码提取可作为后续独立函数，须单独启用，不能在转换时自动新增敏感字段。默认不提供会丢失世纪与校验位的 18→15 逆转换。

### 7.8 日期、时间和四种预设

| 预设 | 输入配置 | 输出语义 |
| --- | --- | --- |
| 转 DATE | 明确模式，如 `uuuu-MM-dd` | LocalDate，仅年月日；从瞬时时间取日期时必须给 zoneId |
| 转 DATETIME | 如 `uuuu-MM-dd HH:mm:ss` | LocalDateTime；若来源带偏移，先指定转换/保留时区策略 |
| 转时间戳数值 | 明确输入时区及单位 SECOND/MILLISECOND | epoch 数值，禁止按数值长度猜秒或毫秒 |
| 转自定义字符串 | 输入模式和输出模式 | STRING；例如 `uuuuMMdd`、带偏移 ISO 字符串 |

底层区分 DATE、LOCAL_DATETIME 和 INSTANT。DateTimeFormatter 使用固定 Locale、严格解析及版本化模式；DST 缺口/重叠默认报错，也可显式选择早/晚偏移。非法日期不能自动滚入下月。NULL、空串、纯空白及解析失败分别处理；默认不轮流尝试模糊格式并取首个成功值。

确需多种输入格式时保存有序候选和歧义策略，多个格式解析为不同日期则报 `DATE_AMBIGUOUS`。历史 CAST 自动迁移仅覆盖可证明等价的输入形态，其余展示样本差异并确认。`now()` 从本次 ExecutionContext 取值，统一到 FlowFile/预览上下文，不能在字段遍历里反复取系统时间。

### 7.9 条件、表达式与验证

条件 AST 支持 eq/ne/gt/ge/lt/le、in/notIn、isNull/isMissing/isEmpty、and/or/not；NULL 比较用显式谓词，普通比较遇 NULL 得 UNKNOWN，分支默认进入 else 并可记录诊断。then/else 输出需能归一到目标类型；缺失 else 必须明确 NULL 或错误。

函数、字段和目标引用均是 AST 节点。支持来源 `${field:CODE}`、规则输入 `${value}`、类型化 `${arg:n}` 及目标结果 `${target:TARGET}` 的受限迁移语法；不允许反射、类加载、文件、网络、系统进程、任意 Java/Groovy/JavaScript。`row.index` 是本输入 FlowFile 的零基序号，重分批会变化，不可用于全局唯一主键。

输出验证包括非空、最大长度、数值范围、精度、允许值、格式和正则。验证发生于最终类型确定之后；一条记录多字段错误可有界收集，最多返回前 20 项并给总计数。验证不执行数据源查询；唯一性和跨记录约束仍交目标库/独立质量模块。

### 8.2 函数元数据契约

能力目录为每个函数提供 `name、version、category、description、inputTypes、outputType、argsSchema、nullBehavior、deterministic、previewSupported、runtimeSupported、introducedIn、deprecatedAliases、examples、limits`。前端依照参数 Schema 生成输入控件，后端依照同一注册表进行校验和调用。

规则计划固定函数库版本；同名函数改变语义必须升版本。预览通过但目标节点缺少对应函数时禁止部署。函数实现必须无共享可变记录状态；可复用不可变日期格式器、模式对象与编译 AST。

正则长度上限建议 512 字符、输入按字段预算限制，并采用具有可控最坏复杂度的正则子集/实现；不能以 Java 线程超时取消包装就宣称消除了灾难回溯。首期不支持的反向引用或复杂回溯语法明确拒绝并提示改写。

### 8.3 自定义函数

保留现有受限函数模板的导入思路，但“自定义”指白名单函数的组合和参数化表达式，不指上传可执行脚本。当前后端模板有数量、长度、value/arg 引用限制，新协议继续保存并明确升级上限。

模板定义包含版本、参数类型、返回类型、表达式 AST、样例和使用引用；编译时展开并检测递归/循环、深度和节点总量。更改模板不修改已发布计划；使用方显式选择新版本并预览差异后重新部署。字典调用在模板展开后提取为统一 lookup 阶段，不能藏在函数 helper 内逐记录请求。

## 9. 编辑模型、执行模型与示例

### 9.1 协议版本原则

旧 `FieldMappingSpec.version=1.0` 按原结构读取，保留 `mappings` 数组和一对多顺序。它通过兼容适配器转换为内部规范模型；不把包含通用步骤链的新配置伪装成旧 1.0 让旧客户端静默忽略。

新增编辑协议建议 `schemaVersion=2.0`，后端先同时支持读取 1.0/2.0，前端能力协商后才写 2.0；旧客户端遇 2.0 只读显示兼容提示。画布总体 DSL 版本与字段映射子协议版本分别管理。新版内容不向旧格式有损回写；旧映射表以带版本的完整投影或摘要承接。

### 9.4 执行计划与摘要

ExecutionPlan 不存浏览器坐标、展开状态和 UI 控件字段；也不覆盖原草稿。编译时批量绑定已授权资源，嵌入不可变的结构化定义或可验证引用，给出依赖顺序和输出 Schema。

计划摘要由规范化后的规则顺序、类型、函数版本、字典定义版本、固定快照、能力要求和预算计算。对象键稳定排序，数组保留业务顺序，数值用规范十进制表示；生成时间、随机 planId 不进入内容摘要。`planHash` 用于一致性和并发比较，不替代授权或签名。

预览可以生成只读候选计划；发布使用后端重新验证并保存的不可变计划，不能信任浏览器上传的编译结果。相同草稿、Schema、资源版本和引擎版本产生相同语义计划；LIVE_BATCH 的字典行值变化不改变定义摘要，也不承诺结果不变。

## 10. 编译与执行算法

### 10.1 编译流程

1. 校验协议、大小、规则数量及未知执行算子/参数，保留不参与执行的命名空间扩展元数据；旧规则经兼容适配，不落库修改。
2. 从认证上下文解析租户及数据范围；收集来源/目标/字典/标准/函数模板引用，在集合外批量读取，逐 ID 检查。
3. 解析逻辑 Schema、明确原生类型和字段身份，验证目标存在、精度、非空及输出冲突。
4. 解析表达式与条件 AST，绑定函数签名和版本，迁移别名；不能识别的表达式返回具体规则问题。
5. 为 TARGET 引用构建依赖图，检测重复目标、自引用、循环和禁用依赖；生成稳定拓扑顺序。
6. 把 lookup 函数提升为字典依赖阶段，合并同定义、同作用域、同快照、兼容投影的需求。
7. 静态计算阶段深度、外部资源数量和最坏预算，生成输出 Schema、计划和摘要。
8. 返回完整诊断和可执行状态；发布另校验真实目标节点的 Bundle/服务/引擎能力。

### 10.2 窗口执行

```text
读取已验证不可变计划，固定 FlowFile 执行上下文和快照版本集
打开一个 RecordReader，建立 success/invalid 的受控 Writer
while 输入仍有记录:
    读取一个同时受记录数、字节数约束的窗口
    保留不可变原输入，建立各记录独立的目标上下文
    for stage in 有界依赖阶段:
        执行本阶段纯计算和条件，收集全部需要的 LookupDemand
        按定义/版本/作用域合并键与投影，按参数预算构成批次
        DictionaryProvider.fetchBatch(...) 统一读取
        在内存回填，继续纯规则与验证
    将该窗口结果流式写入本 Session 的输出内容，不提前提交
完成所有窗口，关闭 Reader/Writer
依据记录策略一次转移 success/invalid 并结束 Session
如后续窗口发生整批错误，按第 15 章处理所有派生输出和原输入
```

来源引用始终读原输入，目标引用读依赖规则的最终结果，步骤输入读上一步结果。不能通过覆盖原输入来偶然决定后续取值。条件短路只收集已选分支字典；若条件自身依赖字典结果，进入下一个阶段，不能在记录循环中临时补查。

“格式化 A → 查字典 A → 用结果查字典 B”至少有两轮 lookup 阶段；一个 Processor 不等于一个 SQL。纯计算和 lookup 都应使用稳定排序，使错误定位、预览轨迹和结果可解释。

### 10.3 输出 Schema 与漂移

编译后的 Schema 是唯一输出字段集合和顺序来源。明确输出覆盖同身份直通字段；`exclude` 在编译投影时执行。目标冲突按规则 ID 定位，不允许多个赋值靠顺序最后覆盖。

运行校验 Reader 实际 Schema 与计划指纹。可配置允许无关新增字段；除计划已明确允许 `sourceOptional=true` 的字段缺省外，已引用字段缺失、类型改变、重复名称或目标 Schema 变化必须按漂移策略拒绝/隔离。允许缺省的字段按7.2节记录缺值策略处理，不能动态扩大权限或自动重建目标表。写出用显式逻辑类型；Avro 等格式的名称约束、nullable union、decimal precision/scale、timestamp logical type 必须在 Writer 适配验证中落实，不靠样本推断。

## 11. 字典服务、批量查询与资源预算

### 11.1 Controller Service 契约

拟定服务接口名为 `HaitongDictionaryService`，以批量调用作为唯一取值入口。规则引擎不能获得可触发远程读取的 `Map.get(key)` 懒加载对象。

```java
// 设计接口示意；不是已存在的 Java 类。
interface DictionaryBatchProvider {
    BatchLookupResult fetchBatch(
        AuthorizedDictionaryBinding binding,
        Set<TypedCompositeKey> keys,
        Set<ValueColumnRef> projection,
        LookupBudget budget);
}
```

binding 由发布/预览资源解析器创建，包含授权作用域、真实已登记数据源别名、字典定义和版本；前端与 FlowFile attributes 不能自行构造可用 binding。返回值分别标明命中、未命中和故障，附读取版本/一致性说明及计数，不返回连接凭据。

数据库读取使用参数化 SELECT/IN 或复合键条件，标识符来自已授权元数据，不能用用户输入拼表名/列名。静态条件及记录相关条件以 AST 表达；记录相关条件值并入类型化复合键，禁止按每个记录的过滤值建立一个临时查询组。

支持比较、IN/NOT IN、IS NULL/IS NOT NULL 和受限 LIKE；LIKE 必须显式转义通配符语义，复用登记预览和运行同一编译器。现有任务生成不认识的条件可能被跳过，这是必须修复的差距：新编译器无法支持时返回错误，绝不丢条件后扩大查询范围。复杂 customSql 进入迁移分类，不强行正则改写。

记录相关条件必须保留“请求键标识—过滤参数—返回行”的对应关系，按完整类型化请求键归集，不能只按code回填。可使用经目标方言验证的请求表/CTE/UNION ALL等有界批量关系；相同code携带不同范围或LIKE条件时不得串用结果。不能证明对应关系的条件组合在编译时拒绝，不退回逐请求查询。

### 11.2 分组与复杂度

分组身份至少为：授权作用域、真实数据源、schema/table、定义版本、静态谓词、键类型与复合键结构、快照/新鲜度模式。相同定义可合并值列投影；不同表和不同过滤条件不能仅因连接相同就当成一个字典。

```text
单窗口业务查询数 Q = Σ(依赖阶段 s，字典定义组 g) ceil(Ksg / Bsg)
Ksg = 该阶段该组的去重类型化查询键数；0 个键不查询。
Bsg = min(配置键批次上限,
          floor((驱动参数上限 - 固定过滤参数量) / 单键绑定参数量),
          SQL长度/请求字节预算允许的容量)
```

当某方言无法表达需要的复合条件时，只能使用已验证的批量提供者或明确拒绝；不能退回逐 key 查询。跨连接的字典分组有界，每组查询有超时和结果上限，连接复用但不跨线程共享 Statement/ResultSet。

若计算得到 `Bsg < 1`，直接报告参数预算不足，禁止除零或退回单键请求。超批次是有界集合分片读取，不是给每条业务记录重新构造查询。

| 同一窗口条件（关闭缓存） | 20 条记录或 20 个字段 | 100 条记录或 100 个字段 | 合规说明 |
| --- | --- | --- | --- |
| 纯函数/静态枚举 | 0 次字典业务 SQL | 0 次 | 无外部逐项读取 |
| 共用一个字典，合计唯一键≤500且参数预算允许 | 1 次 | 1 次 | 跨字段合并，不能只在每字段内批量 |
| 共用两个字典，各自≤500键 | 2 次 | 2 次 | 按定义而非行数增长 |
| 一个字典有600键、每批500 | 2 次 | 2 次 | 按有界批次增长 |
| 两层依赖，各一个字典且键均一批内 | 2 次 | 2 次 | 不能把依赖查询偷放进逐行 helper |
| 100 个字段访问100份不同字典 | 受资源数预算限制 | 不能声称固定为1次 | 超限提示拆分设计，不能无界展开 |

元数据初始化和授权查询单独计数，按配置版本/资源组有界读取，不能每字段或每 FlowFile 重查类型。现有多值脚本测试包含一次元数据查询，20/100 条样本总 prepareStatement 为2；新验收报告必须分别列元数据 SQL 和业务 SQL，不能通过漏计证明“1次”。

### 11.3 一致性、重复键与缓存

| 模式 | 含义 | 迁移原则 |
| --- | --- | --- |
| STATIC_MAPPING | 登记确认的内嵌编码/标准快照 | 固定版本，运行零字典业务 SQL |
| LIVE_BATCH | 每窗口按批次读取当时字典值，无值缓存 | 真实数据库字典迁移默认；多窗口可能看见不同时间的值 |
| VERSIONED_SNAPSHOT | 完整构建、不可变、可按版本取回的字典快照 | 显式选用；FlowFile 固定版本集 |
| TTL_BATCH_CACHE | 带过期和容量的正/负缓存，未命中仍批取 | 显式允许陈旧时间；不能称为固定快照 |

快照同时受行数、字节和构建时间限制，完整成功后原子切换。超限或构建失败不能发布截断快照；按预先配置拒绝或改为 LIVE_BATCH，不能运行中悄悄改变一致性。LIVE_BATCH 和 TTL 缓存不能承诺重放得到旧值；同一 FlowFile 只有定义版本固定，不代表外部数据固定。

缓存 key 包含授权作用域、数据源、定义/过滤条件、键类型、投影和版本；字符 `01` 与数字 1 不可碰撞。撤销授权或定义失效时禁用相关 binding 并清理可见缓存，不因命中缓存绕过资源校验。

重复键新规则默认 ERROR。可明确使用按登记唯一排序列选 FIRST/LAST，但必须有稳定次序；旧多值脚本的“字典序最大 label”可迁移为独立 `LEGACY_MAX_LABEL`，固定比较器并显示兼容提示，不伪装成新默认。不能用 SQL 未排序的首条制造不确定结果。

### 11.4 初始预算建议

以下数值是起步设计值，须在同机压测后固化到版本化配置；用户扩大预算仍受服务端硬上限约束。

| 资源 | 建议默认 | 达限处理 |
| --- | --- | --- |
| 一个记录窗口 | 512 条或8 MiB，先到为止 | 结束当前窗口再读下一窗 |
| 单记录/单字段 | 1 MiB / 256 KiB | 数据错误隔离或整批失败；LOB 任务另定义流式支持 |
| 一个字典键批次 | 最多500键 | 按复合键/驱动参数上限缩小 |
| 一个节点规则数/步骤数 | 规则1,000；每规则32步 | 编译拒绝超限 |
| 依赖阶段/AST深度 | 16 / 32 | 编译拒绝循环或过深 |
| 字典定义/数据源数 | 32 / 8 | 提示拆分业务或经容量评估调整 |
| 每字段token / 每窗token总量 | 1,000 / 100,000 | 明确数据错误，不截断结果 |
| 每窗去重键总量 | 20,000 | 分窗或拒绝单条超预算 |
| 一批查询结果 | 100,000行或16 MiB | 故障并保留原输入，不把截断结果当未命中 |
| 每窗口字典结果累计 | 32 MiB | 所有批次/字典累计计量，超限失败而不截断；及时释放不再使用的阶段结果 |
| 每节点字典并发/查询超时 | 2 / 10秒 | 受连接池和全局并发限制，超时按故障处理 |
| 服务缓存 | 64 MiB、条目和TTL双限 | LRU等明确淘汰，未命中依然批取 |
| 计划JSON | 2 MiB | 超限使用受控不可变包引用或拒绝，不能无界塞属性 |
| Processor运行内存预算 | 建议128 MiB（缓存另计） | 调度并发×窗口/结果/Writer总额在触发前预留；不足则背压/限并发，不无限排队 |

内存预算需要覆盖 `并发任务数 ×（窗口 + 字典结果 + 工作上下文 + Writer缓冲）+ 共享缓存`，不能仅证明窗口512条就宣称全进程有界。输入解析器也需限制单记录构造、JSON深度/字符串、Avro块等分配；若 Reader 在计数前已整体加载大记录，必须在适配层限制或拒绝该Reader组合。

大 FlowFile 内容流式写 NiFi Content Repository，不在 Java 列表中累积全部成功/错误记录。禁止逐窗口提交来规避内存，Session 原子性按15章执行。缓存、计划和格式器生命周期按节点配置版本管理，失效释放资源，防止热更新不断保留旧对象。

## 12. NiFi 自定义组件详细设计

### 12.1 处理器与服务

正式设计名为 `HaitongTransformRecord`，替代适合迁移的 `transform.field-mapping` 和 `transform.field-enrichment` 的内部运行实现。海通业务节点类型和连线操作保留。截图里的旧 `AlignmentProcessor` 类名和1.15.0版本不直接复用，避免误判兼容。

一个主要 Processor 负责一个 Record 读写边界；Reader、Writer、字典服务、DBCP服务属于 Controller Service，不按字段生成。输入可采用当前已验证的 JSON/Avro 格式；其他 Record 格式逐项注册适配能力。

### 12.2 处理器属性

| 属性/API名建议 | 必填/默认 | 说明与校验 |
| --- | --- | --- |
| Record Reader / `record-reader` | 必填 | RecordReaderFactory 引用，验证输入类型能力 |
| Record Writer / `record-writer` | 必填 | RecordSetWriterFactory，输出 Schema 必须与计划一致 |
| Invalid Record Writer / `invalid-writer` | 隔离模式必填 | 独立错误信封 Schema，不能强行套成功 Schema |
| Execution Plan / `execution-plan` | 与plan-ref二选一 | 小型不可变JSON，发布层填入；不启用用户值表达式语言 |
| Plan Reference / `plan-ref` | 与内嵌计划二选一 | 受控存储引用+摘要；调度前加载，不允许任意URL/文件路径 |
| Plan Hash / `plan-hash` | 必填 | 比较载入计划，配置不一致拒绝运行 |
| Dictionary Service / `dictionary-service` | 有外部字典时必填 | 批量服务引用；静态映射可不绑定 |
| Authorized Binding / `binding-ref` | 引用外部资源时必填 | 发布服务生成的资源作用域标识，业务用户只读 |
| Record Error Mode / `record-error-mode` | FAIL_FLOWFILE | 必须与计划一致；改变策略需重新编译生成新planHash并以新计划预览 |
| Window Records / Bytes | 512 / 8 MiB | 取属性值与计划预算较小者 |
| Lookup Batch Keys / Timeout | 500 / 10秒 | 按驱动和服务硬上限收敛 |
| Max Retry Attempts / Backoff | 建议5次/指数退避 | 与外部重试设施一致，不能只配置无执行保障 |
| Sensitive Preview | 默认关闭 | 普通NiFi属性和bulletin只显示脱敏摘要 |

时区、Locale、函数版本、字段规则和字典新鲜度由计划固定，不能又在属性中产生另一套冲突配置。传统“转换前/后处理”改成计划中的输入标准化、字段步骤及输出验证，不提供任意脚本属性。“数据库配置服务”承接为登记连接别名到受控连接池的解析，规则计划不保存用户名、密码或 JDBC 凭据串。

### 12.3 关系、属性和生命周期

| 关系 | 内容 | 接线要求 |
| --- | --- | --- |
| success | 通过规则与目标验证的记录 | 接现有目标写入 |
| invalid | 逐记录隔离信封 | 隔离模式启用时必接受控队列，禁止自动终止 |
| failure | 非重试/重试耗尽的原始FlowFile及受控错误摘要 | 必接故障保留或人工处理，禁止自动终止 |
| retry | 可重试基础设施故障的原始FlowFile | 必接限次退避设施，禁止无限自环 |

允许 invalid 未启用时不创建该类输出，但只要可能产生错误数据就必须有处理去向。failure/retry 的编译接线由发布器托管，不能让用户漏接时自动删除数据。

成功输出属性建议含 `ht.plan.hash、ht.engine.version、ht.dictionary.versionSet、ht.input.count、ht.success.count、ht.invalid.count、ht.execution.id、record.count`。错误属性只存有限的 code/ruleId/stepId/retryAttempt，不存身份证、原记录、SQL参数或凭据。计划及其资源绑定也需受NiFi权限保护。

调度前完成计划解析、服务能力和Schema检查；每次触发固定上下文并读写FlowFile；停止时取消未完成查询并释放连接。一个Processor实例可被并发调度，配置和编译计划不可变，每次触发上下文、Reader/Writer独立；工作线程不得共享 ProcessSession。Service 更新只能以新版本原子切换，不修改正执行计划。

### 12.4 工程与打包

建议在 Java 后端维护范围下建立独立构建模块：`mapping-model`、`mapping-core`、`mapping-runtime`（窗口与Provider接口）、`mapping-jdbc-provider`、`nifi-mapping-service-api`、`nifi-mapping-service`、`nifi-mapping-processors` 及对应NAR。名称为拟定，不表示已存在。

纯内核JAR同时供后端预览和NAR使用，避免打入整个Spring Boot应用。NiFi自带API使用合适的provided依赖；Controller Service接口放共享API NAR，Processor和服务实现引用同一接口类。NAR父子依赖按NiFi类加载限制设计单一路径，共享API NAR再依赖所需标准服务API，不能随意列多个父NAR或复制接口类。[NiFi扩展与类加载说明](https://nifi.apache.org/nifi-docs/developer-guide.html)

当前仓库测试依赖NiFi 2.9.0，pom有Java21声明及历史编译属性，扩展工程必须独立明确toolchain/release并验证。旧方案提到演示环境2.11.0，属于历史记录，本次未复核；截图1.15.0也不能决定新基线。正式实现前读取目标NiFi/Java/Bundle和集群节点能力，形成明确支持矩阵，不因公开文档更新直接升级运行环境。

## 13. 后端接口详细设计

### 13.1 保留的现有接口

现有前缀为 `POST /nifi/api/field-mapping`。保留路径与兼容响应，增加新协议字段需先升级DTO和前端类型，不能假设原接口已支持以下新执行语义。

| 路径 | 当前请求/响应 | 升级内容 |
| --- | --- | --- |
| `/migrate-legacy` | spec或原对象 → 规范化1.0配置 | 支持dryRun迁移报告、兼容策略、不可自动迁移原因 |
| `/validate` | spec/sourceSchema/targetSchema → valid/errors/warnings/schemaCompare | 后端当前已消费传入Schema，前端需补传；新版本再从权威资源绑定校验，返回ruleId/stepId与版本/预算问题 |
| `/preview` | spec/sourceConfig/sampleRows等 → resultRows/rowResults/stats | 统一计划/内核、批量查字典、样本上限、版本与步骤轨迹 |
| `/recommend` | 来源/目标Schema → spec/recommendations | 不覆盖人工规则，给候选依据/置信度，消费明确options |
| `/compile` | spec等 → mode/query/finalQuery/lookups/nifiComponentConfig | 当前未按请求Schema编译校验，需补齐；增加ENGINE_PLAN模式和plan摘要，不把JSON填进query伪装SQL |
| `/lookup-template` | datasourceId/tableId/keyColumn/valueColumn → SQL模板 | 新规则返回结构化字典草稿；旧SQL响应仅供兼容，按资源校验 |

新版compile保留旧字段但在新模式下 `query/finalQuery` 可为空；前端按 `mode` 展示。当前Java `Map.of`不能容纳null，新实现需相应修改响应DTO/序列化，不直接在原Map中塞null。预览保留旧三项主字段并扩充计数含义，不让失败占位行混入成功数。

### 13.2 建议新增接口

以下路径均为拟定，正式实施先核对现有路由并统一命名；不得在文档交付时假称可调用。

| 建议接口 | 方法与请求重点 | 输出/约束 |
| --- | --- | --- |
| `/nifi/api/field-mapping/capabilities` | GET，可选已授权nodeId | 规则/函数参数Schema、版本、后端能力；节点在线能力发布时再核验 |
| `/nifi/api/field-mapping/context` | POST taskId/pipelineId/nodeId | 一次批量返回来源/目标Schema、治理绑定、版本和首跳属性 |
| `/nifi/api/field-mapping/dictionaries/page` | POST pageNo/pageSize/keyword/sortField/sortDir | 当前作用域可见字典分页目录，无连接凭据 |
| `/nifi/api/field-mapping/dictionaries/resolve-batch` | POST definitionIds，最多100 | 定义摘要、字段/类型/版本；整批逐ID校验 |
| `/nifi/api/field-mapping/sample` | POST taskRef、limit≤100 | 一次授权来源采样；不接受任意URL/SQL/凭据 |
| `/nifi/api/field-mapping/draft/save` | POST taskRef、expectedRevision、mappingDraft | 与画布保存共用同一事务服务，返回新revision；不是另一套权威存储 |

字典定义选择、采样、批量解析都是操作授权的一部分，不能让客户端传tenantId决定数据范围。`sourceConfig`仅作为非敏感编辑提示；数据读取从已登记资源定位，不接受旧兼容Map中的jdbcUrl/username/password作为运行依据。

### 13.4 并发和批量契约

保存请求带expectedRevision；冲突返回409及受控差异，不自动覆盖他人修改。重试保存带幂等键，相同键和相同内容返回同结果，内容不同拒绝。部署任务固定draftRevision和planHash，草稿后来编辑不影响正在执行的旧计划。

元数据/权限预取必须在规则遍历外完成。20/100字段加载同一页面时，context一次、能力目录一次、字典目录按需一次，已选字典定义最多一次批量解析；重复行不增加网络请求。分页默认20、上限100；现有物化目标上限20和任务补齐目标上限100继续按各自接口约束执行，不能借新批量接口扩大目标范围。

## 14. 配置存储、版本与权威来源

### 14.1 现有存储事实

| 对象 | 当前位置及实际字段 | 升级处理 |
| --- | --- | --- |
| 来源治理 | `db_table_t.field_governance_config`、字段data_standard_id等 | 保留来源定义；旧动态属性只作明确兼容读取 |
| 目标输出绑定 | 目标表field_governance_config.fieldTransformBindings | 保留bindingId和来源/目标字段ID，不凭_cn命名恢复 |
| 任务字段映射 | `data_access_field_mapping` | 已有source/target字段名、类型、长度、dict_enable/value/code、func_enable/value/code、sort_no、tenant_id、revision |
| 画布草稿 | `nifi_pipeline_t.dsl_json` | 当前任务/节点编辑的规范规则权威载体 |
| 编译指纹 | 现有DslHasher和字段映射编译版本 | 扩入计划、Schema、引擎、函数及字典快照指纹 |

`func_value`在当前完整结构中已为MySQL TEXT、达梦CLOB，不能把升级默认写成“先从VARCHAR扩容”。但已有文本容量不等于完整模型、版本和双向同步已经实现。

当前画布保存主要写DSL，旧Magic保存主要写映射表，Binder可能再从映射记录补充规则；存在两个入口覆盖不同信息的风险。新设计统一为“规范草稿权威 + 接入映射投影 + 不可变发布计划”，不另建第二套平行规则主表。

### 14.2 保存事务

1. 锁定/乐观检查当前租户task、pipeline与node版本，确认它们关联一致。
2. 批量校验规则中的字段、目标、字典和绑定，生成规范草稿及投影。
3. 在同一租户数据库事务中更新DSL及本任务映射投影、必要版本字段；投影写入按现有持久化框架批量完成。
4. 更新revision并提交。失败则全部回滚，不能出现画布显示新规则而Binder恢复旧规则。
5. 保存不调用NiFi、不修改登记主档、不推进来源水位。发布使用独立状态机。

映射投影只能重建可表达的摘要和完整版本引用。复杂步骤链不得压成中文说明丢失参数，也不能在新计划缺失时从不足的摘要猜出执行规则。旧编辑入口未升级前，对新版本规则只读并指向统一编辑器；避免回写丢失。

第一期选用现有 `func_value` 大文本列保存版本化投影JSON，至少含 `projectionVersion、pipelineId、nodeId、ruleId、draftRevision、ruleSnapshot`，其余dict/func关系列只作旧列表摘要。现有表没有node_id，投影写入必须一次读取本task全部投影，在内存按完整身份匹配，禁止仅按target_field覆盖。v2 Binder只读取规范草稿的执行规则，不再向v2节点注入task级旧摘要；旧恢复器仅处理v1。若未来要在数据库按nodeId/ruleId检索或建立唯一约束，再统一四行业DDL扩列，不能某一租户先行形成不同结构。

### 14.3 发布计划持久化建议

建议新增一个租户业务表 `data_access_mapping_plan_t` 保存不可变的计划版本，复用现有流程/部署状态记录关联activePlanId。若实施确认已有通用不可变部署产物表能够完整承载，则复用该表；只能选择一个权威载体，不同时建两套。以下为默认逻辑设计，实际DDL须按现行库结构评审后生成。

| 建议列 | 逻辑类型 | 中文含义/约束 |
| --- | --- | --- |
| tid | 稳定ID字符串 | 数据接入-字段映射执行计划标识，主键 |
| tenant_id | 租户ID | 非空，当前业务租户，不能由客户端赋值 |
| task_id / pipeline_id / node_id | 关联ID | 所属任务、画布和节点，逐ID关联校验 |
| plan_revision / draft_revision | 长整数 | 节点计划版本、编译来源草稿版本 |
| plan_hash | 摘要字符串 | 规范执行计划摘要，无凭据 |
| plan_version / engine_version / function_version | 版本字符串 | 协议及实现兼容校验 |
| source_schema_hash / target_schema_hash | 摘要字符串 | 输入和输出Schema指纹 |
| plan_content | 大文本 | 完整不可变计划JSON，无秘密连接信息 |
| resource_version_set | 大文本 | 字典/标准/Schema定义引用与版本，不存整份业务字典内容 |
| created_by / created_time | 审计字段 | 编译操作者及保存时间 |

建议唯一约束 `(tenant_id,pipeline_id,node_id,plan_revision)`；以 `(tenant_id,pipeline_id,node_id,created_time)` 查询版本历史。真实ID长度、时间类型、索引长度、外键和软删约定必须与现有基础实体一致，不能直接照此逻辑表拼DDL执行。计划不可变，启用/回退状态存于部署记录，不能原地修改计划内容。

新增表属于行业公共结构，必须同步公安`baseline_ga`、澄天、海渔、广电全部实际行业库的完整DDL，按MySQL/达梦原生方言实现中文表列注释、主键和索引；控制库不承载行业任务计划。结构实施后执行`tools/check-db.py`和`tools/export-db.py`并审阅全量差异。本次只写设计，不执行结构变更。

### 14.4 生命周期和保留

运行任务、待重试FlowFile、错误队列和回退部署引用的计划及快照禁止清理。版本保留依据引用与明确保留期，清理先做只读候选报告并逐ID授权；不按“旧于某天”直接删除仍引用版本。用户可在界面比较草稿/运行版本，已保存未部署须明确显示，不能以源码一致代表运行生效。

## 15. 错误处理、事务、重试与监控

### 15.1 分层错误

| 错误层 | 例子 | 处理方式 |
| --- | --- | --- |
| 设计/编译错误 | 未知函数、缺字段、重复目标、依赖环、无权字典 | 定位字段/步骤，禁止发布；允许继续查看/编辑草稿 |
| 数据错误 | 日期非法、码表未命中且策略ERROR、数值溢出 | 按字段回退和记录模式执行，不能标成连接故障 |
| 资源/环境错误 | 快照不存在、服务未启用、权限撤销、Bundle不兼容 | 停止执行并保留原输入，不按未命中回退 |
| 瞬时基础设施错误 | 连接超时、短暂不可达 | 符合分类才有限重试；持续失败进入failure |
| 内容/序列化错误 | Reader无法解析、Writer失败 | 撤销派生输出，保留原输入；是否可重试需分类 |

### 15.2 Session提交边界

FAIL_FLOWFILE模式：任何记录发生不能回退的数据错误，本次所有派生输出都不可发布；移除本Session中已写出的success/invalid候选，保留原输入并转failure。ROUTE_INVALID模式：错误记录写invalid，正常记录写success，全部窗口结束后在同一Session完成转移和提交，原输入只在最终成功路径移除。

后窗失败不能已有前窗success提交。Session可向内容仓库流式写数据，但提交边界仍覆盖整次输入；这与把全部记录保存在内存中不同。NiFi ProcessSession具有提交/回滚事务语义，实际实现须用匹配目标版本的API验证。[NiFi Session说明](https://nifi.apache.org/nifi-docs/developer-guide.html#session-rollback)

### 15.3 重试协议

对可控瞬时故障，处理器停止处理、关闭资源、删除本Session派生输出，在原FlowFile保留原内容并写入 `retryAttempt/nextAttemptAt/errorCode`，提交到retry关系。重试设施按指数退避加抖动调度，建议最多5次、最大退避5分钟，达到次数/总耗时上限进入failure，不能在failure/retry上建立无限自环。

崩溃或无法安全整理Session时调用/交由框架rollback，原输入返回队列；本轮属性变化会一起回滚。因此不得声称“回滚同时保存本轮retryAttempt”。这类异常还需发布器提供的持久重试/熔断设施：按稳定输入执行标识记录崩溃循环，达到门槛暂停节点并告警，保留队列供处理；该设施必须在升级验收中实现，不能仅写一个重试属性就宣布完成。

禁止新旧计划混合重放。retry/failure输入带计划引用，重试固定原计划及快照；切换运行计划前排空或转入绑定旧版本的保留流程。缺少旧计划/快照时拒绝重放，用户显式选择新版本重新处理才生成新的执行记录。

### 15.4 系统字段与幂等

当前不同UI/helper存在“秒+随机”和“毫秒+随机”生成ODS_UUID的模板，升级须统一生成器契约，并在兼容迁移中保留旧任务语义。新建建议使用受支持的标准UUID字符串，先确认目标字段长度；不能无提示改变既有目标列或宣称随机算法绝不碰撞。

首跳生成值固化在成功输出内容中，下游重试读取相同内容，不能再次生成。输入在映射前已具有稳定业务键/记录事件标识时可显式采用命名空间确定性ID；缺少稳定身份时不能承诺源端重新采集仍得到相同ID。Processor回滚后重新计算随机值的情况需单独测试；若要求相同值，必须在进入映射前固化执行上下文或采用稳定输入身份派生。

ODS_RKSJ/ODS_GXSJ从固定上下文产生，后续跳透传。目标UPSERT时RKSJ是否保留、GXSJ何时更新由sink契约明确并验收，不由字段映射模块凭字段名决定。NiFi Session原子性不等于来源水位与目标数据库的分布式事务；继续沿用现有水位/目标幂等协议，不能承诺本组件实现端到端exactly-once。

### 15.5 错误记录与指标

invalid信封建议包含：executionId、planHash、inputRecordIndex、errorCode、ruleId、stepId、sourceFieldRef、targetFieldRef、发生阶段及有限脱敏摘要。完整原记录只进入授权受控内容队列，普通日志和属性不得保存。每条错误最多20项、每项摘要最大512字符，防止错误本身导致内存/日志爆炸。

指标至少包括：输入/成功/隔离记录数、NULL/缺失/未命中数、规则错误码分布、窗口数、字典组/键/查询批次数、查询结果字节、阶段耗时、P95延迟、重试次数、连接耗时和计划版本。普通指标按任务/节点/错误码等有限维度聚合，禁止把每个记录ID/字典key当标签造成高基数。

监控页面继续使用任务有效运行状态，不把最近一次执行SUCCESS当成停止。查看失败样本通过单项授权详情接口，列表一次返回计数和状态，不能逐错误行补查NiFi或数据库。

## 16. 租户、权限与敏感信息边界

1. Java预览/保存/编译由当前认证TenantContext和数据范围定位行业库；Magic从`tenantRuntime.id()`一次解析租户。浏览器tenantId、旧记录租户、FlowFile自带tenant字段都不能决定资源归属。
2. 批量ID先去重和限量，按当前租户读取，再逐ID验证任务、表、字段、字典、数据源及关联。混入越权/缺失对象整批失败，不能丢掉异常ID后静默成功。
3. 标准枚举与物理字典分别解析。静态标准不访问同名物理表；真实字典必须保留有效表/数据源、角色数据范围和已登记关联的检查。
4. NiFi没有交互式用户会话，执行使用发布时经授权绑定的任务资源作用域。服务端托管binding和定义版本，按配置边界/撤销事件检查，禁止逐记录远程租户校验；到期/撤销后的行为为停用与保留输入。
5. 当前普通授权用户模型保留，不新增platformAdmin/tenantAdmin门槛。资源授权和正常业务权限必须继续逐ID落实。
6. 缓存、快照、计划和错误队列按授权作用域隔离；共用Controller Service不表示业务数据共享。一个普通计划只属于一个行业租户，不能以跨库字典之名跨租户取数。
7. 计划、模板、接口和日志无明文密码、token、私钥或可推测口令摘要；连接只从受限运行配置解析，原生NiFi属性按平台权限管理。
8. 表名、列名只能由登记元数据绑定；值使用参数化查询，条件AST使用白名单。执行计划摘要不是访问凭证，计划内容被篡改后必须重新授权编译。

权限验收同时覆盖当前租户两类角色、不同真实租户、同ID/同名字典、撤销权限后缓存命中、混合有权无权100个ID，以及固定字典条件是否被完整执行。资源检查不能因批量而扩大范围，也不能新增循环内授权SQL。

## 17. 兼容迁移、发布与回退

### 17.1 迁移分级

| 类别 | 条件 | 处理 |
| --- | --- | --- |
| A 可自动转换 | 直接、类型化常量、可证明等价函数、完整结构化字典、静态映射、明确日期格式 | 生成新草稿/计划、逐项对比，仍需用户显式部署才生效 |
| B 需确认语义 | 缺省fallback、NULL拼接、精度、世纪、模糊日期、重复键、已有SKIP_ROW、输出冲突 | 展示旧结果与新规则策略，确认后保存 |
| C 保留旧执行器 | 复杂手写SQL、无法证明等价脚本、缺资源关联、未知函数、SOURCE_DB特殊任务 | 保留原DSL和执行策略，列出迁移原因；不静默删规则 |

新普通任务在目标节点具备能力且验收通过后默认用统一Record引擎。存量SOURCE_DB任务保留原策略；仅field-enrichment在当前支持条件下使用来源下推，不能借新引擎修改筛选、分页、增量列或来源水位。后续如增加下推优化，必须证明与统一计划等价并仍按同一测试向量验收。

### 17.2 能力握手

部署前一次有界读取目标节点/集群能力，检查完整Processor类名、bundle group/artifact/version、Controller Service接口与实现、planVersion、engineVersion、functionLibraryVersion和Reader/Writer兼容矩阵。不能继续仅按simple class name匹配首个类型。

### 17.3 发布状态机（需要新增实现）

```text
DRAFT → VALIDATED → PLAN_FROZEN → NEW_GRAPH_PREPARED
      → OLD_SOURCE_STOPPED → QUEUES_SAFE → STATE_CAPTURED
      → SWITCHED → OBSERVING → ACTIVE
任一切换前失败：清理未启用的新图，保留旧图和状态
切换后失败：先停止新来源，按状态与写入边界决定恢复旧图或进入人工恢复
```

当前实现已有非空队列检查，但会清理旧组后编译新组，没有完整状态迁移保障；以下均为升级交付项：

1. 固定草稿/计划及资源版本，保存旧DSL、旧Bundle、连接/服务绑定、部署指纹和运行状态。
2. 创建停止状态的新图，不启动新来源；验证所有服务和属性，避免旧图已删除才发现编译失败。
3. 停止旧来源采集，等待活动线程结束；对success、failure、retry及invalid队列全部核查。非空则排空或保留旧组待处理，不能直接清队列。
4. 捕获来源处理器适配所需的本地/集群state和水位，确认新旧处理器身份映射及恢复协议。无法可靠导出/恢复的来源先禁止自动切换，不能按“队列为空”推断水位已安全。
5. 切换前复核版本无并发修改，把状态导入经验证的新来源；保证同一任务只有一个活动采集者。
6. 切换并观察首批输出、错误队列、SQL次数、延迟和目标幂等。activePlanRef更新与状态记录一致。
7. 旧图在观察完成及所有队列/回退引用解除前保留，不自动删除。删除旧资源仍是明确维护动作。

若新图已经写入目标库，回退不能只恢复旧水位再重跑；需按目标幂等键或明确补偿方案评估重复写入。不能安全恢复时进入RECOVERY_REQUIRED，停止新采集并保留输入、输出、状态和版本供人工处理，不伪报回退成功。

### 17.4 发布流程与仓库约束

实际开发先改本地唯一源：Magic在根magic、共享低代码在根lowcode、Java和静态前端在所属工程。发布前用resource-sync进行目标资源比较与计划，只选本任务文件；发现远端并发修改先解决差异，不全量覆盖。

### 19.2 批量与权限的两项强制证据

证据一：分别准备20/100规则字段、20/100记录样本和20/100引用ID。记录浏览器请求数、授权/元数据SQL、字典业务SQL、连接次数、FlowFile数和实际执行计划。冷缓存、暖缓存、关闭缓存各执行一轮。同一字典一批内，字段数/记录数增加不增加查询；跨批按11.2公式增长。保留SQL计数器/驱动代理证据，不能仅搜索代码或依赖缓存命中率。

证据二：相同数据集混入其他租户、同租户无角色权限、删除/不存在字典、无权目标和不属于来源的字段ID。证明每个ID被校验，整批拒绝且无写入；缓存命中和模板导入也不能绕过。真实会话确认`/sym/tenant/current`，至少两个行业租户验证读写隔离。

不把“100个不同字典”与“100行同一字典”混为一项性能证明。资源组增加的固有成本单独报告，并展示节点预算如何拒绝无界计划。

### 19.3 预览/运行一致性

使用同一计划、相同Reader逻辑Schema、相同样本、同一快照版本、固定时钟和ID生成上下文，比较预览与NiFi：值、逻辑类型、输出顺序、NULL/缺失、错误code、ruleId、invalid数量全部一致。JSON文本键顺序或时间序列化格式差异按明确Writer契约比较，不能只肉眼比较字符串。

LIVE_BATCH在两次执行间被外部修改时不能强求旧结果，测试需锁定字典数据或选择快照，并另测实时模式变化的可解释性。至少包含一条在字典结果上继续函数计算、一条条件依赖lookup的两阶段规则。

### 19.4 故障与恢复

| 注入故障 | 验收要点 |
| --- | --- |
| 后续窗口数据失败 | FAIL_FLOWFILE下此前窗口无成功提交，原输入完整 |
| 第二字典连接超时 | 第一字典结果不导致部分提交；按有限重试执行 |
| Writer关闭失败 | 无半成品success输出，原输入可恢复 |
| 处理器/节点进程中断 | Session恢复、队列和内容一致；崩溃循环可熔断 |
| retry次数达到上限 | 进入failure并保留内容，不无限自环 |
| 快照缺失/被撤销 | 明确拒绝，不换成最新快照继续跑 |
| 单条超大字段/过多token/正则恶意输入 | 有界拒绝或隔离，不OOM/长时间阻塞 |
| 集群某节点缺NAR | 发布失败，旧任务仍可运行 |
| 新图校验/切换失败 | 旧图、队列、水位和绑定保持可恢复 |
| 新图已落库再请求回退 | 按幂等/补偿约束处理，不重复采集造成静默重复 |

### 19.5 数据库与性能范围

转换内核使用Java逻辑类型，跨库变化不生成不同CAST/日期/聚合函数；但字典查询、DDL、Reader和目标写入仍受实际数据库/驱动约束。先覆盖当前实际行业MySQL、达梦和已使用来源/目标，再按产品承诺验证PostgreSQL、Oracle、SQL Server、DB2、Kingbase/GaussDB、Hive等，未验证组合显示未验证，不写成全数据库已支持。

字典能力需验证schema/大小写/引号、参数容量、复合键、中文、LOB、精度、日期和只读权限；无法可靠JDBC批量读取的系统使用已批准的批量提供者或版本快照。当前Hive/MRS来源目标特殊写入、DDL和认证仍由独立适配层验收。

性能采用同一机器、并发、数据分布、Reader/Writer格式、Schema、目标写入和字典新鲜度，对比旧链/新链的rows/s、P50/P95、CPU、GC、峰值内存、Content Repository写入、FlowFile数、JDBC查询数。至少包括纯转换、单字典、多字典、多值、深依赖、大记录和大FlowFile。仅组件减少或SQL计数推导不能转换成“吞吐提升N倍”。

### 21.2 数据库与时间适配原则

转换表达式只编译为 Java 求值，不发送数据库 CAST、日期函数或拼接 SQL。字典读取采用驱动标识符引用、PreparedStatement、参数数量限额及复合键分批；登记与投影操作按真实租户方言引用当前达梦平台的小写物理标识符。输入日期、LocalDateTime、Instant 分别处理，时间转换使用计划 zoneId；LocalDateTime 进入 NiFi TIMESTAMP 表示时以计划时区解析为时刻，避免 JVM 时区与 JDBC 时区叠加造成 8 小时偏移。

目标 INSERT/UPDATE/UPSERT/DELETE 仍由现有数据库写入模块及 NiFi 原生方言负责，转换组件不生成这些写入 SQL。数据库是否支持某一种写入操作、目标主键/唯一键、驱动和事务契约必须按具体数据库判断。字典 DATETIME 参数和读取使用 JDBC 4.2 的 LocalDateTime；不支持对应 JDBC 能力的旧驱动须升级或单独适配。

当前真实联调基线是演示 NiFi 2.11.0、Java 21 和 MySQL；函数语义及批量查询另有 H2 自动测试。Oracle、达梦、PostgreSQL、SQL Server、Hive 等实际驱动的完整读写矩阵仍需真实环境验证。不能将“转换无方言 SQL”表述为“所有数据库版本及所有数据类型均已通过验收”。

### 21.3 批量、性能及失败验证方式

- 20/100 行、每行 100 个同定义码表字段：实际 NiFi 冷查询均为一个 JDBC 读取 SQL，编码跨字段/记录去重，保持单窗口、单字典批取。这里的 SQL 数不包含目标写入与驱动连接初始化。
- 登记资源编译：一次数据源角色授权读取、一次表读取、一次列读取；20/100 个引用使用相同次数。每一个数据源/表/列都须在当前租户和角色范围内，包含无权或跨租户 ID 时整批拒绝。
- 窗口事务：600 条记录在后续窗口失败时没有成功 FlowFile 提交，原输入完整保留；ROUTE_INVALID 的成功与错误输出在同一 Session 提交。
- 核心吞吐测试固定 100 个字段、10,000 行，使用已编译计划和 500 行窗口。结果只表示本机纯转换吞吐，不能替代含数据库、网络和 Content Repository 的 P95/CPU/GC 压测。
- NAR 必须 `mvn clean package`，再运行 `tools/check-mapping-nar.py`，拒绝混入不同版本同名类；打包检查与单元测试是不同验收步骤。
- 当前任务的具体运行报告、校验摘要、临时包和恢复材料按仓库规则保存在忽略的 logs 或受限目录；文档只维护验证方法与功能边界，不累积机器运行快照。

详细构建和运行契约见 [NiFi 扩展维护说明](../data-elements-parent/mapping-extension/README.md)。`tools/package-backend-overlay.py` 校验所选运行类的原摘要，并确认未选中的运行类和资源内容一致，支持当前任务逐类更新及暂存包回读；不能用于绕过并发版本检查。

| 服务端恢复草稿 | 单独接口带流程、节点和 `expectedUpdatedAt`，检查版本后更新草稿与投影 | 与抽屉内尚未保存的复制操作区分；不会直接启动历史计划 |

模板不得携带连接密码、token、私钥、keytab、业务 sampleRows 或快照明细。版本 ID 只是定位标识，不能赋予访问权限；模板导入、计划查看、资源解析和草稿恢复均须复核当前租户及角色范围。跨任务复用必须重新绑定当前可见来源、目标与字典。当前角色与批量计划相关的 13 条选定测试通过；对新增资源类型或调用入口仍需补充相应授权用例。

`restore-draft`、`upgrade-runtime`、`start-published` 共用 `SerializedNifiMutation` 串行保护。数据库层 `PipelineRepository.update` 同时采用比较后更新：UPDATE 条件包含 ID、认证 tenant_id、is_del=0 和旧 updated_at，影响行数不是 1 即报冲突；新时间版本取当前时间与“旧值 + 1”的较大者，保证单调递增。入口版本检查、串行锁和 SQL 条件更新共同防止不同保存/恢复/升级入口覆盖并发修改，不能只依赖 Java 进程内锁。

### 22.4 字典读取的三种一致性模式

字典定义新增 `freshnessMode`；统一内核、后端预览与 NiFi 批量服务使用同一策略实现。运行先核对授权绑定中的数据源、表/schema、键及键类型、取值列、过滤条件、重复键策略，之后才允许命中缓存或快照。缓存不能成为绕过授权或掩盖逐记录读库的途径。

| 模式 | 执行契约 | 主要参数及限制 |
| --- | --- | --- |
| `LIVE_BATCH` | 每个依赖阶段汇总并去重本批键，交给批量 JDBC 提供者；下一次执行重新读来源 | 默认模式；SQL 次数仍受字典组、复合键和参数分批数影响 |
| `TTL_BATCH_CACHE` | 先读有界缓存；仅把所有未命中/过期键合并后批取；命中和未命中结果都可缓存 | `ttlSeconds=1..600`；当前最多 5,000 个缓存项，单项值超过 4,096 字节不缓存；不承诺重放读取旧值 |
| `VERSIONED_SNAPSHOT` | 按明确 `snapshotId/snapshotHash/definitionHash` 读取已构建的完整不可变快照，运行不查业务字典表 | 构建最多 5,000 行、累计序列化条目 1,000,000 字节、查询超时 10 秒；超限或失败不保存截断版本 |

缓存范围包含执行命名空间、规范化字典定义摘要及类型化键。NiFi Service 启用/停用时清理缓存和已加载快照索引；后端预览按租户命名空间隔离。字符 `01` 与数字 1 仍按类型化键区分。缓存容量上限不会把未缓存值变成未命中：超限时本次结果正常返回，后续按批量查询读取。

快照由已登记、已授权的结构化字典定义构建，成功后追加 `DICTIONARY_SNAPSHOT` 资源版本。切换为快照模式须引用该版本；定义摘要或快照内容摘要不一致时拒绝执行，不自动降级为 LIVE_BATCH。NiFi 快照明细进入敏感的 `snapshot-payloads` 服务属性，普通计划响应仅携带引用与摘要。当前创建操作构建一份完整版本；没有把定时刷新、跨节点共享缓存或自动快照淘汰声明为已实现。

本轮实际运行已验证同一字典、100 行、同一键集合连续两次执行：LIVE_BATCH 的字典 SQL 次数为 `[1,1]`，TTL_BATCH_CACHE 为 `[1,0]`，VERSIONED_SNAPSHOT 为 `[0,0]`。这是对应测试条件下的字典读取计数，不包含快照预先构建、授权/元数据预取、连接初始化或目标写入 SQL，也不代表任意多字典场景始终只有一次查询。

### 22.5 Schema 契约、来源取样与脱敏

“锁定物理 Schema”通过已登记来源/目标引用读取实际物理结构，保存到草稿 `schemaContract`，包含来源/目标字段结构、摘要、登记引用和 `allowAdditionalSourceFields`。契约检查覆盖字段名称、逻辑类型、NULL、默认值以及适用的字符串长度、小数精度/小数位；不能仅以页面显示类型认定物理结构一致。

编译/发布重新检查已绑定物理结构，NiFi 读取记录时还检查 Reader 的实际输入 Schema。允许无关来源新增字段的行为由契约明确；缺列、类型或精度变化不能自动重建目标表或偷偷重新推断规则。Schema 引用先批量授权，再按实际数据源分组；每个数据源只打开一次连接，物理读取采用下列有界批量路径，不能在字段/表循环内逐项探查。

| 驱动路径 | 批量方式 | 已明确的边界 |
| --- | --- | --- |
| MySQL/MariaDB | 一次参数化 information_schema.COLUMNS 查询覆盖本数据源请求的 catalog/table，使用完整 COLUMN_TYPE 判定原生类型 | 可覆盖请求中不同 catalog，schema/table 条件绑定参数，不拼入任意标识 |
| 其他 JDBC | 当前连接单 catalog、明确单 schema，调用一次 getColumns 扫描后在内存匹配本批已授权表 | 不按表反复 getColumns；跨 schema/catalog 的通用回退拒绝，须另实现专用批量适配 |

每批最多 100 个引用、8 个数据源；单表最多 2,000 列，总响应及物理元数据扫描最多 20,000 列。驱动扫描超限即拒绝，不为绕过预算无限枚举。当前 Schema 批读 12 条选定测试已通过；这证明实现与测试覆盖的批量边界，不能代替其他真实数据库驱动的连接和类型矩阵验收。

“从登记来源取样并预览（脱敏）”默认 20 行、允许 1～100 行，非法 limit 拒绝；当前自动取样面向已登记的 JDBC 数据库表；服务端用已登记表和列生成受控 SELECT，设置 10 秒查询超时、最大返回行数和 2 MiB 累计样本预算，大文本单值另受限制。它不是任意 URL/SQL/连接信息执行入口，也不是随机抽样或全表统计。

处理顺序固定为“服务端读取原始有限样本 → 服务端用统一内核执行 → 回传前脱敏”。真实来源取样接口同时对 `sampleRows` 和 `resultRows` 全部非 NULL 值进行遮盖，返回 `sampleMode=REGISTERED_SOURCE_MASKED`、`masked=true`；不会让先遮盖的数据参与类型转换。手工样本预览按敏感字段及其派生输出进行保护，别名或目标改名不能自动解除敏感性。公开错误只保留受控错误码和定位信息，不返回原始字段值。

本轮已通过 20/100 行正式预览中的 38 位小数精度与敏感 alias 验证；实际登记来源 20/100 上限取样的输入、输出双端全遮盖已验证。全遮盖响应只能证明没有公开样本值；完整数值正确性另由受控测试向量检查，不能凭遮盖字符串判定转换正确。

### 22.6 56 项能力与 53 项直接值函数

能力接口当前返回 56 项，覆盖历史 51 个声明名称并增加 `idCard15To18`、`idCardValidate`、`uuid`、`now`、`blankToNull`。其中 53 项可作为 `FUNCTION` 的直接值函数；`uuid` 映射到 `SYSTEM_VALUE`，`codeTableLookup` 映射到 `LOOKUP`，`expression` 映射到 `EXPRESSION`。三项特殊能力不能被当作普通值函数直接调用，更不能在纯函数 helper 内逐记录查字典。

每项能力包含函数版本、`previewSupported/runtimeSupported`、实现引擎、对应算子、`directFunction`、`parameterSchema` 及 `additionalParametersAllowed`。参数 Schema 按位置提供 `index/name/type/required/defaultValue/choices`；编辑器据此展示整数、精确小数、字符串、枚举和 JSON/对象输入。精确数值控件使用字符串模式，避免经浏览器浮点丢失精度。`coalesce/nvl` 的额外参数许可与其他固定参数函数区分；无参数函数返回空参数 Schema。

参数表单是当前已实施能力，不代表第 7～8 章所有高级设计选项都已自动开放。当前签名以能力接口及 `FunctionArgumentSchema` 为准，例如 substring 的第二个参数为“截取长度”，不沿用早期设计中“结束位置”的描述。预览与运行都必须通过同一函数绑定器检查参数；界面可选择不等于任意类型、嵌套结构或目标驱动均已验收。

### 22.7 仅替换字段节点的运行升级契约

统一编辑器新增“保留来源 ID 升级运行节点”。它针对已部署画布中的一个字段映射/字段增强节点，保持同流程组中的来源、目标处理器及其 ID，来源 state 不复制、不清空、不删除。该路径与第 21 章原有的整图候选重建不同；画布中其他草稿修改不随本次字段节点升级发布。当前已通过真实 NiFi 旧 QueryRecord → 新 Processor 替换，并再次升级至 1.1.1：来源/目标 ID 和来源水位逐项不变，原 STOPPED 来源没有被误启动。

请求包括 `pipelineId/nodeId/expectedUpdatedAt/expectedPlanHash/start`。服务端从当前已保存 DSL 重新编译该节点；`expectedUpdatedAt` 必须匹配画布版本，`expectedPlanHash` 必须匹配已保存规则的实际计划。前端尚未保存的规则、升级期间的并发修改都必须阻止提交。仅传 nodeId 或相信浏览器上传的计划正文不构成升级授权。

升级准入与切换流程如下：

1. 核对当前租户、角色、流程组归属标记及字段节点所有原生处理器/边界连线的实际身份；核对 Reader/Writer、精确扩展 Bundle 和旧图范围。无法核验的历史图返回明确原因，不猜测关联。
2. 读取并保存各原生 Processor 的实际运行状态。队列必须明确为空；先检查，再停组并等待处理器停止，随后再次检查队列。没有返回可信队列数、队列非空、范围超限或连接被外部修改都不允许切换。
3. 在原字段节点所属组内创建新字段处理器及所需服务，复用已核验 Reader/Writer，建立候选边界连接并检查新处理器有效性。只调整选定节点的入/出边界，不删除来源、目标及其 state。
4. 切换字段节点边界后，将旧映射处理器保留为 `DISABLED`，保留其内部组件供恢复核查；更新节点与原生 ID 的映射、当前计划引用。旧处理器留存不代表可以同时启动两套映射。
5. `start=true` 表示按升级前逐个 Processor 的实际状态恢复：原来运行的组件恢复运行，原来停止/禁用的组件不能被整组启动；只有旧字段链实际运行过时才相应启动新字段处理器。`start=false` 保持停止。不能用流程总体 RUNNING 状态替代每个节点的状态快照。
6. 失败后保留来源及目标，停止相关运行范围并处理候选连接；提交前失败尝试恢复旧边界，无法完整恢复返回需要人工处理的状态。提交后恢复运行失败不应伪称旧计划已回退。恢复完成与否必须回读原生图、引用和状态判断。

当前实现限制在可核验的有限嵌套范围，设置了 512 个处理器、1,024 条连接、512 个可见 Controller Service、128 条字段边界边等上限。升级失败边界 10 条选定测试已通过；旧 1.0 单值字典 SQL 和拆分 SQL 查表规则的转换已修复并测试。上限是拒绝无界操作的保护，不是所有范围内拓扑和故障组合均已验证的承诺。非空业务队列不得为了升级被清空，增量水位不得为了通过检查被删除。

**已发布运行版本的显式启动。** 普通流程 `/start` 继续检查 DSL 部署摘要；有尚未发布草稿时仍拒绝，不因字段节点局部升级而把整图标记为已部署。统一编辑器新增“启动已发布运行版本”，显式调用 `POST /nifi/api/field-mapping/start-published`，只启动当前已部署的原生图，返回 `draftPublished=false`，其余草稿继续保留。

该入口要求 `pipelineId/expectedUpdatedAt`，一次批量读取当前 publication 引用的不可变计划，并通过统一编译重新核验资源与角色范围；之后核对流程归属标记、全部来源/目标/辅助原生 ID、字段节点 plan-id 和所有已登记边界连接。发现未登记的额外 success 候选连接即阻止启动，不能让未完成恢复的支路同时消费记录。各原生范围一次读取 revision，普通组件按范围启动；禁用组件不启动，一次性来源只执行 `RUN_ONCE`，不改为持续 RUNNING。

“启动已发布运行版本”是用户明确启动当前图的动作，与升级时按原状态恢复不同：前者可以启动原本停止且未禁用的现有组件；后者必须保持升级前逐组件的运行意图。当前已完成平台 `/stop → /field-mapping/start-published → /stop` 真实验证及已发布生命周期 3 条选定测试，pending 草稿没有被标成整图部署成功。异常时停止确认失败仍需返回人工恢复状态，不能把接口成功当作所有组件都正常完成执行。

### 22.8 确定性上下文与版本保留

NiFi 新增 `plan-id` 和 `context-node-id` 属性。发布编译器当前将画布稳定 `node.id` 写入 `context-node-id`，运行用它隔离 `ht.plan.hash.<context-node-id>`，并以 `ht.input.identity + context-node-id` 形成生成器上下文；`ht.execution.clock` 固定本输入的时钟。替换原生 Processor 导致其 NiFi UUID 改变时，稳定画布节点身份仍保持不变。缺少该属性的手工旧组件回退到原生处理器 ID，因此不能自动宣称它具有跨替换确定性。

同一输入身份、稳定节点身份、规则/函数版本、计划及固定字典快照是确定性重放的共同前提。同节点读到不同历史计划摘要时拒绝重放；多字段节点串联分别检查自己的摘要。LIVE_BATCH/TTL 读取的业务值可能改变，不能仅因 ID 与时钟固定就承诺完整输出不变；这也不等于目标写入已实现 exactly-once。

当前 `/retention-policy` 返回 `policy=KEEP_ALL`、`automaticDeletion=false`。计划、模板和快照历史没有自动删除接口；当前发布引用可以切换，但被引用的不可变内容保留。旧 disabled 映射处理器也不在升级操作内自动清理。未来清理必须另行建立运行/重试/错误队列/回退引用核对和授权机制，不能把时间早或当前未启用当作可删证据。

### 22.9 已落地接口与操作入口

以下接口前缀为 `/nifi/api/field-mapping`，描述 1.1.1 当前代码契约；已确认测试范围见 22.10 节，不将早期第 13 章的拟定路由当作现行实现。

| 方法与路径 | 请求要点 | 返回或行为 |

| `GET /plans/{id}` | pipelineId | 指定不可变计划正文；单条主动读取 |
| `POST /plans/{id}/restore-draft` | pipelineId、nodeId、expectedUpdatedAt | 恢复草稿和投影，不切换运行计划 |

### 23.3 码表配置与权限

码表流程为“加载授权数据源 → 搜索登记表 → 选择键列/取值列 → 配置策略”。表搜索采用服务端分页，默认20、最大100；用户选定表后一次读取该表字段。单键默认使用当前步骤输入，多键按键列顺序绑定源字段、常量、目标字段或步骤输入。拆分映射的第一键使用拆分编码，其余键作为关联限定。

过滤器提供登记列上的比较、LIKE、NULL、集合及 AND/OR 组合，后台只生成参数化查询，不接收自由 SQL。重复键提供 `ERROR` 和旧规则兼容的 `LEGACY_MAX_LABEL`，不暴露内核尚未支持的任意首条/末条策略。单值未命中可置 NULL、保留、转空字符串、使用默认值或报错；拆分另设输入/输出分隔符、部分未命中策略、文本/数组输出及已命中 NULL/空标签处理。字典读取方式支持实时批量、有限 TTL 缓存和固定完整快照。

表分页为一次整组数据源授权、一次 COUNT 和一次分页读取；20/100项不会触发逐表查询。字段接口及发布编译再次按当前租户、数据源、登记表和列校验。UI 隐藏选项不代替后台授权；错误数据源或他租户表 ID 不能读取字段。表单不得保存数据库密码、令牌或连接 URL。

### 24.2 ODS_UUID 规则

旧生成模板把同一输入的固定时间戳拼接6位或9位随机尾数，压缩后的取值空间不足。默认规则改为 `SYSTEM/UUID32`，生成32个十六进制字符，保留标准命名UUID的完整有效位，适配现有 VARCHAR(32) 字段。

命名空间包含原输入身份、当前节点输入FlowFile的稳定身份、流程ID、画布节点ID、记录绝对下标及规则ID。编译器在整图发布和字段节点升级时都写入 `context-node-id=流程ID:节点ID`。记录下标跨512条窗口继续累加；同一父输入拆分出的不同子FlowFile不能共用生成身份。生成过程不访问数据库、Redis或分布式锁。同一输入重试保持相同ID；不同输入、记录、流程或节点使用不同命名空间。该规则保证重试的一致性，不把UUID当作业务去重或跨系统 exactly-once 的证明。

`UUID()` 是该规则的兼容输入语法，由Java执行，不发送到源库。编译时仅将目标为ODS_UUID且匹配两种已知历史生成模板的表达式升级为UUID32；人工常量、普通源字段和任意自定义表达式保持原意。已发布旧计划不在后台静默改写，应保存新草稿后显式发布或升级。已有36位UUID规则继续支持，配置时须匹配目标长度。

### 24.3 日期与时间

| 登记选择 | 逻辑输出 | 行为 |
| --- | --- | --- |
| 日期 | DATE | 保留年月日，日期时间转日期是明确的日历日期截取。 |
| 时间 | DATETIME | 保留年月日及时、分、秒；使用目标数据库支持的DATETIME/TIMESTAMP等类型。 |

日期解析的默认类型跟随已选择的时间目标。时间目标使用 `uuuu-MM-dd HH:mm:ss` 与DATETIME解析；仅日期解析直接回填时间目标会在编译时报告 `TEMPORAL_PRECISION_LOSS`，避免隐式补零点。确需从日期构造零点时，使用明确的后续CAST。DATE转换同时接受JDBC时间对象与JSON日期时间文本，使预览和执行一致；带偏移的时间点按计划时区取日期。

JDBC读取端在Hive和JAVA_RECORD流程中显式开启 `Use Avro Logical Types=true`，Writer写出完整 `avro.schema`，下游使用配套的类型化Reader。DATE、TIME和TIMESTAMP分别采用 `yyyy-MM-dd`、`HH:mm:ss`、`yyyy-MM-dd HH:mm:ss.SSSSSSSSS`。这一配置遵循 [ExecuteSQLRecord逻辑类型契约](https://nifi.apache.org/components/org.apache.nifi.processors.standard.ExecuteSQLRecord/) 和 [JsonRecordSetWriter格式契约](https://nifi.apache.org/components/org.apache.nifi.json.JsonRecordSetWriter/)。

NiFi的TIMESTAMP中间编码表示时间点：当前验收中本地14:27:49在JSON线上表现为UTC06:27:49，配套Reader和Asia/Shanghai计划时区回读为14:27:49，最终数据库也保存14:27:49。不可将中间文本再按另一套无时区语义解析。DATE保持日历日期，NULL保持NULL。Writer格式中带9位小数不等于所有JDBC驱动和目标列都保留纳秒；当前实际写入验收确认到秒，更高精度须按驱动和物理列另行核验。

Hive的来源ExecuteSQLRecord和自定义字段组件继续绑定 `PUBLIC-WRITER-JSON-TIME_FORMAT`；普通来源也采用匹配的时间编解码参数。字段节点升级保留来源组件和水位；旧来源已输出截断值时，Writer不能恢复丢失的信息，需要受控调整原读取链路。

## 25. 宽表字典容量与数据库时间语义（V2.6 / 1.1.6）

### 25.1 数量报错与容量

“字典或数据源数量超限”的原判断是字典定义超过32个或独立数据源超过8个，并不是字段达到190个。字典授权层另有100个定义的限制，因此仅调整内核仍不足以支持含190个独立字典规则的表。

当前内核及授权层的字典定义上限统一为1,000个；规则最多1,000条，单表Schema最多2,000列。字典数据源仍最多8个，计划2MiB、记录窗口512条/8MiB、查询超时、输出与结果字节预算继续生效。错误分别指出字典定义数量或独立数据源数量，字段数量不占用数据源限额。这是有界容量扩展，不是取消资源预算。

同一登记表的重复授权条件先合并，表归属与字段读取仍各一次批量查询；每个定义再对数据源、表ID、键列、取值列和过滤列逐项核验。相同完整定义仍共享字典ID，不能通过合并查询扩大租户或角色范围。运行时按定义和本窗口去重键批取，不按记录逐项查询；190个不同定义不等于一条SQL，若定义确实不同，每个定义仍有自己的批次。

### 25.2 Linewell写入组件的ODS时间默认值

只有实际目标列包含相应字段时，才为LinewellPutDatabaseRecord生成默认配置。Oracle和OceanBase Oracle模式使用数据库端 `SYSDATE`；其它方言使用适用的数据库当前时间表达式，不将Oracle语法直接发送给其它库。

| 原生组件显示属性 | 同时存在两个ODS时间字段时的默认值 |
| --- | --- |
| insert 追加value 值 | `ODS_RKSJ=SYSDATE,ODS_GXSJ=SYSDATE` |
| update 追加value 值 | `ODS_GXSJ=SYSDATE` |
| merge 排除 update | 包含 `ODS_RKSJ`；存在 `ODS_UUID` 时也包含该字段 |

`ODS_RKSJ` 表示首次入库时间，MERGE更新保留既有值；`ODS_GXSJ` 在新增和更新分支均使用数据库当前时间。仅存在其中一个字段时，仅生成对应赋值；保留元数据的实际字段大小写。字段映射中的LOCALTIMESTAMP仍可用于预览与非Linewell链路，Linewell写入分支以数据库时间为准。

编译器只向Linewell组件生成内部配置意图。NiFi新建组件响应中的真实属性描述用于匹配上述显示项，并以真实API属性名提交一次配置更新；内部键不会发送给NiFi。属性缺失、名称不唯一或只能匹配到动态属性时明确中止，避免创建一个看似同名却不生效的参数。这一读取使用创建响应，无逐行/逐组件补查。普通NiFi PutDatabaseRecord不接收Linewell专属参数，当前默认配置不外推为该组件所有UPSERT分支的同等审计时间能力。

### 25.3 DATE与时间被截断的修正

Oracle的 `DATE` 存储年月日及时、分、秒，OceanBase Oracle模式具有相同语义；不能统一当作仅年月日的Java LocalDate。此差异依据 [Oracle数据类型说明](https://docs.oracle.com/en/database/oracle/oracle-database/19/sqlrf/Data-Types.html) 和 [OceanBase Oracle模式日期时间说明](https://www.oceanbase.com/docs/common-oceanbase-database-standalone-1000000006077987)。

| 数据库或物理类型 | 逻辑语义及本轮验证 |
| --- | --- |
| Oracle / OceanBase Oracle的DATE | DATETIME；登记和物理元数据均按该模式转换；物理DATE标记 `dateContainsTime=true`。 |
| MySQL、MariaDB、PostgreSQL、SQL Server、Db2、达梦、金仓、GaussDB、瀚高、GBase、神通、ClickHouse、Hive及OceanBase MySQL的DATE | 保持仅日期DATE，不因名称相同而套用Oracle含时分秒语义；若实际兼容模式另有扩展，须按真实连接确认。 |
| DATETIME、TIMESTAMP、DATETIME2、SMALLDATETIME、DateTime64、TIMESTAMP WITHOUT TIME ZONE | DATETIME；别名识别与非零时分秒转换测试通过，目标物理精度仍受数据库约束。 |
| TIMESTAMPTZ、TIMESTAMP WITH TIME ZONE、TIMESTAMP WITH LOCAL TIME ZONE、DATETIMEOFFSET | 时间点INSTANT；偏移解析测试通过；带空格的偏移文本也直接按偏移取得时间点，结果不依赖JVM默认时区。NiFi的TIMESTAMP记录类型按已声明输入契约解释时间点。 |
| SQL Server的TIMESTAMP / ROWVERSION | 按ANY保留二进制原型，不当作日期时间；该类型是数据库版本号，依据 [Microsoft类型说明](https://learn.microsoft.com/en-us/sql/t-sql/data-types/rowversion-transact-sql)。 |
| TIME / TIME WITHOUT TIME ZONE | TIME；内核、配置选项、NiFi输入及输出Schema保留时分秒。当前统一Time Format为 `HH:mm:ss`，不宣称TIME小数精度已保留。 |

读取端也必须修正：Oracle DATE列在GenerateTableFetch及QueryDatabaseTableRecord的 `Columns to Return` 中投影为 `CAST("字段" AS TIMESTAMP) AS "字段"`，其它列保持原列名。使用已探查字段、验证标识符、保留原别名，不改过滤条件、排序字段或水位列。否则JDBC/Record读取端可能已经把时分秒丢掉，后面的Writer或映射无法恢复。两条来源发布路径的属性名均按NiFi真实契约校验；[GenerateTableFetch属性说明](https://nifi.apache.org/components/org.apache.nifi.processors.standard.GenerateTableFetch/)与[QueryDatabaseTableRecord属性说明](https://nifi.apache.org/components/org.apache.nifi.processors.standard.QueryDatabaseTableRecord/)可供核对。

已有锁定Schema只修复经当前租户批量授权和物理元数据证实的Oracle DATE语义，其它类型、长度、精度和非空漂移继续拒绝。明确的日期截取步骤保留原意，日期解析误用于时间目标继续报错。旧未锁定规则在发布时结合目标Oracle DATE元数据修复推断类型；首次打开已登记来源/目标的旧规则时，前端一次取得整份物理Schema后编译，不按190个字段逐项读取。

仅升级字段节点不会自动改写旧来源处理器。已有流程若读取端已经输出仅日期，需要同时受控调整来源的投影和配套Reader/Writer，并保留来源组件ID与state；不能通过清空水位、删除队列或重建业务表修正。

## 26. 多格式日期逐值识别（V2.7 / 1.1.10）

### 26.1 需求与执行约定

同一来源表、同一个字段、同一批记录可以混用多种日期文本格式。必须对每个当前值识别；禁止用第一行、抽样结果或列名推断后将整列固定为一种格式。缓存只保存不可变的格式器，不保存“该字段使用某一种格式”的结论。调整输入顺序、跨越512条窗口、并发执行或更换首条值都不能影响转换结果。

附件 DateFormatUtil.java 的14种模式作为格式需求参考。其旧实现将日期、年月、纯时间全部交给LocalDateTime.parse，无法为缺失部分提供完整语义；失败返回NULL/0也容易把错误隐藏。当前实现统一使用严格的java.time解析、完整消费输入和明确失败码，未直接复制旧类。格式符依据 [Java 21 DateTimeFormatter](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/format/DateTimeFormatter.html)：小数秒使用S语义，两位年份固定2000—2099；yyyy/yy在解析模式中兼容为uuuu/uu，带引号的文字不改写。

### 26.2 配置入口与兼容

复用原有字段映射组件，在表格“转换和规则”的配置中选择“日期处理”。普通页面只展示“输入格式”和“转换结果”；日期补全默认折叠。没有新增第二套字段映射组件，没有恢复旧草稿提示或额外表格统计行。

- 输入格式默认为“自动识别”：同一字段逐条适配内置格式。
- 特殊日月顺序、其他语言或项目专用文本选择“指定格式”；原有指定格式规则保持原意，不擅自改成自动识别。
- 数字时间戳显式选择秒、毫秒、微秒或纳秒，避免把业务编码当作时间。
- 转换结果支持DATE（日期）、TIME（时分秒）、DATETIME（保留日期及时分秒）和INSTANT（时间点）。已有目标是DATETIME、TIME或INSTANT时，切换日期处理沿用该语义。
- 需要缺省年月日的输入展开“日期补全”，填写完整的YYYY-MM-DD。只填缺失部分，不覆盖输入已有年月日；不根据运行当天、1970年或JVM时区猜值。
- 空白是否转NULL、非法值置NULL/默认值/隔离错误行，继续使用已有空值与失败策略。未配置替代策略时不得悄悄吞掉转换失败。

示例规则：

```json
{
  "ruleId": "event-time",
  "input": {"kind": "FIELD", "name": "event_time"},
  "target": {"name": "EVENT_TIME", "logicalType": "DATETIME"},
  "steps": [{"operator": "DATE_PARSE", "args": {"pattern": "AUTO", "logicalType": "DATETIME"}}]
}
```

原值直接映射到时间目标、CAST日期类型，以及parseDate函数均复用同一个TemporalParser。函数参数兼容 `parseDate(pattern, logicalType, options)`；例如 `['AUTO','DATETIME',{'defaultDate':'2000-01-01'}]`。省略DATE_PARSE的pattern也按AUTO；DATE_FORMAT仍必须指定输出格式，不猜输出格式。

### 26.3 格式覆盖表

| 输入类别 | 示例 | 处理规则 |
| --- | --- | --- |
| 横线、斜线、点号完整日期 | 2024-06-07、2024/05/10、2024.5.10 | 月日可不补零；DATE保留日期，DATETIME补00:00:00。 |
| 日期时间到分或秒 | 2024-05-10 14:27、2024/05/10 14:27:49 | 缺少秒补00；存在的时分秒不得截掉。 |
| 小数秒 | 2024-05-10 14:27:49.1、.123、.123456、.123456789 | 1—9位十进制小数秒，内核保留纳秒。 |
| 两位年份 | 24-05-10 14:27:49 | 固定解释为2024；99为2099，不使用滚动世纪窗口。其他世纪使用四位年份或明确指定格式。 |
| Java英文日期 | Fri May 10 14:27:49 GMT+08:00 2024 | 自动识别英文星期、月份、时区；CST等缩写须与配置流程时区在该日期的真实简称相符，不任意解释为另一区域。 |
| Oracle风格英文文本 | 10-MAY-24 02.27.49.123456789 PM | 两位或四位年份，12小时制，AM/PM，小数秒1—9位；使用稳定英文环境。 |
| 年月 | 2024-05、2024/05 | 需要补全日期的日；例如2000-01-01补成2024-05-01。无补全配置报DATE_INCOMPLETE。 |
| 纯时间 | 14:27:49、14:27、14:27:49.123456789 | 输出TIME不需要年月日；输出DATE/DATETIME/INSTANT需要补全日期。 |
| 月日 | 05-10 | 用明确补全日期的年份；不以当年作为默认年份。 |
| 紧凑格式 | 20240510、20240510142749、20240510142749123456 | 8位完整日期，14位完整日期时间及后续1—9位小数秒。 |
| 中文日期 | 2024年5月10日、2024年5月10日 14:27:49 | 使用年月日字面符号，可含时间和小数秒。 |
| ISO与数字偏移 | 2024-05-10T06:27:49Z、2024-05-10 14:27:49 +08:00、+0800、+08 | 有偏移先取得时间点；DATETIME按流程时区表达，INSTANT保留时间点。 |

| 数字时间戳 | EPOCH_SECONDS / EPOCH_MILLIS / EPOCH_MICROS / EPOCH_NANOS | 显式单位，整数精确换算；支持负值，不按字符长度猜秒或毫秒。 |

不能把有限格式目录写成“任何字符串都能转换”。业务新格式可以使用指定格式，必要时再补入经测试的自动目录。短时区名、日月顺序、缺失年份和数字单位均有确定规则。

### 26.4 严格校验、精度与时区传输

非法闰日、2月30日、13月、24时、60秒、尾随文本、超过9位小数、非法补全日期均失败；输入最长128字符，指定模式最长256字符。DATE_INVALID、DATE_INCOMPLETE、DATE_UNIT_REQUIRED、DATE_AMBIGUOUS区分非法值、缺失信息、单位和歧义，日志不带源字段值。

DATETIME和INSTANT在流程时区的夏令时重叠/缺口处不得悄悄选择偏移。明确偏移的INSTANT可以表达该时间点；若改为DATETIME并丢弃了偏移导致无法唯一回写，则应保持INSTANT语义。显式DATE截取仍保留原意，DATE解析直接接DATETIME目标的精度保护继续生效。

NiFi格式化Record Writer与Reader使用其运行JVM时区来编码/还原Timestamp载体，业务DATETIME按流程zoneId转为传输时间点，Reader还原后再恢复业务时间。中间JSON中的无偏移文本不能直接与业务本地时间作等值比较；例如流程Asia/Shanghai、NiFi JVM UTC时，业务14:27:49可能在中间显示为06:27:49。验收须核对传输时间点、串联转换与最终数据库值。保留已验证的载体约定，不修改NiFi全局时区。

来源、流程和目标JDBC连接的时区策略必须相互一致，尤其MySQL Connector/J的serverTimezone/connectionTimeZone会影响Timestamp写入。不能仅把中间JSON改成业务时间就认定正确，或擅自删除连接的时区参数。不同真实驱动仍需分别做最终落库验证。

字段映射预览响应单独将日期时间按完整精度呈现，避免全局JSON秒级格式器隐藏微秒/纳秒；不调整其他接口的时间格式。内核/预览可保留1—9位小数秒，MySQL DATETIME(6)本轮只验证到微秒。TIME当前NiFi约定仍为HH:mm:ss，不能据内核LocalTime的纳秒支持宣称所有TIME目标已保留小数秒。

### 26.5 性能、权限和验证方法

自动解析按当前值的结构分流到预编译、不可变格式器，不在每行重新编译模式、不依赖共享SimpleDateFormat、不逐个异常重试全部格式。指定模式在规则编译时创建，运行时复用；未增加每行网络请求或日期转换SQL。数字时间戳沿用数值精度/指数预算，拒绝超大指数，避免精确整数换算造成巨量内存分配。现有512条/8MiB窗口、规则/计划预算和批量字典边界保留。

同一字段20/100条混合格式预览每次一次请求，日期转换SQL=0、字典SQL=0。原生验收使用12种格式混合一列，来源为VARCHAR，同一批含仅日期、非零时分秒、微秒、英文、中文、偏移、年月、月日、纯时间；经过两个映射节点后按目标表真实值逐条比对。测试对象使用新建且有所有权标记的隔离库和独立流程组，完成后只清理本次对象，不触碰业务队列。对未登记tableId的权限拒绝继续验证；没有新增跨租户读取，也没有通过批量入参扩大角色数据范围。

验证分层：共享内核与预览测试、同一Parser的40,000次并发混合格式正确性测试、前端97项回归及构建、NiFi 2.11/2.9 SDK真实编解码回环、演示NiFi 2.11及MySQL端到端读写。40,000次测试只证明并发正确性，不代表生产吞吐承诺；未获得Oracle、达梦、PostgreSQL、SQL Server、Hive等真实测试连接时，不宣称所有驱动都已实测。

### 26.6 发布与使用

最终交付内核、函数库、后端默认Bundle和NAR统一为1.1.10，部署后核对capabilities版本及NiFi处理器/字典服务版本。NiFi 2.11默认包为 `logs/field-mapping-extension/haitong-mapping-nar/haitong-mapping-nar-1.1.10.nar`；NiFi 2.9专用包为 `logs/field-mapping-extension/nifi-2.9.0/haitong-mapping-nar/haitong-mapping-nar-1.1.10.nar`。同一个实例只安装与其NiFi版本匹配的一种包，不能覆盖已加载同版本文件。

更新海通静态页面、共享后端和匹配NAR后，在原字段映射组件选择日期处理、自动识别、正确结果语义，先预览同列混合样本，再保存并重新发布或受控升级字段节点。已有明确指定格式规则不会自动改为AUTO；本轮不批量改写用户业务草稿、来源水位或已运行流程。

## 27. Hive 作为目标库时的原始写入发布规则（V2.9）

### 27.1 判断条件与模块边界

本章的判断对象是**目标库**。流程包含 `sink.hive` 时，Oracle、OceanBase、MySQL 等来源都应用 Hive 目标规则。来源为 Hive、目标为普通数据库的流程保留已有字段转换行为，不能反向套用本章的对标旁路规则。

本次只升级共享 Java 后端的发布编译、映射绑定和部署指纹，以及 Hive 组件清单说明；不修改字段转换内核或 NAR，当前正式扩展仍为 1.1.10。原画布 DSL 和用户保存的映射规则继续保留，发布时派生出面向 Hive 原始写入的执行图。

### 27.2 原生画布生成规则

HDFS 写入分支采用：`来源 ExecuteSQLRecord → ConvertRecord → UpdateAttribute（唯一文件名）→ PutHwHDFS / PutHDFS`。来源的 GenerateTableFetch、Oracle SQL 规范化和调度链保留。

| 位置 | 发布结果 |
| --- | --- |
| Hive 目标前的字段对标 | 旁路 `transform.field-mapping` / `transform.field-enrichment`，不创建对应 HaitongTransformRecord、QueryRecord 或字典服务 |
| Hive HDFS 记录合并 | 不再创建该目标内部的 MergeRecord，来源输出直接进入 ConvertRecord |
| 上游 ExecuteSQLRecord | Record Writer 绑定 `PUBLIC-WRITER-JSON-TIME_FORMAT` 的真实 Controller Service ID；Use Avro Logical Types=true |
| 当前最大值增量采集 | QueryDatabaseTableRecord 使用同一命名 Writer；直接在来源库执行的 SQL 查询也使用相同 Writer |
| 来源字段选择 | 写入 Hive 的上游 GenerateTableFetch.Columns to Return 必须未设置，以 JSON null 显式清空；当前最大值增量采集的 QueryDatabaseTableRecord 同样保持未设置 |
| ConvertRecord | Record Reader 绑定 `PUBLIC-READER-JSON` 的真实 ID；Record Writer 继续使用已核验的 `PUBLIC-WRITER-CSV-HDFS`；不输出零行文件 |
| 文件名 | 使用 `${uuid}`，保留已有唯一文件名与目标目录策略 |

JSON Reader/Writer 必须引用所选 NiFi 节点根作用域已经配置好的全局服务，不再创建任务级同名服务，也不以任务或应用作用域的同名服务代替根作用域服务。每次编译一次读取根作用域直属 Controller Service 列表，按精确名称、类型、唯一真实 ID、ENABLED 状态及校验结果确认引用；根作用域快照同时复用于 CSV Writer 查找，不按来源或目标逐项读取。全局服务缺失、同名不唯一、类型不符或未启用时明确拒绝发布，不自动补建、启用、停用或覆盖配置。

全局 JSON 服务已有的日期、时间、时区及 Schema 配置由环境维护，发布程序保持原值；不能用新建同名服务的默认配置覆盖它们。推荐日期 yyyy-MM-dd、时间 HH:mm:ss、时间戳保留目标需要的精度，并验证 Writer 与 Reader 的实际格式匹配。CSV Writer 仍从可见服务范围查找，校验类型、无表头和分隔符后引用其实际 ID。HDFS 文件格式、分隔符、字段顺序及目标表 LOCATION 须与 Hive 表定义一致。

Hive 目标上游采集的 Columns to Return 不再填入选定字段列表，也不填 Oracle DATE 的 CAST 投影，NiFi 原生属性显示 No value set。非 Hive 目标仍沿用原有字段投影和日期保护逻辑；一个来源同时服务 Hive 与其他分支时，该共用来源属于 Hive 上游，也执行清空规则。Oracle DATE 等驱动时间语义仍须按真实 Hive 目标做最终值验收，不能假设下游格式服务能够恢复来源已经丢失的时间。

HiveRecordPut 模式同样旁路字段对标并使用 Hive 目标的来源 Writer；它没有 ConvertRecord/CSV 环节，不套用 HDFS 组件参数。

### 27.3 分支、规则与错误语义

对标节点链仅在通往 Hive 的成功分支上展开，连接到原始来源；字段映射同时供普通数据库分支消费时继续部署，普通数据库分支仍执行其映射。Hive 上游共享引用全局 Reader/Writer；相同来源经多条映射路径汇入同一 Hive 目标时去重，避免重复投递。非字段映射的业务转换节点不会被自动删除。对标链循环、缺少来源连接或把异常输出作为旁路输入时，在创建原生流程前拒绝发布。

原始 Hive 分支不执行字段重命名、码表翻译、日期 AUTO 解析、校验或 ODS 派生值生成。VARCHAR 中原本混合的日期文本仍按原值写出；若 Hive 目标列要求统一时间格式，需要在来源查询或后续治理链明确处理，不能声称绕过对标后仍执行这些规则。普通数据库分支的转换规则不受此旁路影响。

部署指纹升级为 `hive-global-codecs-all-columns-v3`，防止继续复用任务级同名服务和旧采集投影。完整发布在准备新流程组、清理旧流程之前核验全局 JSON 服务；核验失败返回 HIVE_GLOBAL_SERVICES_UNAVAILABLE，保留旧流程组、状态和队列。编译阶段再次核验当前服务快照，避免发布期间配置已变化。两阶段各一次根服务列表读取，数量不随来源或目标个数增长。字段节点单独升级只沿用已解析的 Writer，不另建同名公共服务；要完成全局引用迁移及采集属性更新，须重新发布整个任务。本次不自动改写既有业务流程、来源水位或队列。

### 27.4 验证与运行边界

112 项 Java 回归覆盖全局真实 ID 复用、实际 NiFi 根与配置中的画布子根区分、任务级同名服务排除、全局缺失/同名冲突/错误类型/禁用状态拒绝、旧流程保护、采集属性清空、非 Hive 日期投影保留，以及前版的分支与映射功能。20/100 个 Hive 目标编译时，根服务列表读取各 1 次，写入组件类型查询各 1 次，任务级同名 JSON Reader/Writer 新建均为 0。Hive 专用对标链的登记绑定在 20/100 个节点时均不查询任务或规则表；混合分支沿用原有一次任务查询和批量规则读取及既有租户、角色数据范围校验，不新增跨租户读取。

演示 NiFi 2.11.0 本轮使用有所有权标记的隔离祖先/任务流程组验证真实祖先服务 ID 可绑定、任务直属服务为 0、Columns to Return 回读为 null。没有启动来源查询，验收对象已删除；此验证不修改根作用域或生产全局服务。只读核查发现演示节点当前缺少上述三个 PUBLIC 服务，不能把隔离验证描述为演示根全局服务已配置完成；生产截图中的全局配置须在对应节点核验。

前版已在演示 NiFi 2.11.0 运行真实 `ExecuteSQLRecord → ConvertRecord`，20/100 条合成 SQL 数据各执行 1 条来源查询，无对标、无合并，CSV 输出保留原文本、非零秒和微秒。该结果验证前版测试编解码配置，不能替代本轮尚未提供的真实根全局服务配置或 Hive 目标落库验收。

演示节点尚无 PutHwHDFS/PutHDFS 扩展，也未获得可用于最终落库验收的 Hive 集群，因此上述结果不能替代 Hive/HDFS 最终落库验收。真实目标仍须校验驱动、认证文件、目标目录、CSV SerDe 及完整行值。

还须区分传输时间点与 Hive 无时区时间文本：本次合成 MySQL 连接指定 Asia/Shanghai，演示 NiFi JVM 为 UTC，来源 14:27:49.123456 在中间 JSON/CSV 中呈现为 06:27:49.123456000，秒和微秒未丢失。普通 JDBC 目标的恢复约定见第26章；HDFS CSV 没有 JDBC 自动恢复步骤，直接写 Hive 前必须单独核对来源连接、NiFi 格式化时区和目标时间语义。不能凭更换服务名称宣称时区问题已解决，也不应为此擅自改动共享 NiFi 的全局时区。

### 27.5 部署与使用
