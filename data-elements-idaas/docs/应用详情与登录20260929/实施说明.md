# 卓鉴：应用详情调整与登录恢复

## 应用详情

“人员与机构资料”拆成“人员”和“机构”两个独立页签，连续放在“角色”前面。人员页展示当前应用的人员资料分配、拟用本地账号、人工来源、授权来源及同步版本；机构页展示机构分配范围和是否包含下级。各自提供刷新、分配和编辑反馈。原来的应用分配权限、对象 ID、版本校验、人工分配与独立授权来源继续由服务端控制。

“运行绑定”确有业务用途：它将卓鉴的应用登记与原行业系统的运行租户、本地权限应用标识关联起来。它不是认证凭据，也不是用户和机构的接口下发地址。本次去掉独立页签，在“概览”下增加默认折叠的“应用连接信息”，保留用途说明、已有标识、核验状态及原权限控制下的核验入口。公安原应用登记 ID、运行关联及本地权限标识保留，未重新绑定或迁移业务库。

## 登录错误及启动检查

故障时启动日志显示，读取控制库 `baseline.api_file_t` 超时，Magic 资源没有完成注册。Spring 已启动、8088 已监听时，请求仍可能落到静态资源处理器，于是 `/portal/login` 返回 `No static resource portal/login`。这次故障同时影响卓鉴的 Magic 登录接口。

`DmCompatibleDatabaseResource` 增加有限重试：仅对连接、读取等临时资源访问故障最多尝试三次，重试间隔为 1 秒和 2 秒；SQL 或表结构错误不重试。全部读取成功后才替换缓存，失败时保留上一次完整资源内容，最终失败仍向 Magic 资源服务报告错误。没有改写租户登录业务逻辑，也没有新增登录旁路。

`start-data-elements.ps1` 增加了启动就绪检查：分别以空参数请求租户登录和卓鉴登录接口，只有二者均返回正常的参数校验错误（400）才显示“Backend ready”。默认启动期限为 300 秒，可通过 `StartupTimeoutSeconds` 指定；若期限内仍未加载，脚本明确提示检查控制库连接和 Magic 资源日志，停止自己启动的进程并以失败状态退出。端口监听或 Spring 的 `Started` 日志不能单独作为启动成功依据。

验收期间观察到控制库、Redis 连接抖动及请求等待较长；资源热加载期间也有短暂的路由重新注册窗口。首轮真实页面验收中，两次登录等待超过 60 秒测试限制，另一次完成了真实页面检查；一次冷启动因资源读取失败被启动检查停止。最终使用修复后的正常启动入口完成冷启动，15 项真实接口检查全部通过。真实页面验收在 390、1440、1920 三个宽度全部通过，每个用例耗时约 11～12 秒，共保留 9 张实际页面截图。真实页面登录等待上限为 120 秒。历史失败记录保留，不把等待上限增加或单次通过描述为数据库、Redis 网络波动已消除。

## Magic 目录读取优化

原目录列表为每个机构重复查询同一套扩展字段定义，113 个机构会产生 113 次定义读取；本次改为对已获授权且在当前页内的对象批量读取扩展字段，共享一次定义查询。

变更仅涉及 `13.统一身份管理` 的两个函数：`@/idaas/directory`、`@/idaas/field-values`。先完成管理范围过滤、再分页、最后生成返回资料；敏感字段继续显示掩码，未定义字段不返回。该优化没有引入跨请求的权限或字段缓存，后续请求及写入仍重新读取定义并执行原有验证。

增量发布限定上述两个函数，发布前保留私有备份，并通过比较原内容再更新；保留已有资源 ID、元数据及其他接口。本次没有新增 HTTP 接口，没有增加或修改业务表、字段，没有修改公安等租户业务资料。Java 运行期变更仅为 Magic 资源加载的框架层重试；包内只替换这一个框架类，保留原有依赖、其他类及配置，并保存原包私有备份。业务规则仍在 Magic API 中。
