# 手动下发隔离验收（2026-10-05）

## 范围与结论

当前只有源数据管理平台（公安）、广电和海渔租户可用，没有独立的行业测试应用和真实接收端。本轮在现有服务上创建了随机标识、未绑定任何租户数据库的临时 QA 应用，接收端是只监听本机回环地址的内存实现。验收结束后，按随机 QA 标识清理了数据。此结果证明中央 Magic 的手动下发协议链路可运行，不代表三个行业接收端已经完成联调。

验收前后均核对公安、广电、海渔、澄天四个应用：`auth_mode=LOCAL`、`provisioning_mode=OFF`，原有接收配置快照相同。四个应用未被启用下发，也没有向行业租户库写入验收数据。服务健康检查为 `UP`，7 个与手动下发相关的运行中 Magic 资源和仓库中的资源源码一致。

## 已执行的真实 HTTP 链路

使用 [`verify_idaas_manual_downlink.py`](../../data-elements/scripts/verify_idaas_manual_downlink.py) 的 `--run-isolated` 模式，通过运行中的 Magic 接口执行以下步骤：

1. 为临时 QA 应用保存关闭状态的接收配置，向回环接收端发送带签名的 PING，验证签名回执，再启用该 QA 配置。
2. 先把一个已分配人员 ID 和一个未分配的随机 ID 放入同一批请求，确认整体被拒绝，接收端没有业务事件；再人工创建一个含机构和人员的有效下发任务。创建时接收端仍只看到 PING。
3. 人工执行任务。接收端故意让首个人员事件失败，任务保持部分失败；等待期间没有自动重试。
4. 人工调用重试、再次执行，确认人员回执成功且尝试次数为 2。
5. 再建完整任务，接收端对相同版本返回可验证的 `DUPLICATE` 回执；随后创建 DELTA 任务，确认未变化对象产生 0 个下发项。

接收端实际看到的事件类型依次为 `PING, ORG, SUBJECT, ORG, SUBJECT`。脚本执行结果为 `cleaned=true`；清理后再次检查临时应用、配置、任务、任务项、关联、人员、机构和审计等 QA 记录为 0。前后快照相同，四个原应用均为 LOCAL/OFF、原应用接收配置数为 0。私有运行证据保存在 `C:\Users\Administrator\.codex\private\idaas-manual-downlink\run-20261005-004148-ee2caf`，其中不应复制到仓库的凭据只从执行环境读取。

默认运行脚本只做只读预检；`--run-isolated` 需要明确提供平台操作账号及控制库凭据，并生成单次随机 QA 标识。异常中断时可用该次私有目录下的 `owned.json` 配合 `--cleanup` 清理，仅匹配本次 QA 标识。

## 页面与权限边界

“同步对象”页仅列出 `enabled=true` 且 `lastTestResult=SUCCESS` 的配置，没有合格配置时禁用下发按钮。浏览器契约测试验证未启用或未测试成功的配置不会发出 `provision/create` 请求；构造 20 行和 100 行人员资料时，开发模式下都只向 `configs`、`tasks`、`options` 三类接口各请求两次（React 开发模式重复挂载），合计 6 次，没有逐行补查。后端仍由 `sync:write` 与应用管理范围守卫把关，且在创建任务时核验所选人员是否属于该应用分配，所选机构是否属于分配范围；本次真实 HTTP 验收已用“有效 ID + 未分配 ID”同批请求验证整批拒绝。不能将页面禁用视作服务端鉴权。

本轮没有新增生产批量读接口，也没有修改 `provision-create.ms` 的 SQL。其现有实现仍在人员、角色和事件遍历中执行逐项 SQL 或辅助查询，尚不满足仓库要求的 20/100 项 SQL 数不随项数线性增长证据；因此**本记录不宣称批量性能验收通过**。如需规模化下发，应先将这些查询改为按应用批量预取并实测 20/100 项 SQL 数，同时复核每个 ID 的应用及角色范围。四个行业接收端的真实联调仍需各租户提供可用接收地址和密钥后单独验收。
