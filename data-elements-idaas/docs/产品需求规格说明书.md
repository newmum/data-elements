# 02　产品定位、范围与角色

## 2.1 产品定位

卓鉴统一身份管理平台为业务应用提供统一账户管理、统一身份认证、统一授权管理、统一应用管理、统一审计管理，即原方案的5A能力；同步管理负责机构和用户身份数据向应用流转。目标是形成权威身份信息源，减少多头维护，并使登录、授权、变更和追溯形成闭环。

依据：原方案§4.5—4.7，附件第21—23页。原方案第18页总体业务框架图同时表达用户、认证、权限、应用、同步、审计六个中心；本文将“5A能力”和“六个支撑中心”区分，不将两者混为同一分类。

## 2.2 产品边界

| 产品面 | 使用对象 | 本次覆盖 | 不默认包含 |
| --- | --- | --- | --- |
| 政企侧统一认证中心 | 政企办公人员、管理人员、接入应用 | 登录、组合认证、密码服务、单点登录和退出 | 面向内部员工开放自助注册；原文未要求 |
| 政企侧管理平台 | 获得平台管理权限的人员 | 总览、应用、组织用户、授权、同步、审计、系统设置、个人中心 | 各业务系统实际业务数据的查询和处理 |
| 公众侧统一认证中心 | 自然人、法人账户使用者 | 注册、登录、密码服务、单点登录、第三方登录适配 | 未接入实名服务时自动判定实名通过 |
| 公众侧管理平台 | 公众侧管理人员 | 概览、应用、自然人、法人、统计、日志、角色成员、安全设置 | 将政企侧全部组织、同步、权限组功能无条件复制过去 |
| 集成服务 | 上下游身份平台、第三方应用、认证供应商 | 标准认证、授权校验、身份查询、同步、日志及适配接口 | 保证所有遗留系统无需改造即可接入 |

原方案明确区分政府侧与公众侧，本文将“政府侧”在页面名称中表述为“政企侧”，业务内容不缩减。两侧可以共享前端工程和基础组件，但身份域、管理权限、数据查询及客户端注册边界必须显式区分。是否物理分库、分实例部署属于C。

## 2.3 角色及管理边界

| 角色 | 可执行工作 | 必须限制的边界 |
| --- | --- | --- |
| 平台管理人员 | 维护被授予的系统功能、机构范围、应用范围 | 管理权限由系统角色授予；不是天然可访问所有业务应用 |
| 分级管理员 | 管理指定区划或单位的机构、人员；在允许时向下委派 | 子级范围不得超过上级授权；不可扩展到兄弟或上级机构 |
| 应用管理人员 | 维护指定应用配置、角色、资源及用户 | 不得管理未授权应用，不得因此获得平台管理员管理权 |
| 审计人员 | 在授权范围内查询登录、操作、API及统计信息 | 审计查看权与业务编辑权分离；日志不提供直接修改入口 |
| 政企普通用户 | 认证、改密、访问已授权应用 | 不因拥有统一账号而获得管理后台入口 |
| 公众侧管理人员 | 在公众域维护自然人、法人及应用 | 不自动获得政企域数据或权限 |
| 自然人、法人账户使用者 | 注册、认证和使用已授权的公众服务 | 注册成功不等于实名核验通过，也不等于具有法人代表资格 |
| 应用机器身份 | 在授权范围调用接口、接收同步 | 与自然人用户身份分开，不能用应用密钥模拟管理员登录 |

依据：原方案§3.2、§5.2.4.1.3、§5.2.8.1、§5.3—5.4。应用管理、审计等为本文建议的职责拆分，可通过自定义系统角色组合实现，不强制写死为不可修改角色。

## 2.4 不做的内容

本平台不管理业务数据库中的表、字段、行级数据访问策略，不提供元数据平台业务操作界面；可登记其应用、角色、菜单及按钮权限，并由业务系统执行相应鉴权。人员资源管理不扩展为薪酬、考勤、招聘系统。统计不扩展为通用商业智能平台。原方案提到上游平台及认证厂商集成，本文只规定接入边界，不宣称相关服务已经购买、连通或通过认证。

# 03　总体架构与业务闭环

## 3.1 逻辑架构

沿用原方案第18—21页的三条集成链路：上游权威身份源向本平台提供身份信息；本平台向下游应用或下级身份平台提供数据同步和认证服务；短信、CA/RA、人脸、微信、支付宝等提供相应认证能力。下级平台上报数据按接口合同接收，不等同于允许任意应用改写权威身份。

管理端负责“配置和查看”，认证中心负责“核验和建立会话”，业务应用负责“使用身份和执行业务权限”，同步服务负责“分发变更并记录结果”。不能用管理页面的状态切换替代后端实际生效。

| 中心 | 核心对象 | 对外结果 |
| --- | --- | --- |
| 用户中心 | 用户、机构、任职、条线、自然人、法人 | 唯一身份标识、归属、状态和受控属性 |
| 认证中心 | 登录事务、认证方式、会话、令牌 | 认证结果、单点登录、退出结果 |
| 应用中心 | 应用、客户端、环境、接入配置 | 接入登记、配置版本、连通验证结果 |
| 权限中心 | 角色、资源、授权关系、权限组、API权限 | 有效权限及其来源、作用域和生效状态 |
| 同步中心 | 目标配置、待办队列、同步任务、实体记录 | 分发状态、错误原因、重试结果 |
| 审计中心 | 登录事件、操作事件、API事件 | 可检索证据、趋势和追溯链路 |

## 3.2 应用接入闭环

创建应用草稿 → 配置基本信息和环境 → 选择接入方式 → 配置回调地址及凭据 → 接入测试 → 登记资源和角色 → 配置用户/机构同步范围 → 授权用户 → 验证登录及权限 → 启用应用。

接入测试与应用启用分离。测试通过只能证明已测试的链路，不能证明全部角色和接口均正确。启用前至少确认回调校验、未授权用户拒绝、禁用账号拒绝、退出或令牌失效策略。测试失败保留草稿，不生成“已上线”状态。

## 3.3 人员全生命周期闭环

创建或接收上游用户 → 指定主职与其他任职 → 赋予应用访问资格和角色 → 同步身份数据 → 记录授权和同步结果 → 任职变更触发履历及权限重算 → 停用时阻断认证并回收会话 → 按下游能力同步停用 → 保留历史审计。

用户、任职和授权是独立对象。调动不应创建第二个用户；同一人在不同机构的排序随任职保存。上游权威字段默认只读并显示来源，本地扩展字段可按权限编辑。确需本地覆盖上游字段时应另定治理规则，不能静默覆盖。

## 3.4 授权与回收闭环

选择授权视角 → 选择对象和目标应用/角色 → 查看已有来源 → 编辑新增或移除项 → 预览新增、失去和仍保留的有效权限 → 后端校验范围与版本 → 提交 → 显示权限版本及下游传播结果 → 记录审计。

“应用授权”“用户授权”“机构授权”是同一授权关系的不同视角，不维护三套相互独立的数据。移除一种来源后，仍通过其他来源持有的权限继续有效，页面必须解释原因。

## 3.5 同步失败恢复闭环

变更形成任务 → 按目标应用与依赖顺序入队 → 发送 → 接收确认 → 记录实体成功或失败 → 管理员查看脱敏原因 → 修正配置或数据 → 仅重试失败项 → 保留前后两次执行记录。

中止任务仅阻止尚未执行的项目，不自动回滚已成功的下游修改。取消队列中的任务不删除历史证据。以上是对原方案“中止并移除”的实施细化。

## 3.6 公众注册与管理闭环

选择自然人或法人注册 → 填写对应信息 → 验证联系方式及必要声明 → 提交 → 创建注册账户 → 按已接入能力完成实名或关系核验 → 返回原业务应用或结果页 → 管理后台查看信息与日志。

“注册状态”“账号启停状态”“实名核验状态”“法人关联关系状态”分别存储和展示。原方案未给出完整实名审核、法人代表核验或子账号创建流程，本文保留展示与适配要求，相关扩展在确认供应商和业务规则后实施。

# 05　统一设计规范与交互规范

## 5.1 设计目标及实施边界

UI-01：整体呈现浅色、清晰、克制的企业级管理系统。白色内容容器置于浅灰页面底色；主色使用Ant Design默认蓝色体系；主要依靠文字层级、空间、分组和状态表达重要性。禁止将身份管理后台设计成霓虹大屏、重渐变展示站或大量装饰卡片的营销页面。

UI-02：Ant Design提供设计语言、主题机制及组件行为，并不规定本项目每个侧栏必须多少像素。下文侧栏宽度、页面留白、表单列数等是遵循其原则选择的项目统一规格，而非假称官方强制值。未被本文覆盖的基础控件细节以当前稳定版Ant Design官方组件文档为准。

设计依据：[Ant Design布局](https://ant.design/docs/spec/layout/)、[字体规范](https://ant.design/docs/spec/font/)、[主题定制](https://ant.design/docs/react/customize-theme/)。这些依据用于基础体系；本项目具体排版和业务交互按以下UI编号验收。

## 5.5 列表、查询与批量操作

UI-08：默认筛选区最多两行；高频条件展开，低频条件放“展开筛选”。文本输入回车触发查询；下拉变更后统一由“查询”执行，除非页面明确采用即时筛选并全页一致。重置恢复页面默认条件和第一页，不清除系统限定的管理范围。

UI-09：表格文本左对齐，数量和金额类数值右对齐，日期时间格式一致；状态列用文字+Tag/Badge。名称过长显示省略及可访问的完整信息，不截断唯一标识的可复制内容。空值使用“—”，真实0显示“0”；未获取成功不能显示0冒充正常。

UI-10：业务名称可进入详情；操作列最多展示两个高频文本动作，其他进入Dropdown。危险操作不与“查看”使用同一含义的图标。操作列使用当前版固定列能力，不通过绝对定位覆盖数据。

UI-11：分页默认20条，可选20/50/100，为项目建议。分页、筛选、排序由服务端完成；计数限定在用户可见范围内。返回列表恢复搜索条件和页码；数据删除导致当前页为空时回退至最后有效页。

UI-12：批量操作明确“已选N项”。允许跨页选择时必须持久化所选ID并明确跨页；更换身份域、应用或筛选条件时清空选择并提示。不把“全选本页”解释为全部结果；批量提交前显示数量、目标和不可操作项，部分失败显示逐项原因及重试入口。

## 5.6 表单与编辑规则

UI-13：普通编辑使用垂直标签Form布局；短字段可双列，说明、URL、复杂选择占整行。必填项统一标识，提示放在字段下方或Tooltip，不用占位符代替标签。相同字段在创建、编辑和筛选中使用同一名称。

UI-14：字段校验分为即时格式校验、提交前校验和服务端业务校验。错误紧邻对应字段；首次提交错误滚动并聚焦首个错误。唯一性校验以保存时服务端结果为准，异步预校验不是最终通过证明。保存失败保留非敏感输入。

UI-15：每个动作区域只保留一个主要动作。例如列表工具栏主按钮为“新建应用”，筛选区可有独立“查询”动作，不机械禁止两个区域各自拥有主动作。抽屉/弹窗页脚统一“取消”和“保存”；危险操作使用明确动词，不只写“确定”。

UI-16：有未保存改动时，返回、切换页签或关闭抽屉需询问是否放弃。保存按钮请求中进入loading并防重复提交。并发编辑返回版本冲突时，提示“内容已被其他管理员更新，请刷新后重新修改”，不覆盖他人结果。

## 5.7 抽屉、弹窗与提示

使用Drawer完成保留列表上下文的编辑/详情；跨应用、大量对象和多步授权使用独立页面。Modal用于短表单、确认和结果，不把长资源树塞进窄弹窗。不连续叠加两个业务抽屉，确需二次选择时采用选择弹窗且能清楚返回。

UI-17：轻量成功反馈用message；需要持续关注或跳转的异步任务结果用notification；页面内持续问题用Alert；阻断访问或完整结果用Result。错误不得同时以message、Modal和Alert重复轰炸。

UI-18：主题上下文通过ConfigProvider → Ant Design App传递；业务反馈使用App.useApp()取得message/modal/notification。Drawer采用当前size接口，销毁隐藏内容使用destroyOnHidden等当前API，不抄用旧版宽高或样式属性。依据：[Ant Design App](https://ant.design/components/app/)、[Drawer](https://ant.design/components/drawer/)、[Modal](https://ant.design/components/modal/)。

## 5.8 加载、空态和异常状态

| 状态 | 展示要求 | 可执行动作 |
| --- | --- | --- |
| 页面首次加载 | 保留导航与标题，内容区域Skeleton | 不用整屏反复闪烁的“加载授权资料”遮罩 |
| 表格刷新 | 保留原表结构，Table loading | 请求期间避免重复提交；已显示数据注明刷新状态 |
| 无业务数据 | Empty说明尚未创建何种对象 | 有创建权时提供相应入口，无权时不展示 |
| 查询无结果 | “未找到符合条件的结果” | 重置筛选，不暗示系统没有任何数据 |
| 接口失败 | 可理解原因+请求追踪号 | 重试；不显示堆栈、密钥或数据库错误 |
| 无权限 | 403及“当前账号无此页面访问权限” | 返回有权限页面，不显示越权对象信息 |
| 登录过期 | 保存安全的返回路径，进入登录 | 重登后恢复路径；不恢复密码、验证码 |
| 数据已删除 | 明确对象不存在或已不可访问 | 返回列表；不继续用旧缓存编辑 |
| 任务部分成功 | 成功/失败/未处理数量分开显示 | 查看明细、仅重试失败项 |
| 外部服务未配置 | 显示“未配置/暂不可用”及管理员处理入口 | 不提供看似成功的扫码或人脸结果 |

## 5.9 响应式、可访问性与文案

UI-19：管理端以1280×720、1440×900、1920×1080作为项目验收视口；公众认证页额外验证375px、390px和768px宽度。小屏认证表单单列，验证码按钮与输入框不互相遮挡。宽表格在表格容器内滚动，不能导致整页横向溢出。

UI-20：所有主要动作可用键盘完成，焦点可见；打开浮层后焦点进入浮层，关闭后返回触发位置。图标按钮有可读名称；表单错误关联到字段；状态同时使用文字。正文及关键标签对比度作为专项检查项，不以“用了Ant Design”代替测试。

UI-21：界面使用完整、具体的动词短语。例如“停用用户”“撤销应用访问权限”“重试失败项”。显示后台任务时写“任务已提交”，不能写“同步成功”。删除、禁用、移除关系、撤销授权分别表达，不混用。

UI-22：视觉验收必须检查长名称、200%缩放、无数据、大量数据、错误、加载、禁用及无权限状态。所有截图使用同一设计基线；项目自有样式的偏差容限为布局位置与间距不超过2px，原生组件内部渲染差异不通过强改CSS消除。

# 06　政企侧统一身份认证中心

本章对应原方案§5.1及§5.2.1，附件第26—29页。原方案明确提供统一登录页、登录接口、单点登录、密码管理和管理后台登录。以下页面字段、状态与校验为D；协议变更为T，见第12章。

## 6.1 A01｜统一登录与管理端登录

**目标与入口：** 用户从业务应用发起登录，或访问管理端后跳转至认证中心。两种入口复用视觉组件，但认证事务必须携带并校验不同的目标应用和身份域。管理端登录成功后仍需检查管理权限，普通用户不得进入后台。

**页面布局：** 桌面可采用左侧品牌说明、右侧登录卡片；背景简洁，不放无关数据可视化。登录卡建议宽400px，内边距32px；移动端隐藏大面积品牌说明。顶部显示系统名称，下方显示“正在登录：已登记应用名称”，应用名称由服务端返回，不能相信URL自由文本。账号密码、短信等方式用Tabs，CA、人脸等仅在已配置且适用于本应用时显示。

| 字段/控件 | 类型与必填 | 默认与校验 | 安全要求 |
| --- | --- | --- | --- |
| 账号 | Input，账号方式必填 | 去除首尾空白；长度按账户策略 | 错误不区分账号不存在或密码错误 |
| 密码 | Input.Password，账号方式必填 | 不自动去除空格；不在日志记录 | 允许密码管理器填充；不默认勾选长期登录 |
| 手机号 | 区号+Input，短信方式必填 | 根据已支持地区规则校验 | 发码接口防枚举与限流 |
| 验证码 | Input，短信方式必填 | 长度、有效期、重发间隔由服务端策略返回 | 单次有效；倒计时只是交互，不替代服务端限制 |
| 登录按钮 | 主按钮 | 表单提交时loading | 同一认证事务重复提交由服务端去重 |
| 忘记密码 | 文本链接 | 跳转A03并保留安全的返回上下文 | 不携带密码或验证码 |
| 第三方认证入口 | 图标+名称 | 仅显示已启用且可用的方式 | 不把模拟认证作为生产结果 |

**处理流程：** 校验表单 → 建立/延续认证事务 → 服务端核验账号状态与凭据 → 需要额外认证时进入A02 → 需要强制改密时进入A04 → 校验目标应用访问资格 → 建立合法会话 → 进入已登记回调链路或管理首页。

**状态：** 密码错误显示“账号或密码不正确”；被锁定显示可公开的解锁方式或等待时间；停用账号显示联系管理员提示；无管理权限显示“当前账号没有管理平台访问权限”；网络故障可重试。错误时不清空账号，按策略清空密码。验证码过期重新获取，不沿用过期事务。

**验收：** AC-A01-1，有业务应用权限但无后台权限的用户，无法访问管理路由及其API。AC-A01-2，未登记回调地址被拒绝。AC-A01-3，刷新页面不会跳过MFA或首次改密。AC-A01-4，连续错误触发后端锁定策略，修改前端倒计时无法绕过限制。

## 6.2 A02｜多因子认证

原方案支持按应用组合多种认证方式，但未明确组合语法。本文建议以“主认证方式+必须完成的附加校验”表达，不将两个可替代的单因子登录入口误称为多因子认证。

页面使用步骤说明、脱敏目标、当前验证表单和“更换验证方式”入口。只展示该账号已绑定且符合策略的备用方式；不得因为短信或人脸服务失败而自动降级为更弱方式。每次验证绑定用户、客户端和认证事务，验证结果不能复用于另一应用事务。

| 条件 | 处理 | 用户反馈 |
| --- | --- | --- |
| 已具备策略所需的验证要素 | 正常进入验证步骤 | 显示验证方式与脱敏接收对象 |
| 未绑定必要方式 | 阻断并进入受控绑定/联系管理员流程 | 不要求用户随意填一个新手机号完成绑定 |
| 外部服务超时 | 保留事务可用期限，提供重试或合规备用方式 | 明确未完成认证，不显示登录成功 |
| 认证事务过期 | 返回A01重建事务 | 解释“验证已过期，请重新登录” |

**验收：** AC-A02-1，删除或修改前端步骤参数不能绕过剩余认证。AC-A02-2，验证码不能跨用户、跨事务使用。AC-A02-3，供应商错误不会被映射为验证通过。

## 6.3 A03｜忘记密码

采用Steps三步：确认账号 → 验证身份 → 设置新密码；完成后Result提示返回登录。账号不存在时使用不泄露存在性的统一反馈。身份验证仅使用已绑定的验证方式或已确定的人工流程；不提供任意填手机号接收重置验证码的路径。

新密码与确认密码为必填Input.Password，强度要求根据后端策略动态展示；即时显示满足项，不以单一颜色进度条代替说明。密码重置成功后按安全策略撤销既有会话并通知用户；页面说明“请使用新密码重新登录”。未接入短信等找回通道时显示管理员联系方式或受控申请方式，不能显示空壳发码入口。

**验收：** AC-A03-1，重置凭据一次使用后失效。AC-A03-2，两个新密码不一致不能提交。AC-A03-3，新密码在网络请求之外不写入前端缓存、埋点或日志。AC-A03-4，找回操作不把停用账号重新启用。

## 6.4 A04｜修改密码与强制改密

普通改密要求当前密码、新密码和确认密码；首次登录、初始密码或策略到期触发强制改密时，根据服务端的有限认证态执行。强制改密完成前，有限认证态只能访问改密及必要验证接口，不能调用业务接口。

页面以Alert解释原因，例如“你正在使用初始密码，请修改后继续”。密码规则不在各页面硬编码，统一读取当前策略。修改成功后是否继续当前认证事务由后端策略确定，其他会话回收规则应明确并写入审计。

**验收：** AC-A04-1，直接跳转业务路由不能绕过强制改密。AC-A04-2，密码策略变更后，登录、改密和后台重置三个路径执行同一有效策略。

## 6.5 A05｜单点登录、回调与单点退出结果

SSO过程通常无需额外操作页；需等待或失败时使用简洁状态页，不展示授权码或令牌。保持原方案“一处登录，访问有权应用”的目的，不能解释为免除应用授权。

统一退出分为平台会话终止和下游应用退出通知。前者成功后不得继续使用本平台会话；后者按接入能力记录待处理、成功、失败或不支持。结果页显示“已退出卓鉴统一身份管理平台”，必要时说明某些应用退出状态无法确认，禁止在未确认时宣称“所有应用均已退出”。

**接口要求：** 对外优先采用授权码+PKCE；需要标准身份声明时采用OIDC扩展。原方案中的第三方密码模式登录接口不作为新接入默认能力，见T-01。认证中心自身验证账号密码的接口不等于对外开放OAuth密码授权模式。

**验收：** AC-A05-1，授权码过期、重复使用或客户端不匹配时拒绝。AC-A05-2，无应用权限用户即便存在SSO会话也被拒绝。AC-A05-3，退出通知部分失败可追溯，不把失败状态伪装为全部成功。

## 7.4 G04｜应用角色管理

依据：原方案§5.2.3.2，附件第30页。

**验收：** AC-G05-1，无法构造循环树。AC-G05-2，导入失败行不会悄悄丢弃。AC-G05-3，隐藏菜单后仍直接调用业务API的请求必须由业务后端按权限拒绝，不能依赖前端隐藏。

| 账号启停状态 | Select | 与锁定状态分开；重置密码不得隐式启用 |
| 来源及扩展信息 | 只读来源+动态表单 | 上游权威字段按规则只读，扩展字段按权限编辑 |

**创建：** 填写信息和主职 → 校验账号唯一性 → 选择受控的初始凭据发放方式 → 保存 → 展示“继续授权应用/查看用户”。禁止所有新用户共用固定弱密码；初始密码策略和安全发放通道属于C，页面不展示永久可查询的初始密码。

**任职变更：** 新增、结束、调整或设置主职需填写变更原因；提交前展示机构与岗位变化及可能影响的继承授权。保存后自动生成历史记录，包含变化前后、操作者、时间和原因。历史任职不可被普通编辑覆盖。

**停用/删除：** 停用前提示影响登录、有效授权和同步；停用保留关系便于审计。删除采用受控归档/逻辑删除建议，已有关联和历史时不直接物理清除。存在未完成同步时显示后续传播状态。

**重置密码：** 仅具备对应权限者可操作，需确认目标；结果返回“重置已提交/已完成”与通知状态，不返回用户旧密码。不允许通过批量重置下载全员明文密码。

**验收：** AC-G09-1，主职变更不创建新的userId。AC-G09-2，不同任职节点可以设置不同排序。AC-G09-3，密码重置不解除停用状态。AC-G09-4，任职调整前后可以追溯且同步引用同一身份。

## 7.10 G10｜机构维护与批量导入

依据：原方案§5.2.4.1.2，附件第32页。

新增支持同级、子级和批量创建。表单字段：机构名称（必填2—100字符）、机构编码（必填且当前域唯一）、上级机构、行政区划、机构类型、排序、启停状态、条线、负责人及扩展属性。主字段为S能力的D细化，区划/类型的实际字典由项目确认。

机构移动采用选择目标上级并预览影响，不默认开放无确认的树拖拽。禁止移动到自身或后代；超出管理员范围、产生无效上级或破坏分级授权时拒绝。若涉及大量人员、继承条线、机构授权和同步范围变化，展示影响数量并记录变更任务。

删除机构前检查子机构、有效任职、分级管理员和授权引用。默认阻止带有效引用的删除，引导先迁移或结束关系。停用机构的建议规则为该节点有效状态向下约束，并触发相关任职资格与授权重算；跨其他有效机构的任职不因此全部失效，见BR-03。启用时不自动清除子节点自身的停用标记。

导入采用“模板 → 上传 → 校验预览 → 确认导入 → 结果”五步。用户、机构和资源共用导入任务组件，但各自校验规则独立。批量创建可用可编辑表格录入，仍执行同样唯一性和层级检查。

**验收：** AC-G10-1，移动不会形成循环机构。AC-G10-2，越级管理员不能移动越权节点。AC-G10-3，导入结果与实际创建/失败数量一致。AC-G10-4，机构停用不删除人员历史。

## 7.11 G11｜分级管理员

依据：原方案§5.2.4.1.3，附件第32页。

列表列：管理员姓名/账号、所属机构、管理范围、可用功能、可管理应用、是否可继续下放、上级委派人、状态、操作。筛选管理员、机构范围、状态。配置页依次选择用户、管理机构、包含下级、可委派功能/应用、是否允许再委派；显示授权上限和本次子范围。

服务端检查“可委派权限是当前有效管理权限的子集”，不能只看前端树是否禁用。授予再委派不等于授予平台所有授权管理权。撤销上级委派或缩小范围时，对其派生下级委派做重算并展示受影响管理员，不留下失去来源的悬挂权限。

**验收：** AC-G11-1，篡改请求选择上级或兄弟机构时拒绝。AC-G11-2，上级授权回收能使超出部分的下级授权失效。AC-G11-3，管理权限变化留有委派链和审计。

## 7.12 G12｜条线管理

依据：原方案§5.2.4.2，附件第33页。

列表包含条线名称、编码、说明、关联机构数、状态及操作；新增、编辑、删除、查询能力完整。机构可关联多个条线，在机构详情展示“本机构配置”和“上级继承”两组来源，并指明继承起点。

本文建议条线有效集合为上级有效条线与本机构配置条线的并集；原方案未描述屏蔽继承或覆盖规则，首版不自行添加“排除上级条线”能力。删除有引用的条线需先确认迁移策略。条线本身不自动授予应用权限，除非后续单独定义条线授权能力。

**验收：** AC-G12-1，上级条线变更能够更新下级有效条线。AC-G12-2，同一条线多个来源去重显示但保留来源解释。AC-G12-3，条线变化不误改手动应用授权。

## 7.13 G13—G14｜组织字典与扩展字段

依据：原方案§5.2.4.3与§5.2.3.5，附件第31、33页。

G13用Tabs区分职务、岗位、职级、职称；表格列为名称、编码、适用范围（通用/机构内部）、所属机构、排序、状态、操作。新增/编辑表单沿用统一模板；被任职引用的数据不可直接删除，允许停用以禁止新的选用，同时保留历史显示。

G14用对象类型切换用户、机构、应用、应用资源；字段列表包含显示名、字段编码、类型、必填、默认值、展示顺序、敏感级别、状态。支持文本、数字、日期、单选、多选、布尔等受控类型；不提供任意JavaScript表达式。新字段默认非必填；已有数据的字段改为必填前需检查历史缺值并明确补齐方案。

扩展字段编码在对象类型内唯一且稳定；已有数据后禁止直接修改类型或物理删除。敏感标记关联脱敏和加密策略，不因为出现在动态表单中就绕过字段级可见权限。字段长度、枚举项和默认值在前后端统一校验。

**验收：** AC-G13-1，停用岗位不破坏历史履历。AC-G14-1，扩展字段在创建、编辑、详情和导入中一致生效。AC-G14-2，敏感字段在无权账户的接口响应中不返回明文。

# 08　政企侧管理平台：授权、同步、审计与设置

## 8.1 G15｜应用授权

依据：原方案§5.2.5.1，附件第33—34页。入口为“授权管理 → 应用授权”，或应用详情中的“授权”。

页面顶部先选择应用；下方分“用户授权”和“机构授权”两类来源，不能将机构授权展开为无法追溯的一堆直接用户关系。中部左侧为待选对象，右侧为已授权对象与来源，底部呈现本次变更数量。授权对象规模较大时使用服务端搜索的Table，不一次性渲染数万条Transfer选项。

用户查询支持姓名、账号和机构；机构选择支持树搜索，并明确“仅本机构/包含下级”。新增授权只建立应用访问资格；需要应用角色时提供独立角色选择，并注明角色由当前应用定义。保存前显示新增授权、取消直接授权、受机构规则覆盖人数及仍通过其他来源有效的人数。

取消授权只删除所选关系。若用户仍有机构/权限组来源，结果显示“已移除该来源；用户仍可通过××权限组访问”，而不是笼统“已撤销全部访问”。后端最终鉴权状态与下游传播状态分别显示。

**验收：** AC-G15-1，应用视角保存后，用户视角即时读取到同一关系。AC-G15-2，机构授权明确包含下级规则且可追溯。AC-G15-3，移除单一来源不会误删其他来源。

## 8.2 G16｜用户授权

依据：原方案§5.2.5.2，附件第34页。

顶部使用可搜索用户选择器，显示姓名、账号、主职机构和账号状态。下面按应用列出访问资格、角色、来源、有效状态和操作；可筛选“已授权/未授权/全部可见”。多个应用批量授权时，每个应用的角色独立选择，不把同名角色当成跨应用同一角色。

详情抽屉展示某一应用的完整来源链：直接授权、机构及包含下级规则、权限组、角色来源、有效时间和最近变更。显示“无效原因”，例如账号停用、角色停用、应用停用或来源过期；“有授权记录”和“当前可访问”不能用同一个勾选框含糊表达。

**验收：** AC-G16-1，账号停用但保留授权记录时，页面显示不可访问原因。AC-G16-2，跨应用批量保存逐应用返回结果，部分失败可单独修正。AC-G16-3，来源详情能够解释有效权限。

## 8.3 G17｜机构授权

依据：原方案§5.2.5.3，附件第34页。

采用左树右表，左侧选择机构，右侧显示应用、包含下级、授权状态、影响人数、配置人和更新时间。新增时选应用和是否包含下级；默认仅本机构，避免无提示扩大到整个组织树。

原文未明确授权是“快照复制给当前用户”还是“随机构成员变化动态生效”。本文建议采用动态关系：有效任职进入范围时获得该来源，离开范围后失去该来源；不把当前人数保存为固定授权名单。变更时展示影响预估，保存时由后端重新计算。

一人多岗按全部有效任职判断机构来源；仅结束其中一个任职不能直接撤销其其他机构来源。机构移动导致范围变化时重新计算权限并记录触发原因。

**验收：** AC-G17-1，新加入机构的用户按规则获得来源，调出后失去该来源。AC-G17-2，多岗人员仍在另一授权范围内时保持相应访问。AC-G17-3，“包含下级”关闭后能准确预览受影响人员。

## 8.4 G18｜权限组

依据：原方案§5.2.5.4，附件第34页。

列表筛选名称、编码、状态；列为权限组名称、编码、应用数、角色数、用户数、更新时间、操作。新建/详情使用三个页签：基本信息、应用与角色、关联用户。基本字段为名称、编码、说明；启停、有效期为D细化，不强制补充审批流。

“应用与角色”按应用分组，先选择应用，再勾选其角色；“关联用户”支持搜索和批量选择，显示人员身份而非只显示重名姓名。保存前预览影响：组内新增/移除的应用、角色和用户数。权限组更改同步作用于其成员，通过版本化关系表达，不为每位成员复制一套不可追溯配置。

删除或停用组只移除该组贡献的权限，直接授权及其他组仍有效。“关联用户汇总”可按组、用户、应用查询，满足原方案要求的统一掌握授权情况。

**验收：** AC-G18-1，一个组可组合多套应用及各自角色。AC-G18-2，组成员变更可追溯到组版本。AC-G18-3，删除组不误删用户及其他来源。

## 8.5 G19—G20｜API授权应用与API授权用户

依据：原方案§5.2.5.5—5.2.5.6，附件第35页。

保留两个业务入口，分别面向应用机器身份和用户身份；组件可以复用，但授权主体类型必须显式显示。左侧选主体，右侧为平台开放API目录及已授予API。目录字段为API名称、稳定权限标识、所属模块、用途、数据范围要求、敏感级别、授权状态；接口HTTP路径仅作技术说明，不作为唯一权限标识。

授权表单包括主体、API集合、可访问数据范围；有效期和用途为D建议字段。平台提供新增授权、查询已授权API、删除授权。应用调用还必须具备有效机器凭据；用户调用必须具备有效用户认证态，不因为列表里勾选了API就允许匿名请求。

**规则：** 授予API访问资格不自动授予无限数据范围；请求权限是主体有效权限与授权范围的交集。应用环境变更不复用另一环境凭据。权限列表不得把“后台管理员管理”等高危接口默认全部勾选。撤销后按照第10章的权限版本与失效机制生效。

**验收：** AC-G19-1，有效凭据但未授权的API返回403。AC-G19-2，授权查询机构A的应用不能查询机构B。AC-G20-1，用户API授权不自动生成平台菜单权限。AC-G20-2，撤销记录保留审计且后续访问被拒绝。

## 8.7 G22—G23｜同步用户与同步机构

依据：原方案§5.2.6.1.2—5.2.6.1.3，附件第36页。

两个页签共用目标应用选择、关键词、同步状态、时间筛选。用户列：姓名、账号、机构、源版本、最近同步版本、状态、最近时间、失败原因、操作。机构列：名称、编码、上级、源版本、最近同步版本、状态、时间、原因、操作。

顶部动作“全量同步”“同步所选”“重试失败项”。全量同步要求确认对象总数、范围和目标，不等于删除后重建；实际语义由接口合同确定。只显示在有效同步范围内或已有历史同步关系的对象；后者应标明“已移出范围”，避免完全消失造成无法追踪。

状态建议为待同步、同步中、成功、失败、已跳过、已移出范围。源数据更新后不能继续显示旧版本“成功”而不提示有待同步变更。提交后显示任务ID并跳转G24，不能在排队阶段提示成功。

**验收：** AC-G22-1，重复点击只形成一个幂等提交。AC-G22-2，成功版本落后源版本时可识别。AC-G23-1，机构同步确保上级依赖满足后再处理子级。AC-G23-2，批量失败项可以逐条定位。

## 8.8 G24—G25｜同步任务与同步记录

依据：原方案§5.2.6.2，附件第36—37页。

G24列表列：任务ID、目标应用、对象类型、触发方式、创建人、总数、成功/失败/未处理数、任务状态、创建/结束时间、操作。筛选为应用、对象类型、状态、时间、任务ID。详情头部展示进度和统计，下面是逐实体处理记录。

| 任务状态 | 可执行动作 | 界面说明 |
| --- | --- | --- |
| 排队中 | 查看、取消 | 尚未处理；取消不改动下游 |
| 执行中 | 查看、请求中止 | 已成功项不会自动回滚，中止需执行器确认 |
| 中止中 | 查看 | 不显示“已中止”，直到未执行项被停止 |

| 已中止/已取消 | 查看 | 保留已执行记录与未处理数量，不删除审计 |

G25同步记录可从任务、用户或机构进入；字段包括事件ID、任务ID、目标、实体ID/名称、操作类型、源版本、发送时间、耗时、响应结果、错误码、脱敏原因、重试关联。禁止展示含密码、密钥、完整证件等的原始请求体。

队列至少保持同一对象的版本顺序以及机构先于关联用户的依赖顺序；新的停用事件不能被重试的旧启用事件覆盖。原方案强调按队列顺序执行，任何并行优化不得破坏此业务要求。

**验收：** AC-G24-1，中止与完成并发时，最终数量准确且只有一个终态。AC-G24-2，总数等于成功、失败、跳过和未处理之和。AC-G25-1，重试可回到原始失败记录。AC-G25-2，旧版本重试不能覆盖较新状态。

## 8.9 G26｜操作日志与API日志

依据：原方案§5.2.7.1，附件第37页。

页面Tabs区分后台操作和API调用，保留各自查询条件。操作日志筛选时间、操作者、模块、类型、目标、结果；API日志额外筛选调用主体、API标识、客户端和请求ID。默认最近7天，长时间范围采用异步查询/导出能力建议，由容量测试确定限制。

操作列字段为时间、操作者/主体类型、模块、动作、目标对象、结果、来源IP、请求ID。API列增加API名称、客户端、耗时、响应码。详情Drawer显示基本信息、变更前后差异、关联对象和关联事件；敏感字段差异只显示“已变更”或脱敏值。

日志查询、敏感日志查看及导出本身也记录审计。日志不可普通编辑或单条删除。导出属D补充效率能力，必须使用可见范围和脱敏策略，下载链接按时效和权限保护。

**验收：** AC-G26-1，应用密钥轮换、用户停用、授权修改均有记录。AC-G26-2，密码、验证码及令牌不出现在日志详情和导出。AC-G26-3，审计查询无权对象时不泄露目标名称。

## 8.10 G27｜登录日志

依据：原方案§5.2.7.3，附件第37页。

筛选时间、身份域、账号、目标应用、登录场景（后台/应用）、认证方式、结果。列为登录时间、账号/用户、应用、认证方式、结果、失败阶段、来源IP、设备摘要、认证事务ID。详情展示主认证、附加验证、应用授权检查、回调等阶段和脱敏原因。

成功登录、错误凭据、账号锁定、账号停用、MFA失败、应用无权、回调失败分开统计；不能把HTTP请求成功直接当作登录成功。登录日志用于还原事件，不显示用户输入的密码或完整认证数据。

**验收：** AC-G27-1，同一认证事务的多步骤可关联且不虚增成功次数。AC-G27-2，应用未授权和密码错误可在管理日志区分，在公开登录页维持必要的安全反馈。

## 8.11 G28｜统计分析

依据：原方案§5.2.7.2，附件第37页。

展示用户总数趋势、登录趋势、应用访问人数Top5、用户登录次数Top5。用户总数趋势需要历史快照或事件重建，不得用当前人数填满过去每一天。访问人数去重单位为身份域+userId；登录次数使用实际成功事件；无明确事件来源的“应用访问”应注明仅统计SSO登录访问，而非业务系统所有页面浏览。

筛选支持日期范围及可管理范围，图表可查看对应表格。排行并列时采用稳定的次排序规则；缺失数据与真实0分别表现。统计取数窗口和时区在页首展示。

**验收：** AC-G28-1，相同条件下统计与日志核对一致。AC-G28-2，缺少历史快照时显示数据起始时间，不伪造早期趋势。

## 8.12 G29—G30｜管理员与系统角色

依据：原方案§5.2.8.1，附件第38页。

G29管理哪些用户可以进入管理后台，列为姓名、账号、主职机构、系统角色、机构范围摘要、应用范围摘要、状态、最近登录、操作。新增管理员从现有有效用户选择并赋予系统角色；不重复创建一个与原身份无关的账号。支持一个人多个系统角色。

G30系统角色配置使用独立页面，分基本信息、功能权限、机构数据范围、应用管理范围、关联成员五部分。功能权限按菜单与动作呈现；具有菜单查看权不自动具备新增、导出或授权权。机构范围必须表示具体节点及是否包含下级；应用范围明确应用ID集合，不用含糊“全部权限”。

系统角色与G04的应用角色完全分开。拥有管理员角色不自动赋予业务应用访问资格；需要访问业务应用时仍按统一授权规则处理。为高敏场景启用“管理员身份禁止访问指定应用/禁止给自己授权”属于可选D策略，原方案未要求全面强制，需业务确认后实施，不能在本文悄悄替用户扩大隔离范围。

保存系统角色变更时预览受影响成员；禁止删除或停用最后一个有效平台恢复管理入口。自身敏感权限提升建议要求独立操作者或受控审批，实际双人规则见待确认项，而非假装已实现审批系统。

**验收：** AC-G29-1，普通用户不因存在于用户库就可进入后台。AC-G30-1，机构范围、功能范围、应用范围均由后端校验。AC-G30-2，系统角色不会出现在应用角色列表。AC-G30-3，最后一个有效管理入口不能被普通操作意外删除。

## 8.13 G31｜账号安全设置

依据：原方案§5.2.8.2，附件第38页。

采用四个表单分组：密码要求、改密策略、登录保护、恢复策略。页面显示当前生效版本、最近修改人、修改时间，保存前预览影响；已经发出的登录事务是否沿用旧策略由后端明确。

| 配置项 | 页面控件 | 行为要求 |
| --- | --- | --- |
| 密码长度/复杂度 | InputNumber、Checkbox | 显示取值范围和示例，不在多个页面各写一套正则 |
| 密码黑名单 | 上传/受控维护入口 | 只提供安全检查结果，不回显用户真实密码 |
| 首次登录强制改密 | Switch | 创建用户后按策略标记，不能仅在前端弹窗提示 |
| 使用初始密码强制改密 | Switch | 原方案要求能力；生产不得通过关闭策略保留已知弱凭据 |
| 定期改密及周期 | Switch、InputNumber | 保留原方案配置能力；实际默认周期由安全评审确定 |
| 连续失败阈值、锁定时间 | InputNumber | 账号与来源的限流策略由后端执行；不可无限试错 |
| 找回/重置后会话处理 | 受控选项 | D补充；默认建议撤销其他会话，准确显示传播状态 |

不在本文宣称某一固定密码长度或改密周期已满足全部法律标准。具体阈值必须由安全责任方确认；策略值在前端展示只是交互，后端所有入口都必须执行。

**验收：** AC-G31-1，直接调用接口也遵守策略。AC-G31-2，策略不能保存为负数、零有效期或互相矛盾配置。AC-G31-3，变更可审计且可追溯到版本。

## 8.14 G32｜单点登录设置

依据：原方案§5.2.8.2，附件第38页。

配置单点登录相关令牌有效期和单点退出开关，属于原方案能力。本文进一步将“认证会话时长、授权码时长、访问令牌时长、刷新令牌策略”分开显示，避免一个“Token有效期”被错误套用到所有对象。哪些令牌实际存在取决于已选协议，未启用的类型不出现无效配置。

生效说明明确对新发令牌和存量令牌的处理。缩短未来有效期不等于已发令牌立即作废；需立即回收时使用会话/令牌撤销机制。单点退出开关显示各应用支持情况和通知失败记录。凭据和时长的允许范围由认证服务返回。

**验收：** AC-G32-1，不同令牌类型具有独立约束。AC-G32-2，关闭下游退出通知不保留已经退出的平台会话。AC-G32-3，页面不承诺尚未具备的下游回收能力。

## 8.15 G33｜字段加密设置

依据：原方案§5.2.8.2，附件第38页。

S要求按敏感字段提供不同级别的国密算法加密配置。本文不从原文推断具体算法、密钥长度或认证资质；由安全技术方案给出可用的受审查加密配置。产品页面使用“加密配置名称/密钥版本引用”，不允许管理员任意输入算法名称并宣称安全。

列表列为对象类型、字段名称、敏感级别、存储保护状态、脱敏策略、密钥引用、迁移状态、操作。加密、前端脱敏与访问权限是三个不同维度，不能用星号遮罩替代后端保护。密码采用专门的安全密码存储机制，不进入可逆字段加密配置。

更改已有字段保护策略时先统计涉及记录并创建后台迁移任务，展示排队、执行、完成、失败；迁移未完成不能提示“全部数据已加密”。密钥本体不在普通页面展示、导出或写日志。

**验收：** AC-G33-1，脱敏权限不能通过前端取消遮罩获得无权明文。AC-G33-2，迁移失败可定位，旧数据保护情况明确。AC-G33-3，密钥与业务字段分开管理。

## 8.16 G34｜API访问限制

依据：原方案§5.2.8.2，附件第38页。保留异常业务系统IP黑名单能力；额外白名单策略并非原文要求，不默认列为已确定范围。

列表列为IP/网段、应用范围、原因、启停状态、创建人、创建时间、操作；新增表单校验IPv4、IPv6或支持的CIDR格式，是否支持网段属于D细化。保存前识别当前管理员或网关来源被误封风险，并要求明确确认。

源IP判定必须由可信代理链和服务端配置确定，不能信任任意客户端填写的X-Forwarded-For。黑名单仅是额外访问限制，不代替认证和API授权。失败提示不暴露整套安全规则。

**验收：** AC-G34-1，修改客户端伪造IP头不能绕过。AC-G34-2，被禁用的规则不生效但保留历史。AC-G34-3，批量重复规则可识别并避免重复创建。

## 8.17 G35｜系统名称与品牌设置

字段为系统名称、Logo、登录窗口名称/必要说明；显示当前配置和受控预览。Logo上传格式校验复用应用图标规则；预览覆盖展开/折叠导航与认证页，不允许长名称撑破布局。保存后按版本刷新，不要求用户清空全部浏览器缓存。

品牌配置只影响系统识别，不允许输入脚本、外部HTML和任意CSS。没有配置Logo时使用统一默认标识，不显示破损图片；名称中不得自动出现“演示”“Demo”等与生产用途不符的文案。

**验收：** AC-G35-1，配置长名称和透明Logo仍保持对齐。AC-G35-2，恶意文件和脚本内容被拒绝。AC-G35-3，两侧域配置关系按部署设计明确，不互相误覆盖。

## 8.18 G36｜账号解锁

列表展示账号、姓名、锁定原因、锁定时间、预计解锁时间、账号启停状态、最近失败次数、操作。支持关键词、原因和时间筛选。点击“解锁”弹出目标确认与原因输入；完成后只清除锁定状态，不更改密码、不重启已停用账号、不新建授权。

# 09　公众侧认证与管理平台

## 9.1 P01｜自然人、法人登录

依据：原方案§5.3.1—5.3.2，附件第39—40页。

沿用A01认证模板，但提供明确的自然人/法人身份入口，并支持PC和移动网页。账号密码、短信、已接入的人脸、支付宝、微信按当前身份类型和配置展示；缺失供应商时不展示可点击却永远成功的占位功能。

法人登录后显示正在使用的法人账户或经验证的代理关系，不把自然人的实名状态自动视为法人授权。注册入口分别指向P02/P03。第三方登录成功只说明该提供方返回了相应身份声明，是否建立本地账户和关联已有账户必须经过显式规则，不能仅凭相同姓名合并。

原文中的对外密码模式登录接口按第12章现代化处理；公众侧与政企侧的会话、client_id、令牌受众分开。是否允许同一自然人作为政企用户建立关联，是C项，不因手机号相同自动归并。

**验收：** AC-P01-1，自然人和法人入口不会混用账号资料。AC-P01-2，扫码取消、过期、供应商异常分别反馈。AC-P01-3，第三方账号不能按姓名直接覆盖已有本地身份。

## 9.2 P02｜自然人注册

依据：原方案§5.3.3，附件第40页。原文仅明确注册能力，未给出字段明细；下表为待业务确认的最小化D字段集合。

页面Steps建议为账户信息 → 验证与确认 → 注册结果，实名校验如需独立流程则不假称已由注册完成。普通输入使用单列表单，最多一屏一个清晰任务；移动端主按钮宽度随容器，不堆叠复杂说明。

| 字段 | 必填规则 | 校验及保护 |
| --- | --- | --- |
| 登录账号 | 是；若决定手机号即账号可合并此字段 | 身份域内唯一，规则与登录一致 |
| 手机及验证码 | 已采用手机号验证时必填 | 验证码绑定注册事务和手机号，服务端限流 |
| 密码、确认密码 | 密码账户必填 | 使用公众域有效策略；不默认复用政企域策略值 |
| 姓名 | 是否必填由实名方案确定 | 不用“姓名相同”作为唯一身份依据 |
| 证件类型、号码 | 仅实名业务确有必要时要求 | 服务端核验、最小化采集、脱敏；不能默认全文导出 |
| 必要服务声明 | 按实际条款展示 | 不默认勾选；用途、保存及处理规则须由责任方提供 |

提交前进行账号冲突与验证状态检查。重复提交使用注册事务ID去重；注册成功显示登录或返回业务应用入口。若实名服务未完成，只显示“注册成功，实名状态未核验/待核验”，不得显示绿色“已实名”。

**验收：** AC-P02-1，未完成必要手机号验证不能创建可用账号。AC-P02-2，重复提交不产生两个用户。AC-P02-3，注册成功和实名状态独立。AC-P02-4，公开页面不泄露已有自然人完整资料。

## 9.3 P03｜法人注册

依据：原方案§5.3.3，附件第40—41页。法人是组织主体，不是“法定代表人”的简称。

页面分账户信息、法人信息、联系人/经办人及结果。建议字段包括法人名称、统一社会信用代码或当地适用登记标识、账号、认证方式、经办人联系方式；不同地区法人标识不得硬套一种中国编码规则。法人证明材料、法定代表人信息、经办关系核验是否需要，由实际实名和关系方案决定，不将附件未说明的人工审批平台默认扩展为既定功能。

重复法人标识时不直接新建第二个法人，也不把当前注册人自动关联为管理者；提示通过已确定的找回或关系验证流程处理。关系未核验的账户不能冒充已获法人授权。结果页分别展示账户创建和法人核验/关系核验状态。

**验收：** AC-P03-1，法人名称与自然人姓名分开存储和显示。AC-P03-2，重复登记标识不能绕过验证接管法人账户。AC-P03-3，未核验时不展示已认证状态。C-04未关闭前，只实现已明确的注册与状态展示，不启用不确定的法人权限。

## 9.4 P04｜公众密码服务

依据：原方案§5.3.4，附件第41页。

复用A03/A04的表单与状态组件，使用公众域账户、策略和校验通道。自然人、法人分别定位相应账户，不将法人联系人手机号的控制权直接等同于法人账户控制权；找回方式依据已验证绑定关系。找回失败不暴露法人或关联人员敏感数据。

**验收：** AC-P04-1，公众找回接口不能重置政企管理员密码。AC-P04-2，重置后状态、会话与安全通知按公众域策略执行。

## 9.5 C01｜公众侧概览

依据：原方案§5.4.2，附件第41—42页。

指标为应用总数、用户总数、本月登录用户人数、本月登录用户次数；用户总数可拆分自然人与法人，明确两类对象计数，不能将关联子账号重复算作独立法人。下方显示近一周登录次数趋势和本月排行；筛选身份类型和日期。

公众侧概览采用与G01一致的卡片、对齐和图表规范，但取数严格限于公众域。当前后台访问者数量不能混入公众用户登录次数。

**验收：** AC-C01-1，人数与次数统计口径不同且准确。AC-C01-2，登录公共应用与登录管理后台可区分。

## 9.6 C02｜公众侧应用管理

依据：原方案§5.4.3，附件第42页。

复用G02/G03的应用登记和接入配置组件，字段包含应用名称、编码、环境、接入方式、访问/回调地址、凭据及启停状态。用户类型明确自然人、法人或两者；允许的认证方式与所选类型匹配。

**验收：** AC-C02-1，公众应用凭据不能访问政企域身份数据。AC-C02-2，未配置完成的认证方式不出现在应用登录页。AC-C02-3，公众应用访问策略必须显式配置或按合同验证，不默认放行。

## 9.7 C03｜自然人管理

依据：原方案§5.4.4，附件第42页。

筛选姓名/账号、脱敏手机号可匹配条件、账号状态、实名状态、注册时间；表格列为姓名、账号、手机（脱敏）、实名状态、启停状态、注册时间、最近登录、操作。主操作为查看、启用/停用，不提供原文未要求的任意修改实名结果功能。

停用需说明影响并写审计，保留关联关系和历史日志。查看证件等敏感信息需独立字段权限，服务端控制返回，不只是浏览器遮罩。

**验收：** AC-C03-1，查看详情不返回无权完整证件。AC-C03-2，关联法人可追溯但不自动授予其管理权限。AC-C03-3，停用保留核验历史，不能再建立合法登录会话。

**验收：** AC-C05-1，新增用户与新增关系不混计。AC-C06-1，后台日志、应用SSO日志和API日志可区分且能串联同一请求。AC-C06-2，不同角色可见的日志范围由后端限制。

# 10　权限、数据与跨模块业务规则

本章将原方案的集中授权、分级管理、身份同步细化为可实施规则。除已引用的源能力外，具体计算方式、时效、并发控制和数据状态均为D，须在需求评审时确认；不代表原方案已经规定这些细节。

## 10.1 BR-01｜四类资格严格区分

通过身份认证只能说明“是谁”；应用访问授权说明“是否可进入某应用”；应用角色与资源说明“进入后可做什么”；平台管理角色说明“可管理本平台哪些内容”。API授权还需校验调用主体、范围和有效凭据。不得用一个isAdmin布尔值替代所有上述判断。

| 判断对象 | 权限来源 | 强制执行位置 |
| --- | --- | --- |
| 平台页面及管理动作 | 系统角色、管理范围、分级委派 | 管理API；前端仅控制可见与可操作体验 |
| 业务应用入口 | 用户、机构、权限组等访问关系 | 认证/授权服务与接入应用 |
| 业务应用菜单按钮 | 应用角色和资源关系 | 应用服务端执行业务权限；前端显示相应菜单按钮 |
| 平台开放API | 应用或用户API授权 | API鉴权层及具体业务服务 |
| 敏感字段 | 字段可见策略、用途与管理范围 | 服务端查询结果和导出结果生成 |

## 10.2 BR-02｜有效授权与来源

建议使用统一授权台账记录主体、应用、角色、来源、范围、起止时间、状态和版本。有效访问关系可按以下逻辑计算：

`应用可访问 = 账号可用 AND 应用启用 AND 存在至少一条当前有效访问来源 AND 满足访问策略`

`有效资源 = 当前应用内各有效角色贡献资源的并集，再剔除停用资源及被明确阻断的项`

来源包括直接用户授权、有效任职命中的机构授权、有效权限组成员关系。时间限制和额外阻断策略如未启用，则不出现虚假的失效倒计时。应用访问资格和角色资源集合分开，配置应用角色时应保证存在相应访问关系或明确提示需要补充。

移除授权是移除某条来源，不能默认清空所有来源。需要“完全阻断”时，应采用账号停用、应用停用或经确认的专门阻断策略；本项目不擅自添加复杂拒绝规则引擎。

## 10.3 BR-03｜状态模型

| 对象 | 状态维度 | 必须遵守的区分 |
| --- | --- | --- |
| 用户 | 启停状态、锁定状态、凭据状态 | 启用不代表未锁定；解锁不代表启用；需改密不代表完整会话 |
| 应用 | 生命周期、检测状态、凭据状态 | 检测通过不自动启用；密钥失效不等于应用被删除 |
| 授权 | 关系状态、计算有效性、传播状态 | 保存成功不代表所有下游均已确认 |
| 同步 | 源实体版本、目标同步版本、任务状态 | 旧版本同步成功不代表新版本已同步 |
| 公众身份 | 注册状态、启停状态、实名状态 | 注册不自动实名；停用不删除已核验历史 |
| 法人关系 | 关联类型、来源、核验状态、有效时间 | 自然人实名不自动证明其法人代理权 |

机构有效状态受自身及有效祖先状态约束。停用机构使其不再提供有效机构任职资格与继承授权；用户在其他有效机构仍有有效任职时，不因此全局停用账号。显式停用用户账号则阻断该用户全部正常登录，不受其他任职来源抵消。恢复机构时不自动开启原本被独立停用的子机构或用户。

## 10.4 BR-04｜管理权限与范围

管理授权由功能动作、机构范围、应用范围共同限定。管理员创建/编辑用户时检查目标用户任职是否在可管理范围；给应用授予用户权限时同时校验应用与用户对象范围，不能只校验其中之一。下级委派权限不得超过上级当前可委派的有效集合。

同一管理员具有多个系统角色时，建议同一维度内合并可授予范围，再与当前动作所需约束求交。不能用“角色A有操作权+角色B看到某应用”推导出超出组织既定边界的组合越权；具体组合规则须在后端授权模型中统一实现并测试。

身份域是硬边界，不通过普通角色范围跨越。若某人有两个域的管理员身份，分别建立上下文、令牌及授权记录，前端切换仅选择上下文，不建立万能跨域令牌。

## 10.5 BR-05｜变更生效与缓存

建议授权服务维护权限版本。管理修改提交成功返回变更ID、新版本和传播状态；接入应用通过在线鉴权、短周期缓存或撤销事件等已约定方式更新。前端清缓存不能让后端权限生效；只刷新菜单不能视为回收完成。

本项目建议平台自身的停用/撤销在提交成功后立即对下一次受保护请求生效；跨应用效果按接入合同承诺时间验证，验收目标见第12章。不能仅签发一个长期离线JWT又承诺随时即时撤销，而不配备可执行的回收机制。

权限更新时客户端收到403或明确版本变更应重新获取权限快照；不得将拒绝请求自动无限重试。正在编辑的无权操作在提交时仍须拒绝，并提示权限已变更。

## 10.6 BR-06｜删除、归档和历史

用户、机构、应用、角色及授权必须使用稳定ID关联；删除名称不删除历史操作记录。普通删除优先采用逻辑删除或归档，具体留存/清理规则由数据责任方确认。涉及子对象和引用时先校验依赖，返回可操作的引用信息。

历史记录保存对象名称与编码的必要快照，避免对象改名后日志无法理解；敏感值不因“历史快照”成为泄漏出口。来源系统删除事件要保留墓碑或版本标记，避免旧同步任务恢复已删除对象。

## 10.7 BR-07｜批量与并发

批量操作包含操作ID、明确对象集合和所需版本。默认每个对象独立校验并返回逐项结果；必须整体一致的授权方案采用单事务提交，不允许不说明地半成功。页面必须知道当前操作是哪一种提交语义。

相同幂等键和相同请求体重复提交返回原结果；相同键但不同请求体返回冲突。编辑和授权使用版本号或ETag，版本冲突返回409，不静默“最后一次保存覆盖”。不允许前端只靠按钮置灰防止重复创建。

## 10.8 BR-08｜数据导入与导出

导入顺序先验证文件类型、大小与结构，再做字段、唯一性和权限校验；预览仅展示当前管理员可操作对象。机构父子关系必须完整；用户导入不能通过额外列授予未声明的管理员权限。建议文件上限10MB、单批5000行作为初始性能测试值，实际阈值经测试配置，不宣称来源已规定。

导出使用后台任务处理大范围数据，只输出所选字段及当前可见范围；默认脱敏。文件包含导出人、时间和范围说明，可选水印为D能力，不自动扩展复杂审批系统。CSV等格式需要防公式注入处理。下载请求重新校验授权，不只依赖拥有URL。

## 10.9 BR-09｜字段与标识约定

系统ID建议使用不可猜测的稳定字符串；编码用于业务识别但不承担安全边界。时间传输使用带时区的ISO 8601格式；存储和显示时区统一约定，默认展示Asia/Shanghai可作为项目选择，不写死到数据本身。排序字段为整数，同级并列时用稳定ID兜底排序。

账号、机构和应用编码的大小写及空白归一策略必须一次确定并同步应用于注册、搜索、导入和唯一性校验。手机号允许地区码；自然人证件、法人登记标识按实际覆盖地区配置校验，不使用姓名作为唯一键。

# 11　核心数据模型与接口需求

## 11.1 核心逻辑实体

下表用于约束前后端语义，属于D逻辑模型，不是最终物理表结构。敏感字段不得因出现在模型中就默认返回给所有前端页面。

| 实体 | 关键属性 | 关联与约束 |
| --- | --- | --- |
| IdentityDomain | id、code、name、status | 政企/公众域边界；不是默认多租户商业模型 |
| User | id、domainId、account、name、status、source、version | 账号在域内唯一；锁定和凭据状态独立 |
| Organization | id、domainId、parentId、code、type、region、status | 树无环；稳定ID；具备历史变化 |
| Appointment | id、userId、orgId、type、position、rank、sort、validTime | 一人多岗；排序和任职绑定；主职约束 |
| BusinessLine | id、code、name、scope | 机构多条线，保存直接关联及可推导继承来源 |
| Application / Client | appId、domainId、environment、clientId、protocol、status | 应用与客户端环境可区分；秘密不作为普通读取字段 |
| AppRole / Resource | id、appId、code、type、parentId、status | 角色、资源必须属于同一应用 |
| Grant | id、subjectType、subjectId、appId、roleId、source、scope、version | 统一授权台账；保留来源与撤销历史 |
| PermissionGroup | id、name、version、status | 关联多应用角色及用户，不复制不可追溯权限 |
| AdminRole / Delegation | id、functions、orgScope、appScope、parentGrant | 系统管理权限与应用角色分离 |
| ApiPermission / ApiGrant | permissionCode、principalType、principalId、scope | API标识稳定；主体认证与授权同时校验 |
| AuthTransaction / Session | id、domainId、clientId、state、expiresAt | MFA和改密事务绑定；会话可撤销 |
| SyncConfig / Task / Record | id、target、sourceVersion、status、attempt、eventId | 幂等、顺序、关联重试、准确终态 |
| AuditEvent | eventId、actor、action、target、result、time、traceId | 不可普通修改；敏感信息受控 |
| Person / LegalEntity | id、accountRef、verificationState、source | 自然人、法人主体独立；注册与实名分开 |
| LegalRelationship | id、personId、entityId、type、source、status | 代理、关联及子账号关系不靠姓名推断 |
| ExtensionDefinition / Value | objectType、fieldCode、type、sensitivity、value | 定义版本和字段权限一致 |

## 11.2 接口通用约定

管理业务接口建议前缀`/api/v1`；身份域由认证上下文和明确路径共同确定，不信任请求体随意传入的domainId。所有对象型接口检查对象归属和权限。标准认证端点按协议实现及发现文档发布，不假设所有OAuth/OIDC路径必须与管理API同前缀。

列表查询统一page、pageSize、sort、filters；响应包含items、total、page、pageSize。空结果返回items为空数组和total=0；失败返回错误，不返回空数组假装无数据。服务端限制最大pageSize并拒绝不支持的排序字段。

普通成功响应提供data、requestId；异步写入返回202及taskId/changeId、当前状态。错误返回稳定业务码、可读消息、fieldErrors和requestId；不要把SQL、堆栈、秘密材料发给前端。

| HTTP / 业务场景 | 前端处理 | 后端要求 |
| --- | --- | --- |
| 400 / 字段校验失败 | 对应Form.Item显示错误 | 返回字段路径和可读原因 |
| 401 / 未认证或会话过期 | 受控重登；保留安全返回路径 | 不把无权限混用为过期 |
| 403 / 无权或越范围 | 显示权限不足并停止操作 | 不通过不同响应暴露无权对象细节 |
| 404 / 不存在或不可公开定位 | 返回列表或结果页 | 敏感对象可按统一策略隐藏存在性 |
| 409 / 并发版本或唯一冲突 | 提示刷新/修改冲突字段 | 不静默覆盖最新数据 |
| 429 / 频率受限 | 按返回等待信息提示 | 限制在服务端执行 |
| 5xx / 服务失败 | 可重试说明及追踪号 | 幂等写请求重试不得重复执行 |

## 11.3 管理API能力清单

## 11.4 授权变更契约示例

建议请求字段：操作ID、目标应用、期望权限版本、增加关系、移除关系、变更原因。预览接口返回当前版本、预计新增/失去访问人数、仍有其他来源的对象及不可处理项。提交必须重新校验，预览结果不是永久授权凭证。

```json
{
  "operationId": "本次操作的唯一标识",
  "appId": "app_example",
  "expectedVersion": 18,
  "add": [{ "subjectType": "USER", "subjectId": "user_example" }],
  "removeGrantIds": [],
  "reason": "岗位调整后的应用开通"
}
```

建议成功结果包括changeId、newVersion、effectiveAt、propagationStatus、perTargetResults。部分目标尚未确认时返回PENDING或PARTIAL，不返回笼统的“全局完成”。以上字符串是契约示例，不是预置生产账号或真实数据。

## 11.5 同步事件契约

下游接口至少能识别eventId、sourceSystem、domainId、entityType、entityId、operation、sourceVersion、occurredAt、payload。下游返回是否接受、实际应用版本及可分类错误码。重复eventId应幂等处理；低版本事件不覆盖高版本状态；父机构缺失等依赖错误可重试，字段不合法等永久错误要求修正。

用户停用、机构移出范围和删除事件的语义必须在合同中明确。没有定义“删除”的下游，不能自动把停用转换为物理删除。同步服务记录原事件与尝试记录，前端只展示脱敏后的可理解内容。

## 11.6 认证与第三方集成契约

授权码流程要求校验客户端、回调、事务关联、有效期和PKCE。采用OIDC时按规范校验签发方、受众及相关身份声明；ID Token用于身份声明，不能代替任意API的访问凭证。服务端保密客户端的凭据保存在受控服务端，不进入React构建产物。

供应商适配层必须把未配置、连接失败、用户取消、超时、核验失败和核验通过分开；记录供应商请求编号但过滤敏感原文。系统需要明确供应商超时、重试和降级规则，不能因为供应商不可用就放行登录或实名。

依据：[OAuth 2.0安全最佳实践RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)、[OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)。OIDC是T级建议扩展，不在原方案中冒称已有实现。

## 12.1 安全与可靠性要求

NFR-S01：生产通信采用HTTPS；登录会话与凭据由受控服务端管理。建议浏览器通过BFF/服务端会话与认证服务交互，使用适当的HttpOnly、Secure和SameSite Cookie，并配套CSRF防护。若采用其他架构，需要等效安全设计；不把长期刷新令牌放入普通本地存储作为默认方案。

NFR-S02：前端、接口和导出均执行输入、输出与文件校验。接口鉴权覆盖对象范围、字段可见性和动作权限。上传内容需验证实际格式与恶意内容，配置URL限制目标地址，避免将测试连接功能变为任意请求代理。

NFR-S03：认证失败、越权尝试、敏感授权变更、密钥轮换、同步失败和系统策略变更均应有可关联日志。日志记录失败时不能悄悄丢弃关键安全事件；应有可靠缓冲、告警或受控降级方案，由技术设计落实。

NFR-S04：普通管理员无法从管理页面取得用户密码、令牌、完整密钥或数据库凭据。受保护信息的查看与导出独立控制。测试环境使用脱敏或合成数据，生产页面不展示固定“演示管理员”和假数据统计。

NFR-S05：管理员注册和初始恢复账号由受控部署流程建立；不得把固定默认管理员密码写进前端或公共配置。备用恢复流程应记录责任人与使用审计，并定期验证，不设置不可审计的万能后门。

# 13　React与Ant Design前端实施契约

## 13.1 工程边界与目录建议

前端采用一个代码仓库和统一设计系统，按身份域与功能模块划分。是否以同一域名/端口部署由安全与运维方案确定，不能用“同一前端工程”推导出认证域和业务域必须共用Cookie边界。原方案未要求多个前端工程，本项目不为了区分角色而复制整套页面。

```text
src/
```

## 13.4 业务组件封装

建议封装PageSection、QueryTable、OrganizationPicker、IdentityPicker、PermissionSourceView、GrantChangePreview、AsyncTaskResult、SensitiveText、AuditDetail九类业务组件。封装保留antd语义，不包成只接受任意JSON、无法处理复杂状态的黑盒低代码引擎。

QueryTable统一查询、分页、空态、失败和批量选择；OrganizationPicker统一机构范围、包含下级与搜索；GrantChangePreview统一授权差异和来源解释；AsyncTaskResult统一任务已提交、执行中、部分失败与重试；SensitiveText仅展示服务端已经授权返回的数据，绝不把未经授权明文提前发到浏览器再遮挡。

## 13.5 状态管理、路由与数据请求

URL保存可分享的查询条件、页码及对象ID，不保存密码、令牌、完整证件或秘密配置。路由进入先检查认证上下文，数据请求服务端再次鉴权。切换对象、域或应用时取消旧请求或忽略其过期响应，避免后返回的旧数据覆盖新选择。

页面状态区分初始加载、刷新、提交、后台任务、成功、失败；不能用一个loading变量控制整个系统。编辑草稿默认只保存在当前页面内存，涉敏内容不自动持久化。所有异步错误有可观察记录和用户可执行下一步。

## 13.6 设计及代码质量门禁

界面开发先实现统一框架和八类页面模板，再逐页装入业务，避免每位开发者各自创造组件风格。至少选应用列表、组织工作区、授权页、同步详情、公众注册五个代表页完成设计验收后，再扩展全模块。

提交合并前必须通过类型检查、静态检查、关键交互测试、无权限场景测试和必要视觉回归。页面不可存在占位按钮、点击无响应、静态成功提示、伪造统计或写死管理员权限。所有新控件优先使用antd，确需自定义控件时说明原因、键盘行为及Token映射。

验收时提供各代表页正常、加载、空、失败、无权、长文本和窄屏截图。文档声明遵循Ant Design不代表成品天然符合规范，实际截图与交互才是验收依据。

## 15.3 Mock数据与一致性规则

所有测试名称、机构和联系方式均为虚构数据；域名采用example.com、example.org等保留示例域。不复用原方案内具体人员信息作为账号。数据包括正常、停用、锁定、待完善、待验证、授权到期、部分失败、未配置等场景，确保界面不只呈现理想状态。

用户、组织、应用、角色、资源、权限组、授权、同步任务、审计事件使用稳定ID关联。应用人数根据有效权限去重计算；撤销单个来源后仍有其他来源时，界面继续显示可访问并列出剩余来源。身份域、应用状态、用户状态、授权期限及资源启停都参与Mock计算。系统管理资格与业务应用访问资格不互相推导。

创建、修改、停用、授权、撤销、配置保存等动作通过统一Mock服务执行，统一处理延迟、异常、校验及事件记录。页面不得直接随机伪造成功提示。异步任务区分“已提交”“执行中”“部分成功”“成功”“已取消”；点击重试只处理失败项，不重做已成功项。中止不回滚已完成项。

## 15.4 存储、重置与错误测试

业务Mock数据按版本存入localStorage；测试登录会话存sessionStorage；不保存用户输入的真实密码、证件资料或认证令牌。浏览器数据可被修改，不具备安全属性。恢复初始数据前二次确认，恢复后同步更新全部页面；数据结构版本不匹配时提示恢复，不使用旧数据盲目运行。

页面提供“前端评审环境”说明入口，包含测试账号、Mock边界、数据重置和故障注入。故障注入只影响下一次Mock写入，失败后保留输入且不更改原记录，用于检查异常状态。长任务失败为确定性规则，不用每次刷新变化的随机数。

## 15.5 前端操作规范补充

编辑Drawer用统一560/736px尺寸；复杂应用详情使用独立页签，授权编辑使用宽工作区及确认预览；所有表格、Modal、Drawer、Form、Tree、Select、Button、Tag来自antd原生组件。自有CSS只处理布局及业务容器，颜色由Token注入。不通过仿制Ant Design样式的HTML元素替代基础组件。

高风险动作必须显示对象、影响与确认动词。导入采用UTF-8 CSV，提供模板、解析预览、逐行错误及提交结果；Excel工作簿导入属于后续适配，不将CSV导入描述成Excel原生解析。导出有筛选范围及敏感字段脱敏，并防止CSV公式执行。数字、日期、空值及状态文案遵循第5章。

## 15.6 后端替换边界

页面只调用src/mock或服务适配层暴露的读写函数，不在页面中拼接虚假令牌、硬编码真实供应商或真实API密钥。未来接入后端时替换服务适配器并新增后端鉴权，不用推翻页面结构。数据模型、分页语义、错误码、版本冲突及授权来源字段与第11章保持一致。

前端鉴权只控制界面可见性与评审行为；生产阶段必须把角色范围、访问限制、自授权限制、令牌校验和数据脱敏重新落实到服务端。不存在“前端已经校验，所以后端无需校验”的实施捷径。
